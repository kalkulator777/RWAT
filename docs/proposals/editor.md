# Веб-редактор паков RWAT: проект v1 (фаза 2)

**Статус:** проект, 2026-11-02. Основа: `docs/roadmap.md` — решения R4–R12, фаза 2 и её «Готово, когда». Что пак умеет и где кончается движок — `docs/proposals/pack-capabilities.md`. Поля формата — `schema/` и сгенерированный из неё `docs/pack-format.md`. Пути Java — от `src/main/java/com/muzhik17/trainsmod/`.

**Как читать.** Это решения, а не обзор вариантов. Где был выбор, рядом одной строкой сказано почему. По документу работают агенты-исполнители: раздел 7 раздаёт работу по этапам, у каждого агента своя зона файлов. Раздел 3.13 — контракты между модулями: агенты одного этапа пишут код против них, не дожидаясь друг друга. Не согласен с решением — пиши в отчёт, а не обходи его.

## 0. Коротко

- **Что:** статический сайт в `editor/` (TypeScript, Vite, three.js; R8). Работает в браузере и без сети, лежит на GitHub Pages: `https://kalkulator777.github.io/RWAT/`. Схемы выкладываются рядом, по их `$id`: `https://kalkulator777.github.io/RWAT/schema/*.json`.
- **2a — свои паки.** Открыть папку или zip, увидеть модель с раскраской по ролям, заполнить формы по схеме, разметить пол, двери и кресла в 3D, проверить так же, как проверит движок, сохранить.
- **2b — IR-паки.** Конвертер `tools/ir2rwat.py` и генератор пола `tools/floorgen.py` работают в браузере как есть, через Pyodide. Редактор правит оверрайды поверх выведенного и сохраняет рецепт без ассетов (R10).
- **Логика движка, нужная на лету, портируется в TypeScript** по списку раздела 4. Каждый порт сверяется с Java (и с Python, где есть третий порт) на общих эталонных данных `fixtures/golden/` (R9).
- **Этапы:** M0 (подготовка в Java и Python) идёт параллельно с M1 (каркас). Дальше M2 — порты и формы, M3 — 3D, M4 — инструменты разметки и проверки, M5 — звук, сохранение и выпуск 2a, M6 — 2b, M7 — выпуск v1. В каждом этапе 2–4 агента с непересекающимися файлами.

## 1. Цель и границы v1

### 1.1. Цель

Сделать пак без ручного JSON и без замеров «на глаз». Числа разметки берутся с модели (кадр OBJ, как в Blender, R6). Ошибки видны до запуска игры, теми же правилами, что у движка. Конвертированный IR-пак правится и пересылается как разметка, без чужих ассетов.

### 1.2. 2a — свои паки формата RWAT

- **Открыть:**
  - папку пака через File System Access API (Chromium; чтение и запись на месте);
  - zip в любом браузере;
  - папку только для чтения через `<input webkitdirectory>` в Firefox и Safari.
- **Дерево пака:**
  - `pack.mcmeta` (секция `pack` и блок `rwat`);
  - типы и модели, парами по id; тип без модели и модель без типа помечены (D4);
  - стили рельсов, имена (lang), ассеты.
- **3D-вид модели в кадре OBJ.** Объекты раскрашены по ролям `schema/obj-conventions.json`. Список объектов показывает разобранные роли, флаги и модификаторы.
- **Формы по схеме.** Единицы `x-unit`, умолчания движка (`default` или `x-engine-default` с посчитанным значением), пометки `x-status` и `deprecated`, описания на en и ru.
- **Инструменты разметки:**
  - зоны пола: на виде сверху, с высотой;
  - двери: в том числе коробка по объекту модели;
  - кресла машиниста;
  - фары: показ направления и цвета;
  - шарниры органов: ось, точка и дуга хода.
- **На лету:**
  - где может стоять игрок (`FloorRegion`): куски пола, разрезы закрытых внутренних дверей, мостики открытых, выходы, кабины;
  - все проверки `FloorCheck`.
- **Предпросмотр:**
  - ход дверей (`.anim` и створки `ROT`/`TL`);
  - органы: ползунок значения; `ROT` и `TL` с `OFFSET` и `INVERT`;
  - свет по группам: `LCG`, `LINVERT`, `FULLBRIGHT`, лампы салона, фары;
  - ливреи и головы сцепок в сцепленном и расцепленном состоянии.
- **Звуки.** Назначение (`.ogg` пака или звуковое событие) и прослушивание `.ogg` пака.
- **Имена en и ru:** `wagon.*`, `rail.*`, `light.*`; для групп света видна цепочка запасных имён.
- **Панель проверок** со ссылками на поле, объект, зону, дверь или кресло. Отмена и повтор. Сохранение в папку и в zip.
- **Стиль рельсов:** форма из двух ключей и предпросмотр тайла, повторённого вдоль пути. Рельсы и основание раскрашены по правилам `rail_tile` из `obj-conventions.json`.

### 1.3. 2b — IR-паки

- **Импорт IR zip** (одного или нескольких — источников рецепта) или открытие готового рецепта `packs/<имя>.json` с папкой оверрайдов.
- **Конвертация в браузере — существующий Python через Pyodide, без порта (R9).** Вызываются `ir2rwat.Converter` и `floorgen` из файлов репозитория байт в байт.
- **Правка оверрайдов поверх выведенного.** На каждое поле три состояния: «как вывел конвертер», «своё значение», «удалить» (`null`). Двери правятся по id (объект `doors`). У пола свои параметры `floor` с перегенерацией.
- **Экспорт:**
  - рецепт и оверрайды без единого ассета (R10): этим делятся;
  - готовый пак для себя — zip тех же байт, что пишет `ir2rwat.py --zip`.

### 1.4. Готово, когда (фаза 2 целиком)

Из карты, в проверяемом виде:

1. **Пак-пример собирается в редакторе с нуля по сгенерированным моделям.** Проверка — прогон журнала правок (Vitest) и сокращённый сценарий в Playwright (M5). Входы — OBJ, MTL, PNG и `.anim` из `run/rwat_packs/RwatExamplePack/`. Результат — декларации и lang-файлы, равные файлам репозитория как JSON-значения. Пак собран не из готовых деклараций.
2. **MVP открывается и правится без потерь** (M6):
   - открыт рецепт `packs/mvp.json` с 46 файлами оверрайдов и обоими zip MVP;
   - правка одного поля меняет в одном файле только эту строку, остальные файлы сохраняются байт в байт;
   - экспорт рецепта не содержит ни одного ассета;
   - готовый пак из браузера совпадает с `ir2rwat.py --zip` байт в байт. Это проверяется на синтетическом IR-паке `tools/tests/irpack.py` в CI и один раз на MVP руками агента до R12.
3. **Сайт выложен** на GitHub Pages из Actions и работает без сети после первого открытия.
4. Ворота каждого этапа (раздел 7) пройдены, CI зелёный.

### 1.5. Сознательно не входит в v1

- **Правка сгенерированного пака.** Пак с `RWAT_CONVERSION.txt` открывается только для просмотра, с подсказкой «правится рецепт». Так решено в карте («Не делаем»).
- **Порт конвертера или генератора пола на TypeScript.** Только Pyodide (R9).
- **Режим «прогулка» по вагону** (порт `RiderWalk.step`, `exitDoor`, `gangwayArrival`) — в v1.1. В v1 «где стоять» показан статично: куски, разрезы, мостики, выходы. Почему: этого хватает для всех проверок, а ещё один порт с ветвистой логикой шага — лишняя поверхность расхождений.
- **Возможности, которых нет в движке:** корпус `hull`, многоугольники пола, `FLOOR_n`, наборы вагонов, пассажирские места, колея. Они приходят в редактор вместе с движком (фазы 3 и 5): «код + схема + инструмент редактора + пак-пример».
- **Несколько паков сразу.** Ссылки на текстуры чужого пространства имён (`ns:path`) помечаются «внешняя, не проверена» (вопрос 9.4).
- **Прослушивание ванильных звуков `minecraft:…`.** Ассеты Mojang в редактор не кладём. Подключение папки игрока — вопрос 9.2.
- **Свободная правка OBJ и текстур.** Редактор не моделлер: геометрию правят в Blender.
- **Мобильные устройства.** Только настольный браузер, от 1280×720.
- **Телеметрия, аккаунты, сервер.** Всё работает локально в браузере, файлы никуда не уходят.

## 2. Сценарии

Термины: **дерево** — левая панель, **вид** — 3D в центре, **инспектор** — правая панель, **нижние вкладки** — «Проверки», «Объекты», «Предпросмотр», «Журнал», «Лог» (раздел 6.1).

### 2.1. Новый пак с нуля (из своих OBJ)

1. «Новый пак» → мастер:
   - имя пака (папка или zip);
   - пространство имён (проверяется по шаблону `common.schema.json#/$defs/namespace`);
   - блок `rwat`: `format` 1, `name`, `version`, `authors`, `license`, `description`.
   
   Мастер пишет `pack.mcmeta` (секция `pack` с `pack_format` 34 и `supported_formats` [34, 48], как у конвертера).
2. «Добавить вагон» → id типа и папка модели, например `stock/coach/`. Затем перетащить в окно OBJ, MTL, PNG и, если есть, `.anim`.
   - Файлы ложатся в `assets/<ns>/<папка>/`.
   - Путь, который Minecraft не примет (заглавные, пробелы), — отказ со списком таких файлов.
   - После M6 есть кнопка «переименовать и переписать ссылки»: её делает `ir2rwat.rewrite_references` через Pyodide.
   - Редактор создаёт пару: тип `data/<ns>/wagon_types/<id>.json` и модель `assets/<ns>/wagon_models/<id>.json` с `obj`.
3. Вид показывает модель. В «Объектах» роли разобраны: тележки, колёсные пары, двери, органы, свет, интерьер, выброшенное. Незнакомое — кузов, и это не ошибка.
4. Инспектор, форма типа: `length`, `bogies`, `mass_t` и остальное.
   - Обязательные поля подсвечены.
   - Пустое поле показывает значение движка (например, `resistance.a` = 7·`mass_t` + 200 → «494 Н при 42 т»).
   - Шкворни можно взять с модели кнопкой «по центрам BOGEY_*» (правило `measurePivots`).
5. Разметка (2.3), органы и свет (2.4), имена: вкладка «Имена», en и ru.
6. «Проверки» пусты → «Сохранить»:
   - Chromium: выбрать папку (`showDirectoryPicker`) или скачать zip;
   - другие браузеры: скачать zip.

### 2.2. Открыть существующий пак

1. «Открыть папку» (Chromium, запись на месте) или «Открыть zip» (любой браузер). В Firefox и Safari есть ещё «Открыть папку для чтения».
2. Редактор строит индекс файлов: пути и размеры, без чтения содержимого. Дальше он читает:
   - `pack.mcmeta`;
   - все декларации (JSON маленькие);
   - lang-файлы.
   
   OBJ и текстуры читаются лениво: когда модель открывают или запускают «Проверить все модели».
3. Пак `rwat.format` новее 1 или с битым номером открывается только для просмотра, с объяснением, как в игре. Пак без блока `rwat` открывается с предупреждением и предложением дописать блок.
4. Пак с `RWAT_CONVERSION.txt` — только просмотр и ссылка на сценарий 2.6.
5. Если в браузере есть несохранённая сессия этого пака (журнал в IndexedDB), предлагается восстановить её.

### 2.3. Разметить вагон: пол, двери, кресла

1. **Пол.**
   - Инструмент «Зоны» переключает вид сверху (ортографическая камера вдоль −Y, перёд −X слева, как в Blender «Top»).
   - Зона — прямоугольник с привязкой: к сетке 1/16 блока (шаг `floorgen.CELL`), к вершинам модели, к краям других зон.
   - Высота зоны (`min.y`) — клик по полу модели в 3D (берётся y вершины под курсором, как записано в OBJ) или число. `max.y` по умолчанию `min.y` + 2.5 (как у конвертера), движок его не читает.
   - Поверх рисуется, где может стоять центр игрока: куски `FloorRegion` при всех дверях закрытыми и при открытых — переключатель «двери: закрыты / открыты / как в предпросмотре».
2. **Двери.**
   - Выделить створку или створки в виде либо в «Объектах» → «Дверь по объекту». Коробка — габарит выделенного в кадре OBJ.
   - В инспекторе: id, флаги `inner`, `fixed`, `connecting`, `group`.
   - Стрелкой показаны ось и сторона «наружу» (`Door.axis`, `Door.outward`), прямо видно, боковая это дверь или торцевая.
   - Створки `DOOR_<n>` с `ROT`/`TL`, не попавшие ни в одну коробку (`doorHolding` = −1), — предупреждение со ссылкой на объект.
3. **Кресла.**
   - Инструмент «Кресло»: клик по подушке ставит `at` (верх подушки).
   - Поворот `yaw` — циферблат, 0 — вперёд, больше 90° от «вперёд» — кресло ведёт назад, это подписано.
   - Круг досягаемости 2.5 и высота над полом (допуск 0.2…1.5) видны сразу.
   - Видно, к какой кабине кресло отнесено (`CabArea`).
4. **«Проверки»** показывают находки `FloorCheck` по-русски или по-английски. Клик по находке выделяет зону, дверь или кресло.

### 2.4. Настроить локомотив: органы, свет, звуки

1. **Органы.** «Объекты» → фильтр «органы». У органа:
   - ключ `<KIND>_<n>` и класс (рукоятка, прибор, виджет…);
   - группа `CG`, подпись `LABEL`, флаги;
   - маркер шарнира (`<KEY>_ROT`): точка, ось, угол.
   
   Ползунок «значение» 0…1 двигает орган так же, как игра (`ControlValue.value`, `StockModel.Control.transform`). У реверсора значение центрировано, у прибора — через `RANGE`. Ось, которая крутит не туда, видна сразу; лечится в Blender (маркер и порядок вершин).
2. **Ручник.** Список `handbrake` модели — выбор из органов модели (`WIDGET_<n>` и т. п.); `HANDBRAKE_<n>` распознаётся сам.
3. **Свет.**
   - Вкладка «Свет» в предпросмотре: переключатели групп `LCG` (не больше 64).
   - Объекты группы горят, `LINVERT` — наоборот. Лампы салона (острова `FULLBRIGHT` ≥ 0.3 в группе с `INTERIOR`) — точки света.
   - Фары: конус в свою сторону (по половине модели) и цвет `_0X…`.
   - Огонь (светящаяся грань, лампа, фара) горит по `ModelParts.lit`: без группы — всегда, с группой — пока она включена, с `LINVERT` — пока выключена. Тот же код у граней, ламп салона и фар.
   - Имена групп — во вкладке «Имена» с цепочкой: ключ пака → ключ мода → `_LABEL_` → код.
4. **Звуки** (вкладка инспектора модели):
   - `idle`, `wheels`, `horn`, `bell` — петли (строка или `start`/`main`/`stop` с `pitch`/`volume`);
   - `clack`;
   - `doors` по id дверей типа;
   - `controls` по ключам рукояток модели.
   
   Ссылка выбирается из `.ogg` пака или вписывается как событие (`minecraft:…`). Кнопка «▶» играет `.ogg` пака на двух концах диапазона и между ними: ползунок линейный и подписан «приближённо», потому что кривые движка редактор не повторяет. У `horn` и `bell` подписано, что берётся второе число диапазона. Ключ `controls`, который никогда не звучит (`WIDGET_*`, `ENGINE_START_*`…), — предупреждение.

### 2.5. Проверить и сохранить

1. «Проверки» обновляются после каждой правки (с задержкой 150 мс). Источники:
   - схема;
   - правила загрузчика вне схемы: геометрия типа, пары тип ↔ модель, существование файлов, ключи анимаций и звуков;
   - `FloorCheck`;
   - проверки моделей как `/rwatc packs validate`.
   
   Каждая находка: важность, текст на языке интерфейса, ссылки.
2. «Проверить все модели» по очереди грузит в фоне все OBJ пака (прогресс, отмена) — аналог `/rwatc packs validate`.
3. «Сохранить» показывает список изменений по файлам: новые, изменённые со счётчиком строк, удалённые. Дальше:
   - **в папку:** пишутся только изменённые файлы; правка существующего JSON — минимальная, форматирование и порядок ключей остальных мест не трогаются;
   - **в zip:** содержимое неизменённых файлов байт в байт то же, сам архив собирается заново (порядок записей и время — фиксированные, как у `ir2rwat.write_zip`).
4. Ошибки сохранению не мешают: пак с ошибкой можно сохранить, загрузчик просто его пропустит. Это ещё раз говорится в окне сохранения.

### 2.6. Импорт IR-пака и правка оверрайдов

1. «Импорт IR» → выбрать zip IR. Мастер рецепта: `name`, `pack_dir`, `namespace`, `sources[]` (`zip`, `root`, `label`), `id_strip_prefix`.
   
   Или «Открыть рецепт»: папка с `packs/<имя>.json` и его `overrides_dir`. Zip-источники, названные в рецепте, находятся рядом (если открыт корень репозитория) или выбираются по одному.
2. Pyodide грузится один раз (полоса загрузки, потом из кэша). Источники монтируются без копирования (WORKERFS). Список типов — из `Converter`.
3. Открыть тип → `Converter.plan(id)`, вывод — в журнал «Лог». Вид показывает IR-модель и разметку из плана. OBJ, MTL и текстуры читаются прямо из zip-источника, по записям, которые нашёл конвертер (`Source.find`: любой регистр, `../`). TypeScript сам путей IR не ищет.
   - Поле с оверрайдом выделено.
   - Рядом серым — выведенное значение: план без оверрайда этого типа, вызов через мост.
4. Правка: формы те же, что в 2a, но пишут в `packs/<имя>/<id>.json`.
   - `null` удаляет поле.
   - Двери — объектом по id, удаление выведенной двери — `null`.
   - `floor` — параметры генератора; «Перегенерировать пол» — заново `plan` с новым `floor`, разница показана наложением.
   - `name` и `lights` пишутся в оверрайд, а не в lang.
5. «Экспорт рецепта» → zip: `packs/<имя>.json` и `packs/<имя>/*.json`, без ассетов. Комментарии `_…` сохранены.
   
   «Готовый пак для себя» → полная конвертация в фоне (прогресс по типам) → zip, те же байты, что `ir2rwat.py --zip`. Или запись в папку в Chromium.
6. Предупреждение о лицензии источника всегда на виду: готовый пак — только для себя (CC BY-NC-ND у MVP).

### 2.7. Поделиться разметкой

Получатель с тем же IR zip открывает присланный рецепт (2.6, шаг 1) и получает тот же пак.

### 3.4. Как модули общаются

- **Состояние** — сигналы в одном хранилище (`app/store.ts`): пак (модель и журнал), выделение (`Link[]`), язык, режим (2a или 2b), открытая модель, состояние предпросмотра. Модули читают сигналы и подписываются; производные (находки, куски пола) — `computed` с задержкой.
- **Изменения пака — только командами:** `journal.dispatch(command)`. Панели, формы и инструменты не трогают модель напрямую. Отсюда отмена, повтор, автосохранение и сценарные тесты одним механизмом.
- **Выделение** — один сигнал `Link[]`. Дерево, вид, «Объекты», «Проверки» и инспектор пишут в него и показывают его. Клик по находке = запись её ссылок.
- **Воркеры** — через `comlink`: `modelWorker.load(packSource, objPath) → LoadedModel` (буферы переданы как transferable), `pyodide.plan(typeId) → PlanResult`. Воркер не держит состояния пака: получает, что прочитать, и отдаёт результат.
- **Панели регистрируются сами:** `app/` находит их через `import.meta.glob('../panels/*/index.ts')`. Новая панель не правит файлы оболочки, и агенты не конфликтуют в `app/`. Так же строки интерфейса: у модуля свой `i18n.ts` (ru, en), их собирает `i18n/`.
- **Объявление панели** (`PanelDef` в `app/registry.ts`, A1.1):
  - `id` — строчные слова через дефис, уникальный;
  - `slot` — место на экране: `toolbar` (кнопки верхней полосы), `tree`, `view`, `inspector`, `bottom`;
  - `order` — порядок в месте; нижние вкладки 6.1 — «Проверки» 10, «Объекты» 20, «Предпросмотр» 30, «Журнал» 40, «Лог» 50;
  - `title` — ключ i18n;
  - `modes` — `['2a']`, `['2b']` или оба (по умолчанию);
  - `component` — компонент Preact без свойств; состояние он читает из сигналов `app/store.ts`.
  
  Несколько панелей в `tree`, `inspector` и `bottom` становятся вкладками; скрытые остаются смонтированными и не теряют состояние. Битое объявление (повторный `id`, неизвестное место) роняет запуск и тест `app/registry`. Сигналы пака, журнала, открытой модели и предпросмотра добавляются в `app/store.ts`, когда их модули подключают (дирижёр или назначенный им агент): `app/` чужим агентам не принадлежит.

### 3.5. Модель пака и журнал правок

- **Файлы:** `path → {original: Uint8Array | null, text?: string, value?: unknown, kind: 'json'|'binary'|'text'}`. JSON разбирается сразу, остальное лениво.
- **Операция** (`Op`, 3.13) — данные: `set`, `remove`, `insert` по JSON-указателю в файле; `putFile`, `deleteFile`, `renameFile`. У каждой есть обратная.
- **Команда** — подписанный набор операций, применяемых разом. Переименование типа меняет оба файла и lang-ключи и предлагает записать старый id в `aliases`, чтобы не потерять составы в мирах. Всё это одна команда.
- **Перетаскивание** ручки зоны — одна команда: операции с одним `coalesceKey` сливаются до отпускания мыши.
- **Отмена и повтор** — стек команд с обратными операциями, глубина 500. Выделение и предпросмотр в журнал не входят.
- **Журнал сериализуется в JSON.** Он же сохраняется в IndexedDB после каждой команды (восстановление после сбоя, M5) и служит сценарием в тестах (`editor/test/replay/`).

### 3.6. Сохранение: неизменённое — байт в байт

- **Файл без операций** не пишется (папка) или копируется содержимым как был (zip).
- **Изменённый JSON:** считается разница между исходным значением и текущим (по указателям), и каждая разница применяется к **исходному тексту** через `jsonc-parser` `modify` + `applyEdits` с отступом, взятым из файла. Меняются только затронутые места. Комментарии-ключи `_…` рецепта и оверрайдов остаются.
- **Новый JSON** пишется функцией `dump` — порт `ir2rwat.dump` — из чтения без потерь (`parseLossless`: число хранит свою запись), иначе `20.0` и `20` склеиваются в одно число и запись теряет, что было в файле: отступ 2, массив скаляров в одну строку, `ensure_ascii=False`, перевод строки в конце. Файлы редактора и инструментов выглядят одинаково. Целое значение пишется без `.0` (Python пишет `20.0` у float): разница только в записи, движок и инструменты читают одинаково.
- **Числа, снятые с модели**, — это координаты вершин как в OBJ или кратные шагу сетки; пишутся кратчайшей записью, которая читается обратно в то же число.
- **Запись в папку** (FS Access) идёт файл за файлом через `createWritable` (Chromium пишет во временный файл и подменяет). Порядок — как у конвертера: `pack.mcmeta` последним.

### 3.7. Формы по схеме

- **Источник — сами файлы `schema/*.json`**. *Решение дирижёра:* редактор грузит их с сайта (`fetchSchemaFiles`; сборка кладёт `schema/` в `dist/schema/`, 5.4), в сборку они не встраиваются (`import.meta.glob` не нужен). Отдельной копии нет: правка схемы сразу меняет формы (R4).
- **По схеме строится описатель поля:**
  - тип;
  - `enum`;
  - пределы (`minimum`, `exclusiveMinimum`, `maxItems`…);
  - единица `x-unit` с подписью из `pack-layout.json#units`;
  - умолчание `default` или `x-engine-default` (`-ru`);
  - кадр `x-frame`;
  - статус `x-status` с меткой из `pack-layout.json#statuses` и `x-status-note`;
  - `deprecated`;
  - описание `description` или `x-description-ru`.
- **Виджеты:** число с единицей, перечисление, флаг, строка с шаблоном, массив скаляров (`bogies`, `vec3`, диапазон `[a, b]`), словарь (`liveries`, `animations`, `sounds.doors`, `sounds.controls`), список объектов (`doors`, `interior`, `cab.seats`), `oneOf` (петля звука: строка или объект).
- **Умолчание движка видно в пустом поле.** Формулы `x-engine-default` считает порт `StockDefaults`, так что подпись «7·mass_t + 200» показывает и число. Явный `0` отличается от пустого поля (правило парсера: «пропущенное = значение движка, явный 0 = ноль»).
- **Зарезервированное поле** (R7) помечено «Зарезервировано, в игре ничего не меняет». Если оно задано — предупреждение.
- **Незнакомые ключи файла** — отдельный блок «Незнакомые ключи» с подсказкой ближайшего (порт `validate_pack.suggestion`) и быстрой правкой «переименовать в …».
- **Поля с `x-frame`** (зоны, двери, кресла, параметры `floor`) кроме чисел открывают свой инструмент в 3D. Тест сверяет, что у каждого указателя схемы с `x-frame` есть зарегистрированный инструмент: новое пространственное поле не останется без инструмента.
- **Незнакомое ключевое слово `x-…`** в схеме роняет тест `core/schema`. Новое слово должно быть понято формами осознанно.
- **Оверрайды (2b)** — те же описатели из `recipe_override.schema.json`, у каждого поля три состояния (1.3).

### 3.8. 3D-вид

- **Мир сцены — кадр OBJ** (Y вверх, ось хода X, перёд −X, +Z — левый борт). Числа разметки совпадают с координатами сцены (R6), пересчёт в кадр движка нужен только портам (`ObjFrame`). Анимации `.anim` (матрицы относительно покоя в пространстве OBJ) и поворот органа (угол вокруг оси через точку) применяются прямо в кадре OBJ: поворот на четверть оборота, которым движок переводит модель, не меняет ни угла, ни относительного движения. Поэтому `IrAnim.toModelSpace` не нужен.
- **Камеры:**
  - перспективная с вращением (по умолчанию);
  - ортографические «сверху», «сбоку» (с +Z), «спереди» (с −X) — как цифровая клавиатура Blender.
  
  Легенда осей в углу: «перёд −X».
- **Направляющие** (переключаемые слои):
  - оси и сетка 1/16;
  - головка рельса (плоскость y = −0.03) и рельсы на z = ±0.8125;
  - шкворни типа (x = −`bogies[i]`);
  - торцы `±length/2` и точки сцепок;
  - корпус коллизии `WagonType.collidableHull` в кадре OBJ (±1.7 поперёк, y −0.036…4.264, ±`length/2`): видно, что выступает за корпус.
- **Отображение:**
  - **Роли** (по умолчанию): плоские цвета по категориям ролей, палитра различима при дальтонизме, у каждой роли ещё и подпись в легенде и в «Объектах»;
  - **Текстуры**: как в игре — `NearestFilter`, отсечение по альфе, без отсечения задних граней;
  - **Свет**: текстуры и состояние групп.
  
  Выброшенное (`HIDE`, `skip`, без текстуры) — полупрозрачный призрак, его можно скрыть.
- **Выбор:** луч через `three-mesh-bvh`; клик — объект, Shift — добавить. Выделение синхронно с «Объектами». Двойной клик по объекту-двери предлагает «Дверь по объекту».
- **Текстуры:** PNG декодируются в воркере (`createImageBitmap` с `imageOrientation: 'flipY'`) и передаются как `ImageBitmap`. UV берутся как в OBJ: переворот V в `ObjLoader` нужен только Minecraft.
- **Предпросмотр** даёт виду только преобразования, видимость и подсветку объектов (3.13, `ViewApi`). Вид ничего не знает о дверях и органах.

### 3.10. Проверки

`checks/` собирает находки (`Problem`, 3.13) из четырёх источников:

1. **Схема** — Ajv по файлу. Указатель находки → ссылка на поле. `deprecated` — предупреждение, как в `validate_pack.py`. Незнакомый ключ — с подсказкой.
2. **Правила загрузчика вне схемы:**
   - геометрия типа (`WagonTypeParser.checkGeometry`: `length > 0`, шкворни строго спереди назад внутри ±`length/2`, |сцепка| < `length/2`);
   - `cab.seats` вместе с устаревшим `seat` — ошибка;
   - тип без модели и модель без типа;
   - ключи `animations` и `sounds.doors` — id дверей типа без учёта регистра;
   - ключи `sounds.controls` — рукоятки модели по точному виду;
   - `handbrake` называет органы, которые есть в модели;
   - звук `.ogg` есть в паке;
   - путь проходит шаблон ресурса Minecraft;
   - пределы, которых нет в схеме: групп света ≤ 64 и групп управления ≤ 64 на вагон, имя группы ≤ 32 (`obj-conventions.json#limits`);
   - `rwat.format`.
3. **`FloorCheck`** — порт, со структурированными находками (раздел 4.6) и ссылками на зону, дверь или кресло.
4. **Модели** — порт `ModelCheck`: нет файла, битый индекс грани, нечего рисовать, нет MTL или текстуры, грани без текстуры, ливрея ничего не заменяет, анимации нет. Плюс створки без двери (`doorHolding` = −1).

Проверки 1–3 идут в главном потоке с задержкой 150 мс: на паке-примере и самом сложном типе MVP это единицы миллисекунд, есть бюджетный тест на 10 мс. Проверка 4 идёт в воркере модели при открытии модели и по «Проверить все модели».

### 3.11. Тяжёлая работа: воркеры и лень

- **OBJ MVP** — 53 файла, около 100 МБ текста, самый большой (`mvp_ir_tem2.obj`) 6 МБ. Разбирается **только открытая модель**, в `model.worker.ts`:
  - чтение через `io` (из папки или из записи zip, без распаковки остального);
  - построчный разбор портом `ObjLoader`;
  - разбор ролей (`ModelParts`), шарниры (`PivotAxis`), острова ламп;
  - сборка `Float32Array` позиций, нормалей и UV по паре «объект × материал»;
  - передача как transferable.
- **Кэш** — три последние модели в памяти. Переключение на четвёртую выгружает самую старую.
- **«Проверить все модели»** идёт последовательно в том же воркере с прогрессом и отменой, память освобождается после каждой.
- **Zip** читается `zip.js` по записям (центральный каталог, потом одна запись), распаковка — в его воркерах.
- **Pyodide** живёт в отдельном воркере, грузится только при первом действии 2b или «Предложить пол». Источники-zip монтируются в WORKERFS: файлы `File` видны Python без копирования в память wasm. Отмена = остановка воркера.
- **Бюджеты** (проверяются тестами, M3 и M7):
  - пак-пример открывается за ≤ 1 с;
  - модель ТЭМ2 разбирается в воркере за ≤ 3 с на раннере CI;
  - главный поток не занят дольше 100 мс подряд (Playwright, `PerformanceObserver` `longtask`);
  - начальный JS ≤ 400 КБ gzip без Pyodide.

### 3.12. Импорт IR через Pyodide

- **Python — файлы репозитория как есть.** Vite кладёт `tools/ir2rwat.py` и `tools/floorgen.py` в бандл как текст (`?raw`), воркер пишет их в `/rwat/tools/` файловой системы Pyodide и добавляет путь в `sys.path`. Копий в `editor/` нет: правка конвертера сразу попадает в редактор, тесты 2b её видят.
- **Клей** `editor/py/rwat_bridge.py` только вызывает и сериализует (это проверяется на ревью):
  - `open_recipe(path)` — `Converter(path)`;
  - `type_ids()`;
  - `plan(id, without_overrides=False)` — `Converter.plan` в JSON; без оверрайдов — временно пустой оверрайд этого типа;
  - `convert(out_zip)` — `convert()` и `write(..., as_zip=True)`;
  - `model_files(id)` — записи zip-источника для OBJ, его MTL, текстур, ливрей и `.anim` типа, найденные `Source.find` и `parse_mtl` конвертера;
  - `suggest_floor(obj, options, doors)` — `floorgen.FloorConfig` и `generate`;
  - `model_doors(obj, animated)` — `parse_obj` и `model_doors`.
- **Файлы в Pyodide:**
  - рецепт и оверрайды — в `/work/packs/` (текущее состояние из модели пака, не с диска);
  - zip-источники — WORKERFS в `/work/src/`, плюс символические ссылки там, где их ждёт рецепт (`../MVP-IR-….zip`). Сам рецепт не переписывается.
- **Вывод `print`** конвертера идёт во вкладку «Лог», предупреждения и ошибки `Converter.warnings`/`errors` — в «Проверки» (источник `converter`).
- **Версия Pyodide** закреплена в `package.json`. Её файлы при сборке копируются в `dist/pyodide/` и раздаются с того же сайта: офлайн и без запросов на CDN. Нужен только стандартный Python (`zipfile`, `zlib`, `json`, `re`, `struct`), они в ядре Pyodide.

### 3.13. Контракты

`editor/src/core/contracts.ts` создаётся в M1 первым коммитом (A1.1) по этому эскизу и дальше меняется только дирижёром или назначенным им агентом. Что вышло — после эскиза.

```ts
// files
export interface FileEntry { path: string; size: number }
export interface PackSource {                  // fs-access | dir-input | zip | memory | node
  readonly kind: string; readonly writable: boolean; readonly name: string;
  list(): Promise<FileEntry[]>;
  read(path: string): Promise<Uint8Array>;
}
export type FileChange = { path: string; bytes: Uint8Array } | { path: string; delete: true };
export interface PackSink { write(changes: FileChange[]): Promise<void> }

// edits
export type JsonPointer = string;              // RFC 6901
export type Op =
  | { op: 'set'; file: string; at: JsonPointer; value: unknown }
  | { op: 'remove'; file: string; at: JsonPointer }
  | { op: 'insert'; file: string; at: JsonPointer; value: unknown }   // into an array
  | { op: 'putFile'; file: string; bytes: Uint8Array }
  | { op: 'deleteFile'; file: string }
  | { op: 'renameFile'; file: string; to: string };
export interface Command { label: string /* i18n key */; ops: Op[]; coalesceKey?: string }

// links and problems
export type Link =
  | { kind: 'file'; file: string }
  | { kind: 'field'; file: string; at: JsonPointer }
  | { kind: 'object'; model: string /* model id */; name: string }
  | { kind: 'zone' | 'door' | 'seat'; type: string /* type id */; index: number };
export interface Problem {
  severity: 'error' | 'warning' | 'info';
  source: 'schema' | 'loader' | 'floor' | 'model' | 'converter';
  code: string;                                // stable: 'floor.zone-too-narrow', 'schema.unknown-key', …
  params: Record<string, string | number>;
  text: string;                                // English, as the engine/tool says it (golden-checked where ported)
  at: Link[];
}

// model pipeline → view
export interface PartBuffers { object: string; material: string; positions: Float32Array;
  normals: Float32Array; uvs: Float32Array }
export interface ObjectInfo { name: string; role: string /* obj-conventions role id */;
  control?: unknown /* ports/objectRole Control */; lightGroup?: string; bbox: [number[], number[]] }
export interface LoadedModel { id: string; parts: PartBuffers[]; objects: ObjectInfo[];
  textures: Record<string, ImageBitmap | null>; problems: Problem[] }
export type Vec3 = [number, number, number];   // OBJ frame
export type OverlayShape =
  | { shape: 'box'; min: Vec3; max: Vec3; style: string; link?: Link }
  | { shape: 'rect'; min: Vec3; max: Vec3; style: string; link?: Link }      // flat, y = min[1]
  | { shape: 'arrow'; from: Vec3; to: Vec3; style: string; link?: Link }
  | { shape: 'arc'; centre: Vec3; axis: Vec3; from: Vec3; degrees: number; style: string; link?: Link }
  | { shape: 'circle'; centre: Vec3; radius: number; style: string; link?: Link };   // horizontal
export interface ViewApi {
  show(model: LoadedModel | null): void;
  setDisplay(mode: 'roles' | 'textured' | 'lit'): void;
  setTransform(object: string, matrix4: Float32Array | null): void;   // OBJ frame, null = rest
  setVisible(object: string, visible: boolean): void;
  setLit(object: string, lit: boolean): void;
  overlay(layer: string, shapes: OverlayShape[]): void;               // boxes, rects, arrows, arcs, circles
  onPick(listener: (hit: { object?: string; point?: number[] }) => void): () => void;
}
```

Подписи портов — в разделе 4.1. Агенты M2 пишут их ровно так, агенты M3–M4 вызывают.

**Создан (A1.1, M1).** Источник правды теперь — сам `editor/src/core/contracts.ts`, эскиз выше оставлен как история. Отличия от эскиза:
- *решение агента:* `PackSource.kind` — объединение `PackSourceKind` (`'fs-access' | 'dir-input' | 'zip' | 'memory' | 'node'`) вместо `string`; `ObjectInfo.bbox` — `[Vec3, Vec3]`; точка выбора — `PickHit { object?; point?: Vec3 }`; у `Command` необязательные `labelParams` для подписи в журнале («Изменить поле {field}»); у `ViewApi.setTransform` записан порядок матрицы (по столбцам, как `Matrix4.elements` three.js); `insert` в конец массива — указатель с `-` (RFC 6902);
- *решение дирижёра* (после влития структурированных находок `FloorCheck`, `kinematics/FloorFinding.java`): значения `Problem.params` — `ProblemParam = string | number | number[]` (список целых — `zones` у `ZONES_UNREACHABLE`; `Infinity` и `NaN` бывают у `SEAT_NOT_SITTABLE`, в golden — строками); добавлен тип `FloorFinding { code, subject: 'floor' | 'zone' | 'door' | 'seat' | 'cab', index (−1 — нет предмета), params, text }` — выход порта `floorCheck`, из него `checks/` делает `Problem`.

### 4.3. Ловушки порта

Каждую закрывает отдельный случай golden.

- **`float` против `double`.** `PivotAxis`, `ObjectRole`, `LampIslands`, `ObjLoader` считают во `float`. Порт округляет `Math.fround` в тех же местах, golden задаёт допуск.
- **`Float.parseFloat` ≠ `parseFloat`.** JS читает префикс (`"1.5abc"` → 1.5), Java отказывает. Java принимает `1f`, `0x1p3`, пробелы. Отсюда свой `parseJavaFloat`.
- **`%.2f` Java ≠ `toFixed`.** Java округляет половину вверх от кратчайшей десятичной записи (`1.005` → `1.01`), `toFixed` — от двоичного значения (`1.00`). Отсюда `formatFixed`: кратчайшая запись JS (совпадает с `Double.toString` JDK 19+) и округление половины вверх.
- **Регулярные выражения** берутся из `obj-conventions.json`: они написаны одинаковыми для Java, JS и Python, `validate_pack --self-check` сверяет их с Java. Тест порта ещё и компилирует каждое в JS (флаг `u`) и прогоняет примеры `examples` схемы.
- **Порядок.** Поиск по видам органов (`control_kinds` по порядку), «первый маркер `ROT` органа», «первая дверь, чья коробка держит створку», порядок вершин маркера — всё важно. Golden даёт имена и вершины в порядке файла.

### 4.4. Правило синхронизации

1. **Эталон — Java** (код и тесты — источник правды), Python и TS — порты. Исключения — `json_dump` и `validate`: у них эталон — Python (`ir2rwat.dump`, `validate_pack.py`), Java их не знает.
2. **Логика с портом меняется во всех портах в одном пулл-реквесте.** Нужный случай добавляется в `fixtures/golden/`, ожидаемое записывает эталон (4.5, п. 8); тест каждого порта читает всю папку. CI гоняет Java (`./gradlew test`), Python (`unittest`) и TS (`vitest`) — красный любой порт = красный CI.
3. **Ссылка на порты в коде.** В javadoc Java-класса — строка «Ported: `editor/src/ports/<файл>.ts`, `tools/<файл>.py`; golden: `fixtures/golden/<папка>/`». В TS — ссылка на Java-класс и метод. Тот, кто правит логику, видит, что править ещё.
4. **Кто проверяет папку,** написано в ней самой: `fixtures/golden/<папка>/ports.json` (`{"reference": "java", "ports": ["ts", "python"]}`). Общего манифеста нет, чтобы агенты разных логик не правили один файл. Мета-тест в каждом наборе сверяет, что каждая папка, где указан его язык, действительно прочитана.

### 4.5. Требования редактора к `fixtures/golden/`

Формат сделан (агент A0.4). Подробности, сравнение и порядок обновления — `fixtures/golden/README.md`, схема — `fixtures/golden/schema.json`.

1. **Одна папка на логику**, имена как в таблице 4.1. Случаи — JSON-файлы, UTF-8, без комментариев; файлов в папке сколько угодно. Ни один тест не перечисляет файлы руками: раннер читает все `*.json` папки, кроме `ports.json` (4.4, п. 4).
2. **Случай:** `{"id", "note", "input" | "input_file", "expected"}`. `id` — `^[a-z0-9]+(-[a-z0-9]+)*$`, стабилен и уникален в папке: по нему находят упавший случай во всех трёх отчётах (в Java это имя динамического теста, в Python — `subTest`).
3. **Файл:** `{"description", "frame", "tolerance", "cases"}`. `description` — какая логика (класс и метод эталона), что во входе и в ожидаемом.
4. **Входы в том виде, в каком их читает движок:**
   - текст OBJ, MTL и `.anim` — строкой;
   - имена объектов — строками;
   - типы — JSON формата пака в кадре OBJ, как в файле.

   Разметка всегда в кадре OBJ. Ожидаемое — в кадре, который отдаёт эталонная функция, и это сказано в файле: `"frame": "obj" | "model" | "none"` (`none` — мест в ожидаемом нет). Вопрос к результату (точка для `fits`, `doorHolding`, `clampFeet`) задаётся в кадре ожидаемого.
5. **Числа.** У файла `"tolerance"` — абсолютный допуск порта: `1e-9` для логики в `double`, `1e-6` для `float`, `0` для текста и правил чисел Java. Эталон сверяет точно. Значения `float` — кратчайшей записью `float` (`Math.fround` от неё даёт то же `float`); в `java_numbers/parse_float.json` — точное значение `float`, допуск 0. `NaN` и бесконечности записываются строками `"NaN"`, `"Infinity"`, `"-Infinity"`, `null` — только «нет значения».
6. **Структура, а не только текст.** Где движок пишет автору строку, ожидаемое — находки `{code, subject, index, params, text}` (`schema.json#/$defs/finding`). `FloorCheck` отдаёт их сам (`FloorFinding`, 4.6, п. 2): `code` — имя кода, `subject` — `floor`/`zone`/`door`/`seat`/`cab`, `index` — номер предмета или `-1`, `params` — из чего сделан текст, в порядке строки. У сообщений разбора типа (`wagon_type`) движок пока отдаёт только текст: `code`, `subject`, `index` — `null`, `params` — `{}`. Порты сравнивают `code`, `subject`, `index` и `text` точно. Редактор переводит находку по `code`, а `text` держит порт честным.
7. **Ввод из файлов репозитория.** `"input_file"` — путь от корня репозитория, только пак-пример `run/rwat_packs/RwatExamplePack/…` (CC0; схема и раннеры не пустят другой): строка — весь вход это файл, объект — файлы кладутся во `input` под своими ключами; `.json` читается как JSON, прочее — как текст. Файлов и чисел из моделей MVP в golden нет (лицензия, R12). Разметку из оверрайдов MVP (наша работа, без ассетов) брать можно.
8. **Размер:** файл ≤ 200 КБ, папка `fixtures/golden/` целиком ≤ 3 МБ, в папке логики ≥ 10 случаев (проверяет `test_golden_folders.py`). Это тест, а не склад моделей.
9. **Ожидаемое записывает эталон логики:** Java для всего, что есть в Java; Python — только для `json_dump` (`ir2rwat.dump`) и `validate` (`validate_pack.py`), у которых Java нет. Режим перезаписи — явный флаг: `./gradlew test --tests 'com.muzhik17.trainsmod.golden.*' -Pgolden.update` (свойство Gradle — входные данные задачи `test`, так что прогоны с флагом и без не отвечают друг за друга из кэша; прежнего `-Dgolden.update=true` больше нет) и `python -I tools/tests/test_golden_<папка>.py --update`. Флаг Java меняет в файле только `expected`, вход и прочий текст остаются как записаны (`fixtures/golden/README.md`, «Как обновить»). Без флага тест только сравнивает. TS ожидаемое не пишет никогда.
10. **Раннеры — по файлу на логику:** `src/test/java/…/golden/<Logic>Golden.java` (константа `FOLDER`, `@TestFactory`), `tools/tests/test_golden_<папка>.py`, `editor/src/ports/<logic>.test.ts`; *решение дирижёра:* раннер TS лежит рядом с модулем, который проверяет (не обязательно в `ports/`), и объявляет `const FOLDER = '<папка>'` — общий мета-тест находит раннеры по этой строке. Общая часть — `Golden.java`, `tools/tests/golden.py` и `editor/src/testing/golden.node.ts` (один модуль на все раннеры TS: чтение папки с `input_file`, проверка по `schema.json`, сравнение `mismatch`). Мета-тесты: `GoldenFoldersTest` (у каждой папки, где назван Java, есть свой раннер) и `test_golden_folders.py` (то же для Python, плюс каждый файл по схеме, `id`, размеры).
11. **Схема формата** golden — `fixtures/golden/schema.json` (draft 2020-12): корень — файл случаев, `$defs/ports` — `ports.json`, `$defs/finding` — находка. Python проверяет по ней каждый файл валидатором `validate_pack.py`; тест Vitest — Ajv, прежде чем читать.

**Отступления от первоначального замысла** (решения агента A0.4):

- **`frame: "none"`** — у логики без мест (имена, числа, тексты) нет кадра; без третьего значения пришлось бы писать неправду.
- **`floor_check`: ожидаемое — список находок**, как сказано в п. 6. Выходы (`walkablePieces`, которые портирует `floorgen.door_seeds`) — отдельные случаи того же типа с ключом входа `exits_of` в файле `exits.json`: вопрос задаёт вход, а не имя файла.
- **Две папки вне таблицы 4.1.** `door_leaves` — правило `DoorLeaves` из старого golden; порт придёт с `modelParts.ts` (M3), владелец `model_parts` (A0.1) может забрать случаи к себе. `anim_model` — кадры `.anim` в кадре модели (`IrAnim.toModelSpace`) из старого `anim.json`: по 4.2 не портируется, портов у папки нет, она хранит прежнее покрытие и может быть удалена, если хватает `IrAnimTest`. В `anim/` остались дорожки как в файле.
- **`pivot_axis` от текста OBJ** — файл `obj_text.json`: углы — все грани всех частей объекта по порядку, как их хранит `ObjLoader` (так их собирает `IrStockModel.ControlBuilder`). Пока нет `ModelParts` (4.6, п. 1), раннер сам берёт части с именем маркера; выбор маркера органа («первый `ROT`») — дело golden `model_parts`.
- **`json_dump`: вход — текст JSON** (`"json"`) или файл пака-примера (`"value"`), а не разобранное значение: `JSON.parse` склеивает `100.0` и `100`, а `dump` их различает.
- **`validate`: ожидаемое — `{pointer, severity, text}`** (указатель RFC 6901, `""` — весь файл). Ajv формулирует находки иначе, поэтому порт сверяет места и важность, текст — справочно; подсказку к незнакомому ключу проверяет `suggestion.json`.
- **Поломки из `ExamplePackLoadTest`** — копии типов пака-примера с одной правкой прямо во входе, а не `input_file` с заплаткой: правка пака-примера не меняет смысл случая, а портам не нужен механизм заплаток.
- **Отражение вместо чистых точек входа:** `StockModel.Control.transform` (класс держит `ResourceLocation`, которого нет в тестовом classpath) и `FloorCheck.walkablePieces` (пакетный доступ). Код движка тот же; чистый дом для них уберёт отражение.
- **Чего нет:** выбора кадра `.anim` и интерполяции (`frameAt`, таблица 4.1) — они внутри `WagonRenderer` с Minecraft. Нужна чистая точка входа (например, `IrAnim.frameAt(frames, progress)`), тогда случаи добавятся в `anim/`.
- **CI:** новых шагов не понадобилось — задача `mod` гоняет `./gradlew build`, `pack-format` — `unittest discover tools/tests`, оба подхватывают раннеры сами.

### 4.6. Что меняется в Java и Python до портов (M0)

1. **`ModelParts` — чистый разбор модели (выполнено в M0, A0.1).** Сейчас он внутри `IrStockModel.load` с `ResourceLocation` и Minecraft, Java-тест его не видит, и golden `model_parts` проверял бы только TS. Выносится в чистый класс (`convention/ModelParts`): на входе части OBJ (имя, материал, «есть текстура», вершины), на выходе роли, органы, створки, колёса, шарниры, лампы, фары. `IrStockModel` строит меши по его ответу. Туда же — правило «фара светит». Так требует `CLAUDE.md`: что решается без Minecraft, решается в ядре.
2. **`FloorCheck` отдаёт структурированные находки** — сделано: `FloorCheck.findings` даёт `FloorFinding` (`code`, предмет и его номер, параметры) и текст из них же (`FloorFinding.text`). Тексты для лога и `/rwat packs` не изменились (`FloorCheckTextsTest`). Golden `floor_check` пишет находки целиком (4.5, п. 6).
3. **Знак оси `PivotAxis` при ничьей** — решено, как в IR (UMC `ModelGroup`): шарнир — центр коробки точек в `double`; конец A и конец B — первая по порядку файла из равноудалённых точек; ближний конец — B, только если `|B|² < |A|²`; точка на равном расстоянии от обоих концов не входит ни в одну половину. Правило в javadoc `PivotAxis`, случаи ничьих — в golden `pivot_axis` (`corners.json`).
4. **Имя объекта с пробелом** — сделано: имя — **весь остаток строки** `o`/`g` без пробелов по краям, пробелы внутри сохраняются, как читают импорт Blender и Immersive Railroading (`ObjectRole.objectName`, `ObjLoader`, `floorgen.object_name_of`, `ir2rwat.parse_obj`; схема `obj-conventions.json#naming`). Первый токен прежнего загрузчика превращал `o Door Leaf` в `Door`. Случаи — golden `obj/object_names.json`.

  - `core/schema`: пак-пример — 0 находок; случаи golden `validate` совпадают с `validate_pack.py`; тест незнакомых `x-…`; тест «у каждого `x-frame` есть инструмент» (с M4);

```yaml
        with: { node-version: '22', cache: 'npm', cache-dependency-path: editor/package-lock.json }
      - run: npm ci
      - run: npm run lint          # tsc --noEmit + eslint
      - run: npm test              # vitest run: ports on fixtures/golden, core, replay, Pyodide in Node
      - run: npm run build         # vite build: the site with schema/ and pyodide/

      - run: npm run e2e
      - if: failure()

```

- Golden в Java проверяет задача `mod` (`./gradlew build`), в Python — `pack-format` (`unittest discover tools/tests`): раннеры golden подхватываются ими сами, отдельных шагов нет (4.5). Задача `editor` от них не зависит и идёт параллельно.
- `build.gradle` объявляет `fixtures/golden/` входом тестов, как `schema/` (иначе кэш ответит старым результатом). Это зона агента golden.
- **Как сделано (A1.1).** Задача добавлена в конец `ci.yml` по эскизу. Ещё два шага:
  - собранный `editor/dist/` каждой ветки сохраняется артефактом `editor-site` на 14 дней (*решение дирижёра*: сборки рабочих веток — артефакт CI, сайт — только из `main`);
  - отчёт упавшего e2e включает и `editor/test-results/` (трассы и снимки).

### 5.4. Выкладка на GitHub Pages

**Workflow** `.github/workflows/pages.yml` — отдельный файл. Почему: правами `pages: write` и `id-token: write` не должна обладать проверка каждого пуша.

- **Запуск:** пуш в `main` с изменениями в `editor/**`, `schema/**`, `tools/ir2rwat.py`, `tools/floorgen.py` (и самого `pages.yml`), плюс `workflow_dispatch`. **Только из `main`** (*решение дирижёра*, вопрос 9.5 закрыт). Ручной запуск с другой ветки ничего не делает: у задачи `build` условие `github.ref == 'refs/heads/main'`. Сборки рабочих веток — артефакт CI `editor-site` (5.3).
- **Задача `build`:**
  - `npm ci` и `npm run build`;
  - `dist/schema/` — копия `schema/` байт в байт (адреса `$id` схем начинаются с `https://kalkulator777.github.io/RWAT/schema/`). Шаг сверяет копию `cmp`;
  - `actions/configure-pages@v5`, `actions/upload-pages-artifact@v3` (`path: editor/dist`).
- **Задача `deploy`:** `actions/deploy-pages@v4`, окружение `github-pages`.
- `concurrency: pages`, без отмены идущей выкладки.
- *Решение агента:* `base: './'` вместо `'/RWAT/'`. Все адреса сборки относительные, и один и тот же `dist/` работает на Pages под `/RWAT/`, в `vite preview` от корня (e2e) и из любой папки. Сборке не нужна переменная окружения, и e2e проверяет те же байты, что уходят на сайт.
- *Решение агента:* `schema/` копирует сама сборка (плагин в `vite.config.ts`), а не шаг workflow. Так схемы попадают в предкэш service worker (он строится по `dist/` в конце сборки), есть в артефакте CI, а e2e проверяет их по `$id`.

**Что включить пользователю** (репозиторий публичный, Pages бесплатны; сейчас `has_pages: false`):

1. GitHub → репозиторий `kalkulator777/RWAT` → **Settings → Pages**.
2. В блоке **Build and deployment** поле **Source** → **GitHub Actions**. Ветку и папку выбирать не нужно.
3. **Settings → Environments → `github-pages`** (окружение создаётся само при включении Pages с источником Actions или при первой выкладке) → **Deployment branches and tags**: оставить `main`. Других веток не добавлять: сайт выкладывается только из `main`.
4. **Settings → Actions → General:** «Allow all actions and reusable workflows» (так по умолчанию) — нужны `actions/*`. «Workflow permissions» не трогать: workflow сам просит нужные права.
5. Сделать шаги 1–2 **до** слияния редактора в `main`. Иначе первый прогон `pages.yml` после слияния упадёт на `configure-pages` (Pages выключены). Если так вышло, включить Pages и перезапустить прогон. Первый раз workflow запускается сам: пуш в `main` меняет `editor/**`. Кнопка **Actions → Pages → Run workflow** (ветка `main`) появляется, когда `pages.yml` уже лежит в `main`.
6. Адрес появится в **Settings → Pages** и в итоге прогона: `https://kalkulator777.github.io/RWAT/`. HTTPS для `github.io` включён всегда.
7. До слияния редактор можно посмотреть из артефакта: **Actions → CI** → прогон ветки → **Artifacts → `editor-site`**, распаковать в `editor/dist/` и запустить `npm run preview` в `editor/` (`http://localhost:4173/`), или отдать папку любым статическим сервером. Service worker работает только на `localhost` и по HTTPS.

## 6. Интерфейс

### 6.1. Раскладка экрана

- **Верхняя полоса:**
  - имя пака и источник (папка, zip, только чтение);
  - «Открыть», «Новый», «Импорт IR», «Сохранить» (со счётчиком изменений);
  - отмена и повтор;
  - режим 2a/2b;
  - язык (RU/EN), справка.
- **Слева — дерево пака:**
  - «Пак» (`pack.mcmeta`);
  - «Вагоны» — пары тип + модель по id, у каждой значок состояния: ошибки, предупреждения, нет модели, нет типа;
  - «Стили рельсов», «Имена» (lang), «Ассеты» (папки и файлы, неиспользуемые серым).
  
  В 2b вместо «Пака» — «Рецепт»: источники, типы IR (отмечены те, у кого есть оверрайд), исключённые, рельсы.
- **В центре — вид:**
  - сверху панель: камера (перспектива, сверху, сбоку, спереди), отображение (роли, текстуры, свет), слои (пол, двери, кресла, корпус, рельсы, оси, призраки), инструмент (выбор, зона, дверь, кресло, линейка);
  - внизу строка: координаты под курсором в кадре OBJ, шаг привязки, единицы.
- **Справа — инспектор:** форма того, что выделено. Тип, модель, стиль, пак, lang — формы по схеме. Объект модели — роль, флаги, описание правила из `obj-conventions.json`, «Дверь по объекту». Зона, дверь, кресло — числа и флаги. В 2b — оверрайд с тремя состояниями поля.
- **Внизу — вкладки:**
  - «Проверки» — список находок, фильтр по важности и источнику, клик ведёт к месту;
  - «Объекты» — таблица объектов модели: имя, роль, ключ, группа, флаги, материал; поиск и фильтр;
  - «Предпросмотр» — двери, органы, свет, ливрея, сцепки;
  - «Журнал» — правки, клик откатывает до выбранной;
  - «Лог» — вывод конвертера и загрузки.
- **Ширина панелей** меняется перетаскиванием, раскладка запоминается в браузере.

### 6.2. Языки

- **Интерфейс — ru и en.** Язык по умолчанию — по `navigator.language` (`ru*` → русский), переключатель запоминается.
- **Тексты формата — из схемы**, отдельного перевода нет:
  - поля — `description` / `x-description-ru`;
  - единицы, кадры, статусы — `pack-layout.json`;
  - роли, флаги, модификаторы — `obj-conventions.json` (`effect` / `x-description-ru`).
  
  Нет русского текста у свойства — тест `core/schema` красный (так же строг `validate_pack --self-check`).
- **Находки `FloorCheck`, `ModelCheck` и загрузчика** переводятся по `code` (4.5, п. 5), английский текст — как у движка.
- **Названия групп света мода** (IL, FHL, …) берутся из `src/main/resources/assets/railswheelsandtrains/lang/{en_us,ru_ru}.json` при сборке: так их покажет игра.
- **Числа** в интерфейсе — с точкой, как в JSON и Blender, независимо от языка. Почему: пользователь переносит их между Blender, JSON и редактором.

### 6.3. Доступность

- **Всё делается с клавиатуры.** У каждого пространственного действия есть числовая форма. Горячие клавиши — по образцу Blender (1/3/7 — виды, G — сдвиг, Delete, Ctrl+Z/Ctrl+Shift+Z). Карта клавиш — в справке.
- **Цвет — не единственный признак.** Роли различаются ещё подписью в легенде и в «Объектах». Палитра различима при дальтонизме (проверяется тестом на контраст соседних цветов). Ошибки — значком и словом, не только красным.
- **ARIA:** дерево — `role="tree"`, находки — список ссылок, вид — `role="application"` с текстовым описанием выделенного для экранного диктора.
- Контраст текста WCAG AA, видимый фокус, масштаб 200 % без потери функций, `lang` у документа по языку интерфейса.
- `prefers-reduced-motion` — без самопроигрывания анимаций дверей и перелётов камеры.

## 8. Риски

| Риск | Чем грозит | Что делаем |
|---|---|---|
| Порты расходятся с движком | редактор говорит «всё хорошо», а игра пропускает тип | список портов ограничен (4.1), golden с записью от эталона, мета-тест `ports.json` каждой папки, ссылки «Ported:» в javadoc, все порты — в одном пулл-реквесте |
| M0 трогает рендер (`IrStockModel`) | регресс в игре | вынос без изменения поведения, снимки автосцен до и после (R18) |

| File System Access только в Chromium | Firefox и Safari не пишут в папку | zip и чтение папки через `webkitdirectory`, честная подпись в интерфейсе |
| Лицензии | чужие ассеты на публичном сайте или в golden | на сайте только пак-пример (CC0), MVP никогда; IR-импорт идёт в браузере пользователя, ничего не отправляется; экспорт рецепта без ассетов (тест); golden без файлов MVP |

## 9. Открытые вопросы к пользователю

1. **Когда замораживать формат v1 (R5: «с первым выпуском редактора»)?** Варианты: с выпуском 2a (M5) или с выпуском v1 целиком (M7).
   **Рекомендую M7.** 2b может потребовать поправок в формате рецепта и оверрайдов, а до M7 сайт и так идёт с плашкой «предварительная версия». Поля фазы 3 (корпус, многоугольники пола) потом добавляются совместимо: необязательными ключами.
2. **Прослушивание ванильных звуков `minecraft:…`.** Редактор может прочитать папку `assets` установленной игры пользователя (Chromium, `showDirectoryPicker`) и играть звуки оттуда. В сам редактор ничего из Minecraft не кладётся.
   **Рекомендую сделать необязательным пунктом A5.1.** Пак-пример целиком на ванильных звуках, без этого его не услышать.
3. **Режим «прогулка» (порт `RiderWalk.step`) — в v1 или в v1.1?**
   **Рекомендую v1.1.** Статичный показ «где стоять» покрывает все проверки, а ещё один порт — ещё одна поверхность расхождений.
4. **Один пак за раз или несколько** (общие текстуры через `ns:path` из другого пака)?
   **Рекомендую один в v1.** Внешние ссылки помечаются «не проверена», второй пак можно открыть позже как библиотеку только для чтения.
5. **Откуда выкладывать сайт:** только из `main` или ещё из рабочей ветки `ccr-4b67d258-0673ah`? Сейчас партия A и фаза 1 в `main` не влиты.
   **Рекомендую:** до первого пулл-реквеста в `main` разрешить рабочую ветку в правилах окружения `github-pages` и выкладывать с неё ручным запуском (5.4, шаги 3 и 5); после слияния — только `main`, автоматически.
   **Решено дирижёром (A1.1):** только из `main`; сборки рабочих веток — артефакт CI `editor-site` (5.3, 5.4).
6. **Начинать фазу 2 с правок Java (M0) — согласен?** Это вынос `ModelParts` из рендера, структурные находки `FloorCheck`, ничья `PivotAxis`.
   **Рекомендую да.** Без этого порт разбора модели нечем сверить с движком, а находки пола не связать с зонами. M0 идёт параллельно с каркасом и фазу не задерживает.
7. **Нужен ли адрес на своём домене** вместо `kalkulator777.github.io/RWAT`?
   **Рекомендую пока нет.** Адреса `$id` схем уже указывают на `github.io`; свой домен потом потребует перенаправления или смены `$id`.

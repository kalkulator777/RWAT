**Платформа:** Minecraft 1.21.1, NeoForge, Java 21, ModDevGradle
**Тип:** самостоятельный мод (не аддон к Create)

Этот документ — источник правды. Решения меняются только через правку SPEC, а не «по памяти».

## 1. Принципы архитектуры

1. **Снизу вверх.** Системы строятся в порядке зависимостей: сеть/сущности → путь → кинематика → рендер → геймплей. Не наоборот.
2. **Сервер авторитетен.** Сервер — единственный источник правды о состоянии состава. Клиент только разворачивает и интерполирует.
3. **Минимальное синхронизируемое состояние.** По сети ходит позиция головы вдоль пути `s` и скорость `v`. Всё остальное (позиции тележек, вагонов, поворот корпусов) клиент выводит детерминированно.
4. **Версионная изоляция.**
   - *Решение 0.1 (старое):* рендер и version-specific вызовы прячутся за собственные интерфейсы с первого дня — порт на NeoForge 26.x неизбежен в горизонте года, цена порта у entity/рендер-тяжёлого мода максимальна.
   - *Решение 0.2 (новое):* та же цель, другой механизм — **«чистое ядро + тонкие адаптеры»** вместо обёрток-интерфейсов над MC-типами. Сплайн, arc-length, кинематика тележек — чистая математика без импортов `net.minecraft.*` (JOML/свои векторы), тестируется юнитами без запуска игры. MC-специфика (entity, рендер, пакеты) — тонкие адаптеры по краям. Буквальные обёртки над `RenderType`/`VertexConsumer` признаны оверинжинирингом: порт всё равно переписывает обёртки, а чистое ядро даёт 90% выгоды дешевле. *Оценка 2026-10-09 (§7):* что именно ломают 1.21.2 → 26.3 и Fabric и правила для нового кода.
5. **Пак-готовность без паков.** Конвейер рендера строится так, как будто модель-паки уже существуют: геометрия — данные во внутреннем представлении, а не код. Парсер формата добавляется позже, рендер не переписывается.
6. **Модель данных шире фичи.** Структуры закладываются под полную версию, даже если v0 использует частный случай (состав = список вагонов длины 1; узел = список соединений длины ≤ 2).

## 2. Скоуп прототипа (v0)

**Definition of done v0:** один вагон на двух тележках едет по сплайновому пути A→B с уклонами, синхронизируется на клиенты без дрожи, переживает сейв/лоад, управляется игроком с места машиниста, рендерится захардкоженной моделью через пак-готовый конвейер. Коллизии нет — вагон «призрак», это осознанно.

### 2.1 Слой 0 — Фундамент

**Состав и вагоны:**
- *Решение 0.1 (старое):* состав — одна сущность (Entity) server-side, хранящая всё состояние.
- *Решение 0.2 (новое):* **состав (Consist) — логический серверный объект, НЕ Entity; вагон (Wagon) — Entity.** Состав живёт в SavedData рядом с графом рельс, тикается своим менеджером и владеет `s`, `v`, направлением и упорядоченным списком вагонов. Каждый вагон — Entity, чья позиция каждый тик выставляется из `s` состава; при загрузке чанков вагоны «пристёгиваются» к составу по UUID. Мотивация: (а) трекинг видимости — длинный состав как одна entity исчезает целиком, когда чанк головы вне view distance, entity-на-вагон решает это ванилью; (б) посадка машиниста — садятся в вагон, rideable-сущность всё равно вагон; (в) персистентность — entity сохраняется в чанке своей позиции, поезд на несколько чанков при частичной выгрузке ловит дюпы/потери, логический состав в SavedData надёжнее и делает заглушку чанклоадинга честной (состав существует всегда, просто не тикает). Create пришёл к той же схеме (логический `Train` + entity на секцию).
- Состояние состава: ссылка на путь, позиция головы `s` (дистанция вдоль пути, метры/блоки), скорость `v` (блок/тик), направление.
- Состав = упорядоченный список вагонов. В v0 список всегда длины 1, но структура — с первого дня.
- Тик: `s += v` (продольная физика — см. Roadmap; в v0 `v` задаётся управлением напрямую с простым сглаживанием).
- **Интерфейс пути (0.2, новое):** Слой 0 строится против минимального интерфейса пути (`samplePosition(s)`, `length()`) с захардкоженной дебаг-реализацией «прямая A→B» — иначе `s += v` нечего тестировать до Слоя 1. Слой 1 затем подставляет настоящий граф, интерфейс не меняется.

**Сетевая синхронизация:**
- Собственные пакеты: снапшот состояния состава (`s`, `v`, id пути) с фиксированной частотой.
- **Уточнения 0.2 (новое):**
  - В снапшот входит серверный `gameTime` — без метки времени снапшоты не интерполируются. Частота v0: каждый тик (пакет маленький, прореживание — потом). При потере снапшота клиент экстраполирует: продолжает `s += v` от последнего полученного.
  - **Ванильная синхронизация позиции entity отключается от рендера.** Сервер обновляет позицию entity-вагона (для трекинга чанков, спавн-пакетов, посадки), но клиент полностью игнорирует ванильную 3D-интерполяцию (`lerpTo` и тик клиентской entity переопределяются, ванильные update-пакеты сведены к минимуму) — позиция вагона на клиенте выводится только из нашего интерполированного `s`. Иначе работают две системы интерполяции одновременно = дрожь из двух источников.
  - **Поправка (2026-06-12, баг «наблюдатель не видит вернувшийся поезд»):** «сведены к минимуму» ≠ `updateInterval(Integer.MAX_VALUE)`. Спавн-пакет entity (`ClientboundAddEntityPacket`) берёт позицию из базы `ServerEntity.positionCodec`, а она обновляется только раз в `updateInterval` тиков. С `MAX_VALUE` база замерзала на моменте старта трекинга: наблюдатель, повторно вошедший в радиус после большого круга поезда, получал вагон в устаревшей (часто непрогруженной у него) точке — там entity не тикает, наш `clientTick` не подхватывает позу, вагон невидим навсегда; хост-пассажир без вагона на клиенте тоже не позиционируется (ванилла не шлёт позиции пассажирам). Итог: `updateInterval = 10` (база спавна ≤0.5 с давности); пакеты движения клиент по-прежнему игнорирует (`lerpTo` no-op), дрожи это не добавляет.
  - **Поправка 2 (2026-06-12, баг «/tp к стоящему поезду — нет локомотива»):** клиентский стейт консиста (`ClientConsists.STATES`) обязан умирать вместе с трекингом. Когда наблюдатель теряет все вагоны состава, снапшоты к нему перестают идти, но стейт оставался жить с протухшим буфером и тикающими часами; при повторном трекинге первый `clientTick` вагона сэмплил этот буфер и телепортировал свежезаспавненную entity на позицию поезда многоминутной давности — обычно в непрогруженный у клиента чанк, где entity выпадает из тик-листа и не тикает больше никогда (свежие снапшоты её уже не чинят) → невидима навсегда; прицепленный пассажир уезжает вместе с ней (отсюда «хост появляется только при выходе из локомотива»). Гонка с первым свежим снапшотом делала баг интермиттентным и пер-вагонным. Фикс: `tickAll` дропает стейт целиком после 60 тиков тишины снапшотов (`STALE_DROP_TICKS`; запас против 20-тиковой экстраполяции — живой, но лагающий поток буфер не теряет); после ре-трекинга вагон стоит на точке спавна (свежей, ≤0.5 с) до первого снапшота. Заодно: снапшоты и rider-sync шлются трекерам **каждого** вагона состава (не только последнего в итерации — наблюдатель, трекающий только часть состава, не получал снапшотов вовсе); дубли клиент отбрасывает по `gameTime`, rider-apply идемпотентен. Диагностика, которой это поймано: `/rwat track` (дамп условий ванильного `updatePlayer`: dist/view/pending/paired + `entityMap`) и клиентский лог `[track-debug]` JOIN/LEAVE вагонов и игроков — оставлены в `debug/`.
- Клиент: snapshot-интерполяция с буфером задержки — рендер на ~2 тика «в прошлом», интерполяция между полученными снапшотами.
- **Критично:** интерполируется `s` вдоль пути, а не 3D-позиция. Интерполяция позиции срезает углы на кривых — источник дрожи и артефактов в RTM.
- **Часы воспроизведения (2026-06-11, по плей-тесту шага 4):** время для интерполяции — **не** клиентский `getGameTime()` (сервер жёстко поправляет его каждые 20 тиков, каждая поправка дёргала `s` назад-вперёд — «состав иногда дергается»), а собственные часы на состав: +1 за клиентский тик, мягкий подвод к `(новейший снапшот − задержка)` слью ≤0.05 тика/тик (5% диляции — незаметно), снап при расхождении >20 тиков. И **фаза рендера**: ваниль рисует entity (и пассажира-машиниста) в окне «прошлый тик → текущий», т.е. на 1 тик позади непрерывных часов; модель надо сэмплить в том же окне `prevClock→clock` по partialTick (`ClientConsists.renderPose`), а тик entity — на `clock` (`tickPose`). Рендер модели «в текущем времени» опережал сиденье ровно на `v·1 тик` — машинист визуально съезжал назад пропорционально скорости и возвращался при остановке. **Пауза (2026-06-11, плей-тест):** на паузе одиночки интегрированный сервер стоит (снапшоты и gameTime замирают), но `ClientTickEvent` продолжает стрелять — часы убегали вперёд (экстраполяция двигала состав), а на пороге снапа в 20 тиков состав дёргался назад, и так по кругу; часы не тикают при `Minecraft.isPaused()`.
- Разворачивание: из интерполированного `s` клиент вычисляет позиции обеих тележек по arc-length, из них — позицию и ориентацию корпуса. Детерминированно, одинаково на сервере и клиенте.

**Персистентность:**
- Рельсовая сеть: сохраняется как данные уровня (SavedData) — граф узлов и сегментов.
- Составы: сохраняются с миром (позиция `s`, скорость, состав вагонов, ссылка на путь). *Уточнение 0.2:* составы — в SavedData (см. решение 0.2 выше), вагоны-entity — штатно в чанках, связь по UUID.

**Чанклоадинг (заглушка v0):**
- Правило: состав тикает только если его чанки загружены; иначе замирает на месте. *Уточнение 0.2:* «его чанки» = **чанк головы** (позиция тележки на `s`); проверка габарита целиком — вместе с настоящим чанклоадингом в v1.
- Интерфейс «кто и когда тикает состав» выделен отдельно, чтобы заглушку можно было подменить без перестройки (см. Roadmap).

### 2.2 Слой 1 — Рельсовая система

**Модель данных:**
- Сегмент пути = параметрический сплайн в **3D** (Эрмит или кубический безье — выбрать при имплементации, интерфейс не зависит).
- Каждый сегмент имеет **arc-length таблицу**: соответствие «параметр t ↔ пройденная длина». Всё движение — по длине, не по сырому t.
- Узел = точка с **списком соединений** (в v0 максимум 2, структура допускает N — задел под стрелки).
- Сеть = граф узлов и сегментов, живёт в SavedData.

**Высоты:** подъёмы и спуски входят в v0. Сплайн изначально трёхмерный — переход с 2D на 3D потом ломает кинематику, а разница в сложности сейчас минимальна.

**UX постановки (переработано 2026-06-10, сборка зелёная, в игре ещё не проверено):** блок-маркер + предмет рельс (заменили инструмент-планировщик «клик по двум блокам»; `TrackPlannerItem`, `PendingMarkerPayload`, `ClientTrackPlanner`, `MarkerRenderer` удалены вместе с пакетом pending-маркера):
- **Блок-маркер** (`RailMarkerBlock`, `rail_marker`): ставится на землю там, где будет узел; при установке запоминает горизонтальное направление взгляда игрока, округлённое до 45° (`rotation` 0–7, 0 = юг, по часовой как yaw). Направление = **ось касательной** сплайна в этом узле (знак разрешается в сторону второго конца при постройке, 180° эквивалентно 0°). Визуал: столбик из досок + железная планка-стрелка сверху по оси (8 поворотов = 2 модели «прямо»/«диагональ» × y-поворот блокстейта 0/90/180/270; в модели-диагонали элемент повёрнут на −45° — **знак угла не проверен в игре**, если планка показывает не ту диагональ, поменять на +45).
- **Стрелочный маркер** (`RailSwitchMarkerBlock`, `rail_switch_marker`; добавлен 2026-06-11, сборка зелёная, в игре не проверено) — по образцу RTM: тот же маркер (наследник, те же 8 поворотов и реестр; визуал — золотая планка вместо железной), но клик рельсами по нему строит узел-развязку. Реестр маркеров общий, тип различается по типу блока. Два режима, выбираются автоматически по окружению:
  - **Y-стрелка:** стрелочный маркер = остряк (точка A), два ближайших обычных маркера = концы веток (B и C). Строятся два сегмента A→B и A→C; узел A общий (второй `createSegment` снапится в узел первого), общая касательная A → гладкое ответвление. Все три маркера потребляются.
  - **4 стрелочных маркера, без обычных** — если при клике в радиусе есть ещё ≥3 стрелочных: кликнутый паруется с маркером вдоль своей оси касательной (max |cos| между осью и хордой), оставшиеся два — друг с другом; дальше **вид развязки решает геометрия хорд пар** (как в RTM — оба вида строятся одними и теми же 4 маркерами):
    - **Хорды пересекаются между маркерами → X-перекрестная стрелка** (угол любой: «плюс» и косая «хромосома» — один код). Пересечение хорд (в горизонтали; валидации: разница высот путей ≤1, каждый луч ≥ мин. длины) становится **общим центральным узлом M**, каждый путь режется через него: 4 сегмента A–M, M–B, C–M, M–D — центр является настоящей развязкой (выбор направления через неё — механика перевода, v1). *(Первая реализация 2026-06-11 строила глухое пересечение из двух независимых сегментов без узла — по плей-тесту переделано в тот же день: нужна стрелка, а не diamond.)* **Две оси в одном узле:** узел хранит одну ось касательной — у центра креста их две; решение — опциональная пер-концевая касательная в сегменте (`RailSegment.dirA/dirB`, null = ось узла, как обычно): узел M несёт ось первого пути, сегменты второго пути несут свою ось переопределением (персистится в NBT и в синк-пакете).
    - **Хорды не пересекаются (параллельные пути) → scissors-съезд** (перекрёстный, 2026-06-11): A–B и C–D — проходные сегменты двух путей, плюс обе диагонали накрест-накрест: каждая соединяет противоположные концы (по проекции на ось пути 1) и выходит/вливается по касательным своих путей — плавные S-кривые. Диагонали пересекаются **глухо, без общего узла** — переход «диагональ→диагональ» не бывает валидным маршрутом, центральный ромб чисто визуальный. Все 4 узла примыкания — трёхрёберные стрелки с осями своих путей, продолжения путей снапятся гладко. Валидации: пути не ближе 1.5 блока, все сегменты ≥ мин. длины. *(Ранний вариант «навязывание оси маркером при снапе» не понадобился.)*
    - Все 4 маркера потребляются.
- **Глухое пересечение из 4 обычных маркеров (2026-06-11):** перекрёсток без стрелки строится обычными маркерами — клик рельсами по обычному маркеру пробует крест с **тремя ближайшими** другими обычными: парование как у стрелочных (кликнутый — с лучшим по |cos| оси, остальные — друг с другом); крест строится (два независимых сегмента, узла нет — переключать нечего) только если хорды пар пересекаются строго между маркерами **и** каждый маркер смотрит вдоль своей хорды (|cos| ≥ 0.7 — при 8 поворотах честная погрешность ≤22.5°, cos ≈ 0.92), иначе тихий откат к обычной постройке «к ближайшему». Ворота — геометрия, а не число маркеров: первый вариант требовал «ровно 3 в радиусе 512», и любой забытый маркер в мире блокировал крест (плей-тест 2026-06-11); фильтр направлений страхует обратное — случайный треггер чужими маркерами.
- **Постройка одним кликом = единый элемент (2026-06-11):** сегменты, построенные одним кликом (Y/N/X/scissors/глухой крест), получают общий `group` (`RailSegment.group`, 0 = одиночный; персистится в NBT и синке) — поломка любого блока полотна сносит **всю** конструкцию (`removeStructure`), как и `/rwat rail remove`. При удалении клетки полотна, остающиеся под выжившими сегментами, **сохраняются** — снос пути у стыка или у глухого пересечения больше не выгрызает дыры в полотне соседа (закрыт прежний известный долг).
- **Рельсы на свободных концах (2026-06-11, клиентский рендер):** узел лежит в центре клетки маркера, и рельсы обрывались посреди клетки. Свип рендера удлиняет модель рельс на 0.5 блока (до края клетки) экстраполяцией вдоль концевой касательной (`OverhangPath`) — но только на **открытых концах**: конец открыт, если никакой другой сегмент узла не уходит от узла в пределах 60° от наружного направления (cos > 0.5; честные продолжения почти касательны, cos ≈ 1). На стыках продолжение рисует сосед — нахлёст дал бы z-fighting; стык, потерявший соседа, становится открытым и получает довесок при следующей перестройке — концы всегда выглядят завершёнными. Узлы стрелок открыты со стороны, куда не уходит ни одна ветка: носок Y и свободные концы scissors тоже получают довесок (первый вариант «только узлы с одним сегментом» их пропускал — плей-тест 2026-06-11); сонаправленные открытые концы (обе ветки Y кончаются в носке по одной оси) рисует только сегмент с меньшим id — иначе два одинаковых довеска мерцали бы друг о друга.
  - **N-съезд (crossover, 2026-06-11):** 2 стрелочных + 2 обычных маркера — диагональ между двумя (обычно параллельными) путями. Стрелочные A и C — точки съезда, смотрят каждый вдоль своего пути; обычные B и D — продолжения путей (каждый сопоставляется со «своей» развязкой по max |cos| оси и хорды). Строятся 3 сегмента: проходные A–B, C–D и диагональ A–C — выходит из A по касательной пути 1, вливается в C по касательной пути 2 (плавная S-кривая); узлы съезда несут оси своих путей, проходные сегменты прямые, дальнейшие продолжения снапятся гладко. Перекрёстный съезд (scissors) пока не собирается: точкам примыкания нужны две оси (проходная + диагональная), а пер-концевое переопределение доступно только построителю X — потребует «маркер при снапе в чужой узел навязывает свою ось» (отложено).
  - **Автодетект вида развязки** по числу других стрелочных маркеров в радиусе при клике: 0 → Y, 1 → N, 3 → X или scissors (по геометрии хорд, см. выше), 2 → отказ с подсказкой (неоднозначно).
  - **Перевод стрелок (v1, реализовано 2026-06-11, сборка + тесты зелёные, в игре не проверено):**
    - **Состояние** — счётчик выбора на узле (`RailGraph.switchSelections`, node id → int; персистится в NBT `RailNetwork`, едет в синк-пакете). Семантики «какая ветка» в счётчике нет — он берётся по модулю числа кандидатов в момент прохода.
    - **Маршрутизация стала направленной:** `walkRoute`/`continuation` в узле ищет сегменты, уходящие в пределах 60° от направления движения (`CONTINUATION_DOT = 0.5`, общий с рендером). Один кандидат — едем (обычный стык, прямой проезд центра X-крестовины, пошёрстный въезд на стрелку — всегда пропускает на «ствол» независимо от состояния, противошёрстного взреза нет); несколько — противошёрстная стрелка, выбирает счётчик (`кандидаты, отсортированные по id, [счётчик mod размер]`); ноль — конец пути **или излом** (два сегмента под непроходимым углом — раньше маршрут шёл и через изломы, теперь поезд там останавливается; гладкие стыки не задеты — у них общая ось узла, cos ≈ 1). Следствие: X-перекрёсток проезжается прямо насквозь (перпендикулярная пара — не кандидаты), поворот через центр потребует slip-кривых (отложено) — стрелочный пост для X не регистрируется.
    - **Переключение редстоуном:** при постройке Y/N/scissors позиция каждого потреблённого стрелочного маркера регистрируется как **стрелочный пост** (`RailNetwork.switchStands`, pos → node id; персистится): Y — носок, N — оба узла съезда, scissors — все 4. Сервер каждый тик (`RailEvents` → `tickSwitches`) опрашивает сигнал в клетке поста **и в клетке под ним** (рычаг на полотне силит блок полотна); **передний фронт** двигает счётчик узла на +1 (цикл по веткам), звук поршня, ревизия графа++ → синк и перестройка маршрутов/рендера. Посты, чей узел исчез (развязку снесли), вычищаются на ходу.
    - **Анимация остряков (клиент) — ОТКЛЮЧЕНА флагом `RailRenderer.SWITCH_BLADES = false` (2026-06-12):** по решению на плей-тесте весь визуал перьев отложен «на потом» (без настоящей крестовины-frog он читается как скрещение рельсов в горловине). При флаге `false` сегменты рисуются целиком, как обычный путь, — никакого вырезания зон, отклонения и анимации; **механика стрелок не затронута** (состояние, перевод редстоуном, маршрутизация, перепривязка поезда работают). Вернуть визуал — `SWITCH_BLADES = true`. Описание самой механики перьев (на случай возврата): первые `BLADE_LENGTH = 3` блока каждой расходящейся ветки у узла стрелки (кластер сонаправленных концов, взаимный cos > 0.5 — у Y/N/scissors это и есть ветки; перпендикулярные ноги X кластера не образуют) вырезаются из статичной запечки и рисуются отдельным мешем: на выбранной ветке прогиб 0 (остряк прижат, маршрут едет по ней), на остальных кончик увезён на `BLADE_TIP_OFFSET = 0.35` блока **в сторону выбранной** с линейным спадом к пятке (сдвиг горизонтальный, через `BladePath` поверх сплайна; концевой довесок 0.5 на носке едет вместе с остряком). Смена состояния по синку линейно-сглаженно (smoothstep) перетекает за 500 мс — стрелка зримо «переводится»; перестройка меша остряков — только на время анимации и при смене ревизии (плюс один финальный кадр в покое), статика не трогается. Логин принимает текущее состояние без анимации. *(Первый вариант 2026-06-11 не отклонял остряк вовсе — плей-тест «анимация не работает»: направление сдвига бралось как перпендикулярная составляющая касательной соседней ветки относительно своей, а в носке обе ветки выходят по общей оси узла → касательные при t=0 совпадают → составляющая ≈ 0. Исправлено: сторону сдвига берём по расхождению веток у пятки — точки на `BLADE_LENGTH` вдоль каждой ветки от узла, перпендикуляр к своей оси, знак по их разности.)* **Шпалы в горловине (2026-06-11, плей-тест switch1/switch2.png «выглядит странно»):** две полные двухрельсовые модели, сходящиеся в носок, задваивали шпалы и крестили рельсы внахлёст. Теперь в зоне остряков прижатая (выбранная, `amount < 0.5`) ветка рисуется **полной** моделью (со шпалами), а отклонённые — `RailModel.railsTile()` (модель без объекта `RAIL_BASE`, только два рельса): горловина несёт один комплект шпал (от ствола + выбранной ветки), а расходящиеся ветки идут тонкими перьями поверх. Скрещение внутренних рельсов у точки расхождения остаётся (настоящей крестовины-frog пока нет — отдельная геометрия, отложено).
    - **Поезд видит изменения сети (та же ревизия графа):** маршрут состава — больше не замороженный список ног со спавна. При каждом изменении ревизии (постройка, снос, перевод стрелки) состав **перепривязывается** (`Consist.reanchor`): находится нога под головой (по старому материализованному пути), от её сегмента маршрут обходится заново по текущему графу (через стрелки по их состоянию), ориентация ноги сохраняется (иначе маршрут зеркалится), `s` пересчитывается на ту же мировую позицию. Достроили путь — состав поедет дальше; снесли кусок — маршрут просто укоротился (поезд встаёт у нового конца), а если снесли сегмент прямо под головой — голова прыгает на ближайшую выжившую ногу старого маршрута (на её торец); заморозка (`resolve → null`) остаётся только если не выжило ничего. Перевод стрелки под составом, голова которого уже проехала узел, маршрут головной ветки не меняет (обход идёт от сегмента головы; пошёрстный выезд проходит всегда). **Важно для теста:** чтобы перевод стрелки реально перенаправил состав, голова должна стоять **до** узла (на стволе) — отладочный состав ~18 блоков, на коротком подходе голова при спавне выталкивается за носок на ветку, и стрелка под ней уже не действует (это правильно — нельзя переводить стрелку под головой). `Consist` сам в юнит-тесте не проверить (тянет MC-рантайм, которого нет в classpath тестов), но граф-уровень перепривязки покрыт чистыми тестами `ConsistReanchorTest` (фейсинг-разворот после перевода + пошёрстный выезд из любой ветки) — оба зелёные.
- **Предмет рельс** (`RailItem`, `rail`): клик по маркеру → ищется ближайший **другой** маркер (реестр в `RailNetwork`, до 512 блоков) → сегмент строится между центрами клеток двух маркеров, касательные — из их направлений; оба блока-маркера исчезают (потребляются), их клетки занимает полотно. Клик по не-маркеру — подсказка; ПКМ в воздух — зарезервирован под будущий GUI кастомизации рельс (пока заглушка-сообщение; **реализовано 0.9**: выбор стиля рельса с 3D-превью, §6.10–6.11). Реестр маркеров (`pos → rotation`) живёт в том же SavedData `RailNetwork`, персистится, чистится хуками `onPlace`/`onRemove` блока и валидируется по миру при поиске (протухшие записи выкидываются).
- Прямая = частный случай сплайна (оба маркера смотрят вдоль линии A→B). Никакого отдельного кода для «прямых рельс»; кривые получаются направлениями маркеров.
- Конец существующего пути продолжается так же: маркер возле существующего узла (снап-радиус 1.5) переиспользует узел и его касательную — гладкое продолжение.
- Валидации (пересечения, предельные уклоны, радиусы) — нет в v0. Превью сплайна до постройки — нет (маркеры физически видны, линия-превью ушла вместе с планировщиком).

**Визуал рельс (v0):** минимальный — хоть отладочная линия/простая геометрия вдоль сплайна. Красота — потом.

**Рендер рельс из .obj (реализовано 2026-06-10, проверено в игре с атласом 2026-06-10; с 0.9 модель — стиль сегмента из пака, §6.10, а rail.obj MVP из мода удалён):** модель `DevAssets/rail.obj` (3 объекта: RAIL_LEFT/RIGHT — два рельса вдоль **X**, разнесены по Z на колею ±0.81; RAIL_BASE — шпала поперёк вдоль Z, шире колеи. Треугольники, есть UV+нормали; единицы = блоки, Y-вверх, **рельс вдоль X, тайл 1.0 длиной** (стыкуются каждый блок); материал ссылается на `mvp_tracks_map.png`, которой в комплекте НЕТ) скопирована в `resources/assets/.../geo/rail.obj`. `client.render.model.ObjLoader` парсит .obj → `Mesh` по объектам (первое реальное применение сменного источника модели из §2.4). Текстурирование (2026-06-10): атлас `mvp_tracks_map.png`, под который модель и заточена, **получен** и скопирован в `resources/assets/.../textures/geo/mvp_tracks_map.png` (UV в .obj лежат в 0..1, индексируют атлас). `RailModel` грузит .obj из classpath один раз, сливает 3 объекта в **один меш** с **родными UV** и белым цветом вершин (атлас несёт цвет, вершины не тонируют). Рендер — один батч `RenderType.entityCutoutNoCull(mvp_tracks_map.png)`. **Флип V (2026-06-10):** `ObjLoader` кладёт `v = 1 − vt.v` — OBJ хранит V началом снизу-слева, MC сэмплит V сверху; без флипа рельс брал низ атласа (мусор) вместо полос профиля сверху. (Промежуточные заглушки до получения атласа — плоский цвет рельсов и box-проекция дуба на шпалу — убраны.) Урок на будущее (когда текстур станет >1, напр. отдельный материал на состаренный рельс): immediate `bufferSource()` держит один общий BufferBuilder для произвольных текстур, поэтому два буфера одновременно держать нельзя — нужно emit→`endBatch` по очереди, иначе `IllegalStateException: Not building!`. `client.render.RailRenderer` тянет тайл вдоль сплайна КАЖДОГО сегмента с изгибом (локальный Z вершины → дистанция s, локальные X/Y → правый/верх кадра пути; нормали — в тот же кадр), кэширует по segment id, перестраивает при смене ревизии графа; рисует через `RenderLevelStageEvent` на стадии **AFTER_BLOCK_ENTITIES** (важно: блочные стадии типа AFTER_CUTOUT_BLOCKS стреляют до того, как ваниль ставит поворот камеры на модель-вью стек — геометрия «прилипает» к камере; AFTER_BLOCK_ENTITIES — та же конфигурация, в которой ваниль рисует block entities), свет сэмплится посегментно (центр тайла +1 блок). Очистка кэша на logout. **Коллизия рельсового полотна (0.3; переосмыслено 2026-06-10):** полотно — это **коллизия рельс**, видимый реальный блок `TrackBedBlock`, выставляемый вдоль сплайна. Его **материал** (как он выглядит — воздух/гравий/земля/…) выбирается вместе со стилем рельса (с 2026-10-10, ниже; до того — фикс. гравий). Габариты блока: высота `layers` 1–8 (по 2px), `noOcclusion`; предмет (гравийное полотно) в креатив-табе. *(Промежуточно 2026-06-10 полотно сделали невидимым и только в воздухе — это было непонимание (материал/вид — дело редактора, а сам блок видимый), откатано.)*
- **Материал полотна (решение 1.3, 2026-10-10, по просьбе пользователя).** Подложка выбирается в экране рельсов рядом со стилем — 13 материалов (`rail.BedMaterial`): гравий (по умолчанию), каменистая земля, земля, песок, камень, булыжник, андезит, гладкий камень, каменные кирпичи, серый бетон, дубовые и еловые доски и **невидимая** («воздух»).
  - **Блок на материал**, а не свойство блокстейта: `track_bed` (гравий — прежнее имя, старые миры не трогаются), `track_bed_<материал>`; все — `TrackBedBlock` с тем же `layers` и той же формой. Так у каждого свои звук шагов и цвет на карте (от ванильного блока-образца), а у невидимого — `RenderShape.INVISIBLE`, нет частиц, не затеняет соседей (AO) и не застит небо даже полным блоком на крутом уклоне. Форма и рамка выделения у невидимого остаются: по нему ходят, его ломают (снос сегмента), по нему кликают Shift+ПКМ. Прочность у всех одна (1.5) — ломается всё равно сегмент целиком.
  - **Ресурсы генерируются** `tools/gen_track_bed.py`: список материалов он читает из `BedMaterial.java` (единственный источник), текстура — ванильная `minecraft:block/<id>` (исключения — словарь в скрипте), модели `block/track_bed/base_<n>` (шаблон высоты) + `<материал>_<n>`, блокстейты, модель предмета; предупреждает о блоках без имени в lang-файлах. Новый материал = строка в enum + запуск скрипта + имя в lang.
  - **Данные:** сегмент хранит материал (`RailSegment.bed`, id; `""` = гравий — его же получают сегменты из старых сейвов; NBT `Bed`, синк в `RailGraphSyncPayload`); стиль и материал вместе — `RailSegment.Look` (с чем строит предмет и что применяет перекраска). Незнакомый id кладёт гравий. Предмет: data component `railswheelsandtrains:rail_bed` (нет = гравий), в подсказке — «Подложка: …». `SelectRailStylePayload` несёт и материал; сервер принимает только известный ему.
  - **Укладка:** клетка, нужная нескольким сегментам, получает полотно того, кому нужно больше слоёв; при равной высоте — **старшего** сегмента (меньший id): путь, пристроенный к существующему, не перекрашивает стык, и результат не зависит от порядка обхода. Смена материала — та же перекладка, что и смена стиля (`RailNetwork.relook`): блоки другого материала заменяются на месте.
  - **Перекраска:** Shift+ПКМ рельсами по полотну применяет к конструкции и стиль, и подложку из предмета; `/rwat rail bed <материал>` — вся сеть измерения, стили не трогаются (`/rwat rail style` теперь не трогает подложку).
  - **Экран** (`RailStyleScreen`, «Стиль рельсов и подложка»): под 3D-превью — подпись «Подложка: …» и ряд иконок блоков (у невидимой — барьер), выбранная обведена, имя — в подсказке. В превью рельс лежит на полосе выбранного полотна 3 блока шириной (рисует сам блок полотна — невидимое не рисуется). Автоскриншот: `-Pautoshot=rail:<стиль>@<материал>`.
  - **Не сделано:** произвольный блок как материал (copycat-модель с block entity — отдельная большая работа; список покрывает ходовые случаи), материал по стилю из пака (дефолт подложки в декларации стиля), разные материалы под шпалами и на откосах.

- **Полотно = ровно те блоки, которых касается нарисованная модель рельса (решение 2026-10-09).** Требование: под каждым кусочком модели — полотно, даже если модель задевает блок совсем чуть-чуть, и ни одного блока полотна без рельса. Полоса выше была шире модели (шпала стандартного рельса ±1.25, MVP ±1.3125) и сплошной, а шпалы дискретны: на сети «New World (2)» 3469 из 27 340 блоков полотна (13%) были без модели; одно сужение полосы до ±1.25 оставляло 632 — промежутки между торцами шпал на кривых. Теперь `path.BedRaster` кладёт тайл стиля сегмента **тем же свипом, что и рендер** (`path.TrackSweep` — общий код рендера и полотна: путь с `OverhangPath` +0.5 на открытых концах, `tileCount = max(1, round(L/tile))`, кадры станций), проецирует каждый согнутый треугольник на землю и точно отсекает по сетке блоков (Sutherland–Hodgman). Блок — под путём, если кусок грани в нём не тоньше `MIN_TOUCH` = 1/256 блока (1/16 px; толщина = 2·площадь/периметр куска — ширина полоски вдоль края, ~треть катета уголка): видимое касание считается, волосок и шум на границе — нет (торец рельса на осевом открытом конце лежит ровно на границе блока). Осевая прямая — по-прежнему ровно 3 блока от клетки узла до клетки узла; на кривых и диагоналях полотно идёт по торцам шпал. `BedRasterTest` сверяет растр с независимой проверкой (каждая точка модели — над полотном; в каждом блоке полотна модель есть — SAT «треугольник/квадрат») на кривых, диагонали и широкой шпале.
- **Отпечаток стиля знает сервер (2026-10-09):** форма полотна — от стиля сегмента (§6.10). `data.RailFootprintReloadListener` на data-перезагрузке читает те же `assets/<ns>/rail_models/*.json` и OBJ, что рисует клиент, — из пакетов сервера (RWAT-паки и jar мода зарегистрированы и как data-паки, §6.2), по тем же правилам (`HIDE` не рисуется, рельсы растягиваются на тайл — `path.TileFootprint`; клиентский загрузчик переведён на эти же правила); реестр `rail.RailFootprints`. Стиль, которого у сервера нет, кладёт полотно стандартного рельса — как клиент рисует незнакомый стиль стандартным; не загрузился даже стандарт — встроенные боксы его шпалы и рельсов. Грани материала без текстуры клиент не рисует, а полотно учитывает (в паках таких нет).
- **Перекладка (2026-10-09):** полотно сегмента зависит от соседей — открытый конец даёт +0.5 рельса, а состояние концов задаёт раскладку тайлов по всему сегменту. Поэтому постройка и снос перекладывают полотно отредактированных сегментов **и их соседей по общим узлам**, перекраска — полотно конструкции (`RailNetwork.layBed`): что было под ними и больше не нужно ни одному сегменту — убирается, что нужно — кладётся; слои в блоке = максимум по всем сегментам, чьё полотно его занимает (чужие тоже — стык и пересечение не теряют нужного соседу). Принадлежность блока (поломка, перекраска) — точный тест по растру с префильтром по габариту сегмента (оболочка контрольных точек Безье + вылет тайла) и растеризацией только тайлов рядом с блоком (`BedRaster.Area`). Цена — ~10–20 мс на сегмент в 400 блоков (мостовой тайл MVP, ~1000 треугольников, ~150 мс), только при правках.
- **Старые миры:** полотно, уложенное полосой, при сносе или перекладке сегмента убирается вместе с новым (`legacyStrip` воспроизводит старую раскладку) — сирот не остаётся; `/rwat rail rebed` перекладывает полотно всей сети измерения разом (грузит все её чанки) — для миров до 2026-10-09 и после смены тайла стиля в паке.
- **Сегмент — единое целое (2026-06-10):** поломка игроком любого блока полотна разбирает весь сегмент А→Б (`playerWillDestroy` → `RailNetwork.removeSegmentContaining`: точная проверка принадлежности клетки по `bedCells` сегмента; на общей клетке стыка побеждает первый найденный сегмент). Блок «глупый» — геометрию графа не хранит и источником правды не является (граф живёт в SavedData); удаление сегмента убирает свои `TrackBedBlock`-блоки. Это коллизия для игрока/мобов; вагон в v0 по-прежнему без коллизии (§2.5).

**Статус Слоя 1 (проверено в игре 2026-06-10):** постройка/езда по графу работает. Косметические долги закрыты: (1) [исправлено 2026-06-10] кривая укладка полотна — теперь отбор клеток по расстоянию до оси (§выше); (2) [неактуально] отладочная линия сплайна удалена вместе с дебаг-оверлеями.

### 2.3 Слой 2 — Кинематика

- **Вагон = корпус на двух тележках (bogie).** Сразу две, не одна: одноточечная модель — это вагонетка, она выкидывается целиком.
- Каждая тележка — точка на сплайне на своей дистанции: ведущая на `s`, задняя на `s − wheelbase`.
- **Корпус не движется сам.** Позиция = середина между тележками, ориентация (yaw + pitch) = по вектору между ними. Отсюда бесплатно: вписывание в повороты, наклон на уклонах.
- Движение состава = продвинуть `s` головы; всё остальное выводится.
- **Управление (v0):** игрок садится в вагон (ванильная посадка пассажира, одно место), клавиши вперёд/назад меняют целевую скорость, простое сглаживание. Без HUD, без GUI.
- Поведение на конце пути (v0): остановка на границе сегмента/сети. **Замкнутое кольцо (2026-06-10):** маршрут, у которого конец совпадает с началом (последняя нога кончается в узле первой), помечается `TrackPath.loop()`; `s` состава растёт монотонно без ограничений (зажим минимума головы/конца не применяется), а `RoutePath` заворачивает `s` по модулю длины только при сэмплинге — интерполяция клиента не видит скачка, состав циркулирует бесконечно. Кольцо короче поезда — наложение вагонов, валидации нет (v0).

**Статус Слоя 2 (реализовано 2026-06-10, сборка + 5 юнит-тестов зелёные, в игре ещё не проверено):** двухтележечная модель вынесена в чистое ядро `kinematics` (без MC-импортов): `ConsistGeometry` (фиксированный `DEFAULT` = 3 вагона, база тележек 4, шаг между вагонами 7), `WagonPose` (позиция корпуса + обе тележки + yaw/pitch), `ConsistKinematics.wagonPose(path, headS, wagonIndex, geometry)`. Состав из нескольких вагонов: по сети по-прежнему синхронизируется только `s` головы, каждый вагон разворачивает свою позу по индексу и общей геометрии. `WagonEntity` получил синхронизируемый `DATA_WAGON_INDEX`; `/rwat spawn` ставит 3 вагона и поднимает стартовый `s` так, чтобы весь поезд влез на путь. Дебаг-рендер (метки тележек + линия сплайна) удалён 2026-06-10 вместе с остальными оверлеями — кинематика проверена, картинка стала «настоящей». Нормальные модели — Слой 3.

**Посадка и управление (реализовано 2026-06-10, сборка зелёная, в игре ещё не проверено):** машинист садится правым кликом в **головной вагон** (одно место, ванильная посадка через `passengerAttachments`); трейлерные вагоны без места. Модель скорости — **тяга-нотчи** (выбор пользователя, прочтение SPEC «целевая скорость + сглаживание»): клавиши вперёд/назад двигают целевую скорость `targetV` (шаг `THROTTLE_RATE`, до `MAX_SPEED=0.5` бл/тик, через 0 в реверс), фактическая `v` плавно едет к цели (`ACCEL`); отпустил клавиши — скорость держится (круиз). На конце пути `v` и `targetV` обнуляются. Ввод: клиент каждый тик шлёт `DriveInputPayload(consistId, throttle∈{-1,0,1})` (ваниль-клавиши W/S), сервер применяет только если игрок реально сидит в кабине этого состава; без машиниста газ обнуляется. `/rwat speed` ставит и `v`, и `targetV`. Без HUD/GUI (одноразовый actionbar-хинт при посадке). Клиент-предикшн водителя — вне v0 (§2.5).

**Жёсткий состав и упор в конец пути (0.3, 2026-06-10):** состав v0 — жёсткое тело: все вагоны привязаны к одному `s` головы и разнесены на фикс. шаг, между собой не сталкиваются. Чтобы хвост/голова не «уезжали» за край сплайна (где `samplePosition` зажимает координату в концевую точку и вагоны схлопываются), голова держится в диапазоне `[min(длина_поезда, длина_пути), длина_пути]` (`Consist.minHeadS`/`advance`). Если путь короче поезда (~18 блоков) — состав не помещается и пинуется к концу (дебаг-ограничение, строить путь длиннее поезда).

### 2.4 Слой 3 — Рендер

- Один **захардкоженный вагон** (уровень «коробка с окнами»). Его задача — проверить трансформации: позиция/поворот из тележек, наклон на уклонах, корректный сэмплинг света.
- Геометрия — во внутреннем представлении (данные), бэйкается и рендерится через современный pipeline (RenderType / VertexConsumer). Не legacy GL, не геометрия руками в коде рендерера.
- **GPU-бейк (2026-06-11, по плей-тесту шага 4 — FPS 110→30-40):** путь «`Mesh.emit` в `VertexConsumer` каждый кадр» означает CPU-трансформацию и переливку каждой вершины каждый кадр — для ванильных моделей нормально, для ЧМЭ3 (17 233 квада ≈ 69k вершин × 2 вагона) плюс сотен тайлов рельс — главный пожиратель кадра. Решение: `GpuMesh` — меш заливается в `VertexBuffer` (VBO) один раз, кадр = несколько draw call'ов (`drawWithShader`, modelview = глобальная MV × поза из `PoseStack` — эквивалент CPU-пути). Свет и overlay запекаются в вершины: рельсы — посегментно при перестройке (ревизия графа или раз в 200 тиков — факел у путей подхватится за ~10 с), вагон — `BakedStockModel` на каждое встреченное значение packedLight (на улице это ровно одно; кэш чистится при >8). Партовая структура (корпус/рамы тележек/каждое колесо) сохранена — у каждой части своя матрица за кадр (артикуляция, вращение колёс). Осознанный компромисс: нормали запечены в модель-спейсе и за кадр не довращаются — диффузная подсветка фиксирована относительно модели (вершинный шейдер entity берёт нормаль как есть; перезапечь — негде, отдельной uniform-матрицы нормалей у `drawWithShader` нет). `DEBUG_BOGIES` выключен (отыграл своё).
- **Туман и статичные мировые буферы (2026-06-11, плей-тест bug3.png — рельсы местами бело-голубые):** entity-шейдеры считают туман от **сырой координаты вершины** (`fog_distance(Position)`) — для энтити это верно, их вершины каждый кадр CPU-трансформируются в камера-относительные. Статичный VBO рельсов хранит абсолютные мировые координаты → туман считался «от нуля мира»: участки пути с большими координатами тонули в тумане независимо от камеры (дальняя кривая у нуля рендерилась нормально — ключевая улика). Решение: рельсы рисуются **террейн-шейдером** (свой `RenderType` `rwat_rails`: формат BLOCK, `RENDERTYPE_CUTOUT_SHADER`, текстура рельс, lightmap, no-cull — `RwatRenderTypes`), который складывает `Position + ChunkOffset` и от суммы считает и позицию, и туман; рендерер передаёт `ChunkOffset = −камера` — ровно как ванильные чанки. Следствия: (а) диффуз по нормалям у террейн-шейдера нет — затенение запекается в цвет вершин при перестройке (формула `minecraft_mix_light` entity-шейдера); (б) `BufferBuilder` молча пропускает атрибуты, которых нет в формате (overlay в BLOCK), поэтому общий `Mesh.emit` обслуживает оба формата; (в) у **вагона** обратная ситуация: его вершины модель-спейсные (малые), entity-туман от них ≈ 0 — вагон не туманится вовсе; в радиусе трекинга энтити (<64 блоков) это незаметно, принято осознанно.
- **Регионизация рельсового меша + каллинг рельсов (2026-06-12, по фризу 0.8–1.3 с каждые ~10 с на сети ~3800 блоков, GC-лог чистый — профайлер показал 98% кадра в `after_block_entities`):** один VBO на всю сеть означал, что любая перезаливка — перестройка по ревизии графа и особенно периодический relight (раз в 200 тиков, см. GPU-бейк выше) — перепекала и заливала **весь** меш синхронно в рендер-потоке. Чинилось в два слоя: (1) relight отделён от геометрии — тайл кеширует согнутый+затенённый меш и точку сэмпла света, по таймеру только пересэмпл света и перезаливка при реальном изменении; на большой сети этого мало — стриминг чанков у игрока постоянно меняет свет дальних тайлов (невыгруженный чанк даёт 0) и перезаливка всего меша возвращалась почти каждый relight; (2) меш разбит на **бакеты по регионам 64×64 блока** (`RailRenderer.Bucket`, ключ — `ChunkPos.asLong` региона): VBO на бакет, бейк **лениво при первой видимости** (бакет, к которому игрок не подходил, вообще не заливается), relight пер-бакетный и пропускает невыгруженные/незапечённые бакеты, рисуются только бакеты в радиусе прорисовки **и** с загруженным чанком в центре (заодно ушли рельсы, висящие в пустоте за пределами прогруженного мира), GPU-память бакетов дальше 2× радиуса освобождается. Принцип «кадр = один draw call на рельсы» осознанно заменён на «draw call на видимый регион» — это десятки вызовов, цена незаметна. Лезвия стрелок (`bladeTiles`) остаются одним маленьким мешем без регионизации.
- **Ревью рендера (2026-10-08, сборка + тесты зелёные; клиент входит в копию тестового мира без ошибок, модели грузятся в фоне; визуально в игре не проверено):** охота на оставшиеся источники «рывка раз в N» после регионизации. Сделано:
  - **Рельсы — по-сегментная синхронизация вместо полной перестройки.** Раньше любая смена ревизии (постройка сегмента где угодно в измерении, **каждый перевод стрелки редстоуном** — при `SWITCH_BLADES = false` геометрию не меняющий вовсе) выкидывала все VBO, перегибала всю сеть и в том же кадре заливала все видимые регионы — у всех игроков в измерении; редстоун-часы на стрелке = фриз на каждый такт. Теперь у каждого сегмента кэш тайлов под ключом «кривая (p0/m0/p1/m1) + концевая обработка (overhang, вырез под остряки)»; новый граф перегибает только сегменты с изменённым ключом (новые, их соседи, у которых сменился overhang) и выкидывает удалённые — грязными становятся только задетые регионы. Состояние стрелки в ключ не входит (двигает только остряки).
  - **Бейк регионов растянут по кадрам:** бюджет 131 072 вершины за кадр (минимум один регион), видимые и ближние первыми; грязный регион рисует **старый** меш, пока новый не готов (раньше меш сбрасывался в `null` и перезаливался синхронно). Покрывает и логин/телепорт, и пересветку, и правки графа.
  - **Пересветка рельс — по событию, без опроса.** Прежняя схема «раз в 200 тиков пересэмплить всё» была упрощением июня (не было сигнала об изменении света): до 10 с запаздывания факела и полный проход по сети каждые 10 с, даже когда ничего не менялось. Теперь как у ванили, которая так же перестраивает секции чанков: два клиентских миксина — `ClientChunkCache.onLightUpdate` (клиентский движок света сообщает каждую секцию с изменившимся светом; вызывается из `runLightUpdates` внутри `renderLevel`, **до** стадии рельс — факел виден в том же кадре) и `ClientLevel.setSectionDirtyWithNeighbors` (свет, пришедший с сервера: подгрузка/выгрузка чанков, пакеты света; 3×3×3 как у ванили) — помечают секцию, если в ней сэмплится свет хоть одного тайла (индекс «секция → тайлы»). В кадре пересэмпливаются только тайлы помеченных секций (≤ 2048 за кадр, остаток — в следующих), регион перезаливается, только если значение реально изменилось. Тайл в невыгруженном чанке держит прежний свет (раньше проверялся только центральный чанк региона — тайлы на границе прорисовки моргали 0↔реальный свет); приход чанка сам сообщается как изменение света. Смоук-тест 2026-10-08 на копии мира с сетью из 108 регионов (463 секции): оба миксина применились рядом с Sodium/Iris/Lithium/ModernFix, регионы заливаются порциями по кадрам, события подгрузки чанков доходят до рельс.
  - **Компактный тайл:** вместо `Mesh` из record-объектов (~22 КБ на тайл, ~85 МБ old gen на сеть в 3800 блоков) — `float[]` позиций + `int[]` (нормаль 3 байта + затенение 1 байт), UV и базовый цвет живут в общем `TileTemplate` (~4 КБ на тайл). Треугольники рельса (rail.obj — сплошь треугольники) пекутся в режиме `TRIANGLES`, без вырожденной 4-й вершины (276 вершин на тайл вместо 368).
  - **Изгиб по «станциям»:** у вершин тайла всего 7 различных локальных X — кадр пути (позиция/касательная/right/up) считается раз на станцию, а не дважды на вершину (~50× меньше сэмплов сплайна и аллокаций `Vector3d`).
  - **Frustum-каллинг регионов рельс** (`event.getFrustum()`, AABB центров тайлов + 2 блока): раньше рисовалось всё в радиусе, включая регионы за спиной.
  - **Вагоны — LRU вместо полного сброса кэша бейков.** Кэш (модель, packedLight) при переполнении (>16) закрывал **всё**, и все вагоны на экране перепекали ~70k вершин в одном кадре — поезд под фонарями/в тоннеле с факелами делал это регулярно. Теперь LRU на 24 записи + **не больше одного нового бейка за кадр**; остальным вагонам на кадр-другой отдаётся последний бейк той же модели при другом свете (ступенька света на пару кадров позже вместо рывка). Принципиальное решение (свет вне VBO — свой шейдер с uniform света, одна запечка на модель навсегда, заодно честные нормали и туман вагона) отложено: под Iris свой шейдер не патчится шейдерпаком.
  - **`ObjLoader` больше не дробит квады.** Четырёхугольная грань веером резалась на два треугольника-вырожденных-квада — 8 вершин вместо 4; IR-модели ~85% квадов, так что каждый вагон гонял почти вдвое больше вершин (и бейк, и вершинный шейдер, и VRAM). Квад рисуется теми же (0,1,2)+(2,3,0) — картинка та же. Лог загрузки: интерьер плацкарта 12 155 → 6 435 квадов.
  - **LOD интерьера:** объекты с **префиксом** `INTERIOR` (у плацкарта `INTERIOR_1` — ~37% всей геометрии, у ЧМЭ3 964 квада) выделены в `StockModel.interior` и рисуются, только пока камера ближе 32 блоков к центру корпуса (из кабины/салона — всегда). По префиксу, не по подстроке: токен `_INTERIOR_` есть и у видимых снаружи частей (окна кабины ЧМЭ3).
  - **Модели грузятся в фоне:** `StockModels.preload()` на client setup разбирает .obj в `Util.backgroundExecutor()` (раньше — синхронно в рендер-потоке в кадр, когда тип впервые попадал в кадр); битый ассет → пустая модель + лог, а не падение рендера.
  - **Батч отрисовки** (`GpuMesh.Batch`): draw call'ы группируются по `RenderType`, setup/clear состояния — раз на тип, а не на каждый меш (вагон ~10–12 мешей → ~5 групп; рельсы — одна).
  - **Смена измерения:** клиент сравнивал серверную ревизию графа, а она у каждого измерения своя — при совпадении счётчиков оставались рельсы прежнего измерения. Теперь `ClientRailGraph.generation()` — локальный счётчик синков (никогда не повторяется в сессии), плюс рендер рельс сбрасывается при смене `ClientLevel`.
  - **Не сделано (сеть, не рендер):** перевод стрелки и постройка по-прежнему шлют всем в измерении **полный** граф (а Y-стрелка — 3–4 раза подряд за одну постройку); клиенту теперь это дёшево, но трафик растёт с размером сети — кандидат на дельта-синк.
- Партиал-тик: рендер использует интерполированный `s` из сетевого слоя.
- **Каллинг (0.2, новое):** MC отсекает entity по её AABB — длинному вагону нужен расширенный cull-бокс (`getBoundingBoxForCulling`), иначе вагон исчезает у края экрана.
- **Сменный источник модели (0.3, новое — закрывает открытый вопрос про .obj):** `EntityRenderer` не знает про источник геометрии — он лишь эмитит в `VertexConsumer`. Геометрия живёт во внутреннем `Mesh` (квады: позиция/UV/нормаль/цвет), и источник этого меша **сменный**: сейчас захардкоженный генератор, потом тот же `Mesh` отдаёт `ObjLoader`/парсер пака — рендерер не меняется. .obj годится для цельного корпуса (статичный меш); подвижные части (двери/пантограф) — это несколько частей, каждую двигать своим `PoseStack` (рендерер уже умеет), либо glTF с иерархией — но это забота загрузчика, не рендерера. У NeoForge встроенный .obj есть только для блоков/предметов, для сущностей эмитим сами (так гибче, по принципу standalone).

**Статус Слоя 3 (реализовано 2026-06-10, сборка зелёная, в игре ещё не проверено):** геометрия-как-данные `client.render.model.Mesh` (квады pos/uv/нормаль/цвет, `emit` в `VertexConsumer`, строится один раз) + захардкоженный генератор `WagonModel` («коробка с окнами»: тёмно-красный корпус, окно-полоса голубых декалей по бортам, модель-спейс x∈[−1,1]/y∈[0,2]/z∈[−3,3], +Z вперёд). `WagonRenderer` рисует залитую модель через `RenderType.entityCutoutNoCull(white)` (плоский цвет × свет, нормали → диффуз; без culling, чтобы не ловить winding руками), поза/поворот — из `WagonPose`, свет — `packedLight` сущности. Текстуры-ассета нет: используется ванильный `textures/misc/white.png`, цвета во вершинах. Дебаг-оверлеи (красные метки тележек + жёлтая линия сплайна на головном) удалены 2026-06-10 — свою валидационную роль отыграли. **Модель ЧМЭ3 (реализовано 2026-06-11, сборка зелёная, в игре ещё не проверено):** первый настоящий локомотив вместо «коробки» — ассет формата Immersive Railroading из `DevAssets/CHME3` (`mvp_ir_chme3.obj`, ~100 именованных объектов, 6 материалов, масштаб 1:1, длина рамы 18.125 блока, ось движения в исходнике — **X**). ### v1.5 — **Коллизия.** Две РАЗНЫЕ задачи, не смешивать:
- **(а) «Стены выталкивают»** — игрок/мобы не проходят сквозь корпус, проход через дверные проёмы (двери: открыта/закрыта). *Решение 0.6 (2026-06-12):* делаем **жёстко, IR-уровень** (выбор пользователя — в IR корпус непробиваем снаружи, нельзя ни пройти, ни пролететь сквозь стены, только в открытую дверь), а не мягким пост-выталкиванием. Прежняя формулировка «набор выталкивающих AABB/OBB» = мягкий пуш — его одного мало: он не ловит тоннелирование (быстрая/летящая сущность за тик проскакивает). Реализация в **двух частях, общая геометрия**: (1) **жёсткий swept-clamp** перемещения сущности об корпус — миксин на `Entity.collide` (common: клиент клампит локального игрока, т.к. движение игрока клиент-авторитетно и сервер `collide` для игроков не зовёт; сервер клампит мобов). OBB решается переводом перемещения и AABB сущности в локальный кадр вагона (там корпус осе-выровнен), пер-осевой sweep как в ванили, поворот обратно — вся математика в чистом `kinematics.HullCollision` (юнит-тесты). Clamp запрещает только ВХОД (уже-проникшая сущность свободна — её достаёт часть 2). (2) **толчок от движения вагона** — сервер в `ConsistManager.tick` выпихивает то, во что вагон наехал (случай «вагон догнал стоящего», который clamp на чужом движении не покрывает): мобам — `setPos`, игрокам — импульс через motion-пакет (knockback-стиль, без `setPos` → без рубербенда/«moved wrongly»). **Корпус — сплошной OBB** (без дверных проёмов в этом инкременте, выбор пользователя), выводится из `WagonType.length` + габаритные константы (полуширина/высота/длина=length/2), так что и кабинный локомотив без `interior` получает корпус; пер-тип переопределение и проёмы дверей (= разрыв в наборе слэбов, гейт открыта/закрыта, общая дверная геометрия с (б) п.5) — следующий шаг. Свой пассажир (`getVehicle()`) с корпусом своего вагона не сталкивается. **Статус: ядро реализовано 2026-06-12** (сборка + юнит-тесты `HullCollisionTest`, в игре не проверено). Первый боевой миксин на общей (не клиент-онли) стороне — инфра из (б).
- **(б) «Пол везёт» (moving platform)** — *решение 0.5 (2026-06-12) заменяет прежнее:* ~~дискретные позиции вместо свободного хождения~~ → **схема IR «пассажир с управляемой точкой привязки»**. Прежняя оценка «месяцы» относилась к честной moving platform (свободный игрок в мировых координатах против серверной валидации движения); IR её не делает. Вместо этого игрок внутри вагона — **технически пассажир (riding) entity вагона**: (1) анти-чит «moved wrongly» не применяется к пассажирам — позицию диктует vehicle, война с валидацией не происходит; (2) ванильная физика/коллизия игрока выключена — мод полностью владеет позицией; (3) перемещение по вагону = симуляция в **локальных координатах модели**: на вагоне `Map<UUID, локальная позиция>`, клиент шлёт ввод, сервер поворачивает ввод в локальный кадр, двигает точку и клампит против статичной внутренней коллизии (пол/стены/потолок/полки — AABB в модель-спейсе, вагон относительно себя неподвижен), мировая позиция = поза вагона × локальная точка; вся динамика (ход, крен, повороты) приходит бесплатно через трансформацию позы. (4) Снаружи корпус — выталкивающий OBB (= задача (а)); пассажир с ним не сталкивается. (5) Дверной проём — триггер-зона в локальных координатах, ворота режима: вход через открытую дверь или ПКМ (`startRiding`, конверсия мир→локаль), выход — ПКМ/проход через открытую дверь изнутри (локаль→мир, dismount); закрытая дверь = зона неактивна + проём закрыт коллизионной панелью. Выпасть из едущего вагона нельзя — других путей из режима нет. (6) Рендер пассажиров — по той же интерполированной позе (`renderPose`), что и корпус: игрок не дрожит относительно интерьера; локальное движение клиент предсказывает сам. Честная цена — недели: сложность в конверсии мир↔локаль на границах, клиентском предикшне локального движения и выгрузке/логауте пассажира внутри вагона. Разметка `SEAT_*` в ассетах остаётся заделом под сидячие места (фиксированная локальная точка = частный случай той же схемы).

## 5. Подвижной состав как данные (дизайн 0.4, принят 2026-06-11)

Цель: от захардкоженного «все вагоны — ЧМЭ3, геометрия в константах» к системе, где тип вагона — **декларация данных**, а разные конфигурации (число тележек, масса, мощность, тормоза, наличие кабины) — это разные записи реестра, не разный код. Паков пока нет, но фундамент кладётся пак-готовым (принцип №5): сейчас реестр захардкожен в коде, потом тот же реестр наполняется парсером JSON из datapack — потребители не переписываются (тот же приём, что интерфейс пути в Слое 0).

### 5.1 WagonType — декларация типа вагона

Чистое ядро (пакет `stock`, без MC-импортов). Поля (эскиз будущего JSON 1:1):

- `id`, `length` (по сцепкам/буферам, блоки), `bogies[]` — **список** продольных позиций пивотов тележек относительно центра (+вперёд). Список, не пара: двухтележечный вагон — частный случай; задел под трёх-/сочленённые.
- `mass_t` (тара; груз — поле инстанса, позже), `max_speed_kmh`.
- `traction` (опционально): `power_kw`, `max_tractive_effort_kn`. **Наличие секции = вагон тянет.**
- `cab` (опционально): место машиниста. **Наличие = из вагона можно управлять составом.**
- `brakes`: несколько контуров (§5.4).
- Единицы в декларации — человеческие (т, кВт, км/ч, кН); конвертация в блоки/тик — один раз на границе загрузки.

**Роли — способности, а не enum (анти-RTM-проблема):** «локомотив» = traction+cab, головной вагон без двигателя = cab без traction, моторный вагон ЭМУ = traction без cab, пассажирский/грузовой = ничего. Машинист в любой кабине управляет всем составом; тянут все traction-единицы состава (MU бесплатно — сумма в формуле §5.5).

Серверная часть (физика/геометрия) и клиентская (модель/текстуры) — разные половины декларации; при переходе на паки это штатный сплит datapack/resourcepack. Сервер авторитетен, клиенту физика не нужна.

### 5.2 Части модели: одна модель, конвенция имён (IR-стиль, анти-RTM)

**Решение:** модель вагона — **один OBJ**; части помечаются **именами объектов** в редакторе (Blender): `BOGEY_FRONT*` / `BOGEY_REAR*` (дальше — `DOOR_*`, `WHEEL_*` и т.п.). Отвергнута RTM-схема «тележка и корпус — отдельные модели, сборка координатами в JSON»: куча правок координат вслепую и перезапусков игры на каждую итерацию. В нашей схеме моделлер видит вагон собранным в Blender'е, координаты живут в модели, JSON координаты не таскает. Ассет ЧМЭ3 уже размечен этой конвенцией (включая разметку под будущее: `DOOR_*`, `GAUGE_SPEED_*`, `THROTTLE_*`, `REVERSER_*`, `COUPLER_*`).

Загрузчик режет меш на компоненты: **корпус** (всё непомеченное) + **группа на тележку**. Группа тележки при загрузке переносится в локальные координаты своего пивота (z −= pivot из `bogies[]`, сопоставление по имени FRONT/REAR; для N тележек — по ближайшему пивоту). Рендерер рисует корпус по позе корпуса, а каждую тележку — **своим PoseStack: позиция = точка её сэмпла пути, поворот = локальная касательная пути** → артикуляция тележек на кривых и переломах профиля получается бесплатно и закрывает долг §2.4 («BOGEY_* едут жёстко»).

### 5.3 Тормоза: несколько контуров, как у настоящих

Контуры различаются **кто ими управляет и на какие вагоны они действуют**; в декларации вагона — только усилия:

- **Автотормоз (train)** — кран машиниста, действует на **все** вагоны состава, у каждого своё `force_kn` (вагон без секции — нетормозной).
- **Вспомогательный (independent)** — только секции с кабиной/локомотивы, не трогает состав.
- **Электродинамический (dynamic)** — у тяговых единиц; усилие зависит от скорости (гаснет ниже `fade_kmh` — реостат на малой скорости не держит).
- **Стояночный (parking)** — ручник, фиксированное усилие, держит состав на уклоне без машиниста.

~~v-first упрощение: усилие контура = нотч × `force_kn`, мгновенно.~~ **С 1.3 (2026-10-10):** усилие контура = нотч × `force_kn`, но **не мгновенно** — рукоятка задаёт цель, усилие идёт к ней инерционным звеном первого порядка (`physics.ControlResponse`; время в секундах до ~95%): тормоз — `brakes.apply_s`/`release_s`, тяга — `traction.ramp_s` (сброс тяги вдвое быстрее набора). Время поезда — по самому медленному вагону (один грузовой в составе тормозит как грузовой). Это наполнение цилиндров и раскрутка дизеля, а не симуляция магистрали: **пневматика по-прежнему НЕ моделируется** (волна давления, истощение). Состояние «усилие в действии» — только на сервере, транзиентно (после рестарта берётся положение рукояток), в сеть не идёт.

**Тормозные системы (1.3):** `brakes.system` — пресет силы на тонну и времени: `passenger` (по умолчанию) — 1.0 кН/т, 4 с / 8 с; `freight` — 0.6 кН/т, 15 с / 30 с; `ep` (электропневматика: электрички, современные вагоны) — 1.1 кН/т, 1.5 с / 3 с. Любое поле перекрывает пресет.

**Стояночный — теперь в физике (1.3):** ручник — **на вагон** (`Consist.handbrakes`, по UUID — переживает сцепку и расцепку; NBT `Handbrakes`), сила `parking_kn` (по умолчанию 0.4 кН/т — держит ~4% уклона), держит на стоянке и тормозит на ходу. Поставленный предметом/командой вагон **стоит на ручнике**. Ручники — монтировкой (ПКМ по кузову вне торцевых зон сцепки, §6.12), **маховиком в кабине** (орган `HANDBRAKE`, §6.3/§9.3: клик — ручник этого вагона; маховик доворачивается к состоянию за 1.5 с, его видят все) или `/rwat handbrake <id> <true|false>`; в профилях с `auto_handbrake` (§5.6) они ставятся сами на стоящем составе с закрытой тягой и снимаются, когда тягу открывают (`physics.AutoHandbrake`) — монтировка тогда только подсказывает. На пульте — строка «Ручники N/M» (§9.7). **ЭДТ (dynamic)** — данные остаются, но в физике его нет. **Отложен (решение пользователя, 2026-10-10):** в моделях MVP и в конвенции IR ручки ЭДТ нет вовсе (проверено по всем OBJ обоих архивов MVP), а в нашей физике воздушный тормоз ничем не наказывается (нет нагрева колодок, истощения магистрали) — у ЭДТ пока нет игровой причины. Вернуться вместе с этим; кандидаты — смешанное торможение краном машиниста (без новой ручки) или своя `DYNAMIC_BRAKE_n`. Управление: реверсор + нотчи тяги + кран автотормоза + кран вспомогательного (расширение текущего `DriveInputPayload`).

### 5.4 Продольная физика (бывш. roadmap v0.5, уточнение)

Состав жёстко сидит на сплайне → одно скалярное уравнение на состав в тик:

```
F = Σ тяга_i(нотч, v) − Σ тормоза_i − Σ сопротивление_i(v) − Σ m_i·g·уклон(s_i)
a = F / Σ m_i;   v += a;   s += v
```

- Тяга: гипербола постоянной мощности `TE = min(TE_max, P/v)` — тяжёлый состав медленно разгоняется, локомотив упирается на подъёме, два локомотива тянут вдвое.
- **Сцепление колёс с рельсом (1.3):** тяга каждого вагона ≤ `μ(v)·m·g·adhesion`, торможение каждого вагона на ходу ≤ `μ(v)·m·g` (Куртиус–Книффлер, сухой рельс: `μ = 0.161 + 7.5/(v_км/ч + 44)` — 0.33 с места, 0.23 на 60, 0.21 на 120). Это не симуляция буксования по осям (её по-прежнему нет), а потолок силы: вагон не тянет и не тормозит сильнее, чем держат колёса. Ревью показало, зачем: IR кладёт мощность всей электрички на головной вагон — головной ЭР2 (40.9 т, 422 кН) без потолка разгонялся до 60 км/ч за 1.9 с.
- **Регулятор (1.3):** тяга тяговой единицы гаснет на последних 5% её `max_speed_kmh` — локомотив не тянет быстрее своей конструкционной скорости.
- **Предел скорости (1.3):** `max_speed_kmh` вагона теперь **необязателен** (нет — вагон поезд не ограничивает) и это **допустимая** скорость. Жёсткий кап `min(max_speed)` — только в профиле с `hard_speed_limit` (аркада); в остальных под горку или толчком поезд может превысить её (последствия — позже: безопасность/автоторможение), предел — только абсолютный 400 км/ч. Раньше кап молча гасил энергию на спуске и не давал ЭР200 ехать быстрее 120 из-за прицепов с умолчанием конвертера.
- Сопротивление: Дэвис `a + b·v + c·v²` на вагон (качение и обшивка) **плюс лоб `c_front·v²` — платит только вагон, идущий первым по ходу** (1.3): локомотив в середине не толкает воздух, хвостовой вагон при движении назад — толкает.
- Уклон: проекция веса **каждого вагона по его собственному `s_i`** (pitch уже сэмплится) — длинный состав на переломе профиля ведёт себя правильно (голова на спуске, хвост ещё в горе).
- Сознательно НЕТ и в полной версии (анти-скоуп): буксование по осям (потолок по сцеплению — есть, 1.3), продольная динамика сцепок (набегание/растяжка), пневматика тормозов (инерция наполнения — есть, 1.3).
- **Сверено численно (ревью 2026-10-10, копия `step` на Python по паку MVP):** до 1.3 — электричка ЭР2 0→60 км/ч за 4.7 с, ЧМЭ3 с 20 порожняками упиралась в 58 км/ч (аэро `c = 9` на каждый прицеп завышено в 5–10 раз), выбег пустого грузового замедлялся 0.2 м/с² (реально 0.02–0.04), отпущенный вагон держался только на уклоне ~2‰ — любой вагон на горке укатывался. После 1.3, профиль `realistic`: ЭР2 0→60 за 22 с, ЧС4т + 12 плацкартов — за 81 с, ЧМЭ3 + 20 крытых выходит на 91 км/ч, тормозной путь со 60 км/ч — 130–250 м (`standard` — 85–165 м).

### 5.5 Порядок работ (каждый шаг играбелен)

1. **WagonType в чистом ядре + захардкоженный реестр** (одна запись — ЧМЭ3); `ConsistGeometry`/константы `Chme3Model` выводятся из него. Рефакторинг без изменения поведения.
2. **Разрез модели по конвенции имён + артикуляция тележек** (§5.2) — видимый выигрыш, валидирует конвенцию.
3. **Состав из разных типов**: `Consist` = список инстансов типов, таблица офсетов вместо равномерного pitch, синк композиции один раз (тиковый синк `s`+`v` не меняется). Тут же `flipped` (вагон задом наперёд) — вскрывает ошибки знаков рано.
4. **Продольная физика + новое управление** (§5.3–5.4).
5. **JSON-загрузка реестра через datapack** — меняется только источник реестра; с этого момента пак технически существует. Сцепка/расцепка в игре — v1 roadmap.

**Статус: шаги 1–3 реализованы 2026-06-11** (сборка зелёная; шаги 1–2 проверены в игре — артикуляция работает, шаг 3 в игре не проверен): пакет `stock` (`WagonType` с `Traction`/`Cab`/`Brakes`, реестр `WagonTypes` с ЧМЭ3), `WagonPose` несёт пер-тележечную позу (`BogiePose`: позиция + yaw/pitch из касательной в точке тележки), `Chme3Model` отдаёт `StockModel` (корпус-бакеты + тележки в локальных координатах пивотов), `WagonRenderer` рисует тележки своими PoseStack. Кап скорости = min(maxSpeedKmh) по вагонам (с 1.3 — только в аркадном профиле; тормоза и тяга — с инерцией, §5.3–5.4). Старые `targetV`/`THROTTLE_RATE`/`ACCEL` удалены; `/rwat speed` ставит `v` напрямую, дальше физика её честно съедает сопротивлением. Вспомогательный тормоз: данные есть, ручки нет — придёт с HUD кабины.

**Пассажирский плацкарт (2026-06-12, сборка зелёная, в игре не проверено):** второй тип подвижного состава — аммендорфский плацкарт из `DevAssets/PLAZKART` (`mvp_ir_amendorf.obj`, 101 объект, IR-конвенция имён: `BOGEY_*`, `DOOR_1..6` (4 наружные + 2 торцевые межвагонные), `TRAPDOOR_*`, `INTERIOR_*`, 38 плоских маркеров `SEAT_*` — задел под посадку/коллизию). Сделано: (1) загрузчик `Chme3Model` обобщён → `IrStockModel` (та же логика разреза по конвенции, параметризована `Spec`: ресурс, материал→текстура, пивоты, skip-префиксы; общий IR-профиль колеса — константы Y_LIFT/радиус 0.53 общие) + клиентский реестр `StockModels` (id типа → модель, лениво; незнакомый id → модель ЧМЭ3 — зеркало builtin-фолбэка реестра типов); (2) тип `rwat:plazkart` builtin + `data/rwat/wagon_types/plazkart.json`: длина 25.125, тележки ±8.5, 53 т, 120 км/ч, без traction/cab (первый чистый прицеп — живой тест «роли = способности»); (3) ассеты: `geo/plazkart.obj`, 4 свои карты (`body/bogue/interior/second_class`), сцепка и колёса переиспользуют общие IR-карты ЧМЭ3 (`couple.png`/`wheels.png` — mtl хочет `mvp_cargobogue2_map.png`, которой в ассетах нет); (4) `WagonRenderer` выбирает модель по id типа слота, кэш бейка по паре (модель-identity, свет), rigid-фолбэк пивотов — из типа слота; (5) дебаг-состав `/rwat spawn` = ЧМЭ3 + плацкарт (~46 блоков пути); cull-AABB вагона inflate 12→16 (полурама плацкарта 12.6). `SEAT_*`/`HIDE`-объекты в рендер не попадают; двери статичны (закрыты); FULLBRIGHT-объекты рисуются обычным светом (эмиссия — потом).

**Шаг 5 реализован 2026-06-11** (сборка + 4 теста парсера зелёные, в игре не проверено): реестр двухслойный — захардкоженный builtin (ЧМЭ3 — страховка для старых сейвов и незнакомых id) под датапак-слоем, который выигрывает при совпадении id. Сервер читает `data/<ns>/wagon_types/*.json` (`SimpleJsonResourceReloadListener`, id = расположение файла `<ns>:<имя>`, тело id не содержит — файл не может врать о своей идентичности; битый файл логируется и пропускается, не валит остальной пак) и шлёт слой клиентам через `WagonTypesPayload` на `OnDatapackSyncEvent` (вход в мир + `/reload`) — снапшоты несут только id, клиенту нужны сами декларации (length/bogies) для разворачивания позиций. Формат JSON 1:1 с §5.1 (`WagonTypeParser`, чистый GSON — юнит-тестируем без MC); мод сам везёт первый «пак»: `data/rwat/wagon_types/chme3.json` (неймспейс датапака не обязан совпадать с modid, id остаётся `rwat:chme3`). `DEBUG_CONSIST` → метод `debugConsist()` через `byId` — датапак-переопределение ЧМЭ3 реально применяется и на сервере при спавне. Известное ограничение: уже загруженные составы держат старые экземпляры типов до перезагрузки мира (слоты резолвятся при load/spawn); модель клиента всё ещё захардкожена (Chme3Model для всех id) — модель-паки это v2.


### 5.6 Профили физики сервера (решение 1.3, 2026-10-10)

**Запрос пользователя:** реализм и аркада — «каждому своё»; переменные — в конфиге, но **отдельные значения работают только в профиле `custom`**.

**Принцип:** пак описывает **настоящую машину** (реальные массы, силы, времена); насколько аркадно играет сервер — его конфиг, а не данные. Один и тот же пак годится и для аркадного, и для хардкорного сервера. Физика одна на весь сервер (составы общие, сцепляются между игроками, импульс должен сохраняться) — «каждому своё» для отдельного игрока делается ассистентами в кабине (удержание скорости, помощник остановки, прогноз тормозного пути — следующий шаг, им нужен HUD), а не физикой.

**Конфиг** — серверный (`ModConfig.Type.SERVER`): общий файл экземпляра `config/railswheelsandtrains-server.toml`, а копия в `<мир>/serverconfig/` переопределяет его для этого мира (правило NeoForge 1.21.1). Адаптер — `ServerConfig` (§7.3); физика видит только чистую запись `physics.PhysicsTuning`. Проверено на выделенном сервере (2026-10-10): файл создаётся со всеми комментариями.
```toml
[physics]
profile = "STANDARD"   # REALISTIC | STANDARD | ARCADE | CUSTOM
[physics.custom]        # читается ТОЛЬКО при profile = "CUSTOM"
traction_scale = 1.0          # множитель силы тяги
brake_scale = 1.4             # множитель всех тормозов (авто, вспомогательный, ручник)
resistance_scale = 1.0        # множитель сопротивления движению
response_scale = 0.5          # множитель времён набора тормоза/тяги; 0 = мгновенно
adhesion_limit = true         # потолок силы по сцеплению колёс с рельсом
adhesion_scale = 1.0          # состояние рельса (1 = сухой; задел под погоду)
auto_handbrake = true         # ручники ставятся/снимаются сами (§5.3)
hard_speed_limit = false      # жёсткий кап по самому медленному вагону
coupling_max_speed_kmh = 15.0 # быстрее — удар без сцепки (§6.12); 0 = сцепка на любой скорости
```
Значения `custom` по умолчанию — те же, что у `STANDARD`.

| | realistic | standard (по умолчанию) | arcade |
|---|---|---|---|
| тяга / тормоза / сопротивление | ×1 / ×1 / ×1 | ×1 / ×1.4 / ×1 | ×1.5 / ×2 / ×3 |
| время набора тормоза и тяги | ×1 | ×0.5 | мгновенно |
| сцепление колёс с рельсом | да | да | нет |
| ручники | вручную (монтировка) | сами | сами |
| предел скорости | допустимая | допустимая | жёсткий кап |
| сцепка | до 10 км/ч | до 15 км/ч | на любой скорости |

`standard` — настоящая физика с уступками масштабу Minecraft: дальность прорисовки 128–192 блока, а реалистичный тормозной путь пассажирского со 100 км/ч — 400–500 м (машинист не видит станцию, когда пора тормозить); реализм играбелен с приборами (прогноз тормозного пути, сигналы) — это задел. Множитель гравитации **отвергнут**: числа на HUD врали бы; крутые горки Minecraft честнее решать подсказкой уклона при постройке.

**Не сделано:** ассистенты машиниста (на игрока), прогноз тормозного пути на пульте, ЭДТ (нет ручки), повреждения при ударах.

## 6. Паки контента (решение 0.8, 2026-10-08)

**Зачем.** Подвижной состав переезжает из мода в паки: **мод — движок без контента, контент — паки**. Повод — порт Matoi Vanilla Pack (MVP, FrozeRain и др., IR-пак под 1.12.2, лицензия **CC BY-NC-ND 4.0**): ЧМЭ3 и плацкарт, жившие в jar (§2.4, §5), — это ассеты MVP, и они уходят из мода вместе со встроенным слоем реестра (§5.5 шаг 5). Закрывает пункт v2 «Модель-паки» и реализует §4 №2 («свой формат + офлайн-конвертер»).

### 6.1 Что такое RWAT-пак
Обычный пак Minecraft — **один каталог/zip служит и ресурс-паком, и датапаком**. Свой контейнер не изобретаем: MC уже даёт неймспейсы, наложение паков, перезагрузку (F3+T, `/reload`), загрузку текстур и синк датапака на клиент.

```
<Пак>/
  pack.mcmeta                          pack_format 34 + supported_formats [34, 48] (ресурсы и датапак 1.21.1)
  data/<ns>/wagon_types/<id>.json      сервер: физика/геометрия, §5.1 (+ aliases, §6.4)
  assets/<ns>/wagon_models/<id>.json   клиент: модель того же id (§6.3)
  assets/<ns>/lang/en_us.json          имена: wagon.<ns>.<id>
  assets/<ns>/…                        OBJ/MTL/PNG/.anim — где угодно, пути — в декларации
```
Неймспейс — пака, не мода (`mvp:chme3`). Сплит data/assets — штатный сервер/клиент из §5.1: серверу модели не нужны, клиент получает декларации типов синком (`WagonTypesPayload`).

### 6.2 Где лежат и как включаются
`<папка игры>/rwat_packs/` (zip или каталоги; `pack.RwatPacks`, `AddPackFindersEvent` для обоих `PackType`). Пак регистрируется **required** (`PackSelectionConfig(required=true, TOP)`): всегда включён, в меню ресурс-паков не выключается, датапак-половина подхватывается мирами автоматически, включая уже существующие (`PackSource.shouldAddAutomatically`). Пользователю: положил zip → перезапустил игру. Доп. каталоги — системное свойство `rwat.packDirs` (раны client2/server смотрят в общий `run/rwat_packs`, у основного клиента это и есть его `rwat_packs`).
- **Почему не в jar:** размер (MVP ≈ 160 МБ распакованным), лицензия (контент NC-ND живёт отдельно от кода, со своими LICENSE/Credits), независимые версии мода и паков.
- **Мультиплеер:** набор типов задаёт **сервер** (его `rwat_packs`); клиенту для моделей нужен тот же пак, без него вагоны — коробки по длине типа (§6.5). Раздача пака сервером — потом.

### 6.3 Декларация модели (`assets/<ns>/wagon_models/<id>.json`)
```json
{
  "obj": "stock/rolling_stock/passenger/mvp_ir_amendorf/mvp_ir_amendorf.obj",
  "bogies": [8.5, -8.5],
  "skip": ["WIPER_"],
  "animations": { "door1": "stock/…/anim/mvp_ir_amendorf_door1.anim" },
  "liveries": { "mvp_rzd": "l_mvp_rzd" }
}
```
- **Конвенция OBJ = конвенция IR** (§5.2): 1:1, Y вверх, ось хода X, **перёд — −X**, именованные объекты (`BOGEY_FRONT*`/`BOGEY_REAR*`, `*_WHEEL_n`, `INTERIOR*`…). Поэтому IR-ассеты ложатся в пак **байт-в-байт** — конвертируются только декларации. Пути без неймспейса — в неймспейсе пака.
- **Текстуры — из MTL** (`mtllib` → `map_Kd`, пути относительно OBJ, `../../common/…` работают; `MtlParser`). Ручная карта «материал → текстура» в коде ушла. Отсутствующий файл — лог + ванильная фиолетово-чёрная клетка (сигнал автору пака).
- `bogies` — где в OBJ стоят пивоты тележек (+вперёд); не задано → центр мешей рамы `BOGEY_*`. Кинематику по-прежнему ведут `bogies` **типа**.
- **Всегда пропускаются** `*HIDE*` и `CARGO_FILL*` (уровни груза 1…100 % лежат друг в друге; груз не моделируется — вагон рисуется пустым); `skip` добавляет свои префиксы. *С 2026-10-12 объекты `SEAT_*` рисуются, как в IR (там они — обычная геометрия модели): в MVP текстурированные `SEAT_` — подушки (кресла кабины и сиденья ДР1, раньше невидимые), а плоские метки мест без материала отпадают вместе с остальными частями без текстуры.*
- `animations` — группа → IR `.anim`; id группы сопоставляется с `id` двери типа без учёта регистра (`Door1` ↔ `door1`). Анимируются **только перечисленные** группы: каждый анимированный объект — отдельные draw call'ы (у ДР1 22 группы), поэтому конвертер пишет сюда лишь двери, объявленные в типе; остальные IR-анимации остаются статикой.
- `liveries` — ливрея → подпапка рядом с OBJ; текстура с тем же именем файла в подпапке заменяет базовую (семантика IR `tex_variants`).
- `handbrake` (1.3, 2026-10-10) — ключи органов (`["WIDGET_13", "WIDGET_14"]`), которые являются **маховиком ручного тормоза** этого вагона (§5.3): клик по нему затягивает/отпускает ручник вагона, маховик показывает состояние. В IR такого органа нет — у MVP маховик размечен как `WIDGET` с подписью «Hand Brake», и конвертер вписывает его ключ сам (2ТЭ116, М62 — по маховику в каждой кабине, ТГМ23). Свой пак может вместо этого назвать объект `HANDBRAKE_<n>` (наш вид органа) — тогда поле не нужно.

### 6.4 Декларация типа
§5.1 без изменений, плюс `"aliases": ["rwat:chme3"]` — старые id, которые тип забирает себе (миграция сейвов при переезде/переименовании). Только сервер: снапшоты несут уже разрешённые id. Алиас, совпадающий с реальным id или с чужим алиасом, отбрасывается с ошибкой в логе. С 2026-10-10 — необязательные `"couplers": {"front": …, "rear": …}`: где срабатывает сцепка относительно торца, + наружу (§6.12; конвертер переносит из IR).

**Значения по умолчанию — в движке (решение 1.3, 2026-10-10):** физика, которую пак не указал, берётся из `stock.StockDefaults`; **пропущенное поле = значение движка, явный `0` = ноль**. Раньше парсер ставил ноль: пак без `resistance` давал вагон без трения (катится вечно), без `brakes` — без тормозов; «умные» значения жили в конвертере, и автор пака с нуля об этом не знал. Теперь самый маленький вагон — `{ "length": 17.75, "bogies": [5.86, -5.86], "mass_t": 24.0 }`, остальное — по массе: Дэвис `a = 7·m + 200` Н, `b = 14`, `c = 1.3`, лоб `c_front = 5` (близко к российским нормам для роликовых подшипников на бесстыковом пути: плацкарт 53 т выбегает со 100 км/ч с ≈0.04 м/с²); тормоза — по системе (`passenger` по умолчанию, §5.3), вспомогательный 0.7 кН/т у вагонов с кабиной, ручник 0.4 кН/т; `traction.adhesion` = 1, `ramp_s` = 4. Новые поля: `resistance.c_front`, `traction.adhesion`/`ramp_s`, `brakes.system`/`apply_s`/`release_s`; `max_speed_kmh` — необязательно (§5.4). Парсер отказывает (с именем поля) на массе ≤ 0, отрицательных и бесконечных величинах, незнакомой тормозной системе.

### 6.5 Жизнь без пака
Встроенных типов в моде нет. Незнакомый id (пак удалён, типы ещё не синкнулись) → **заглушка с тем же id** (`WagonTypes.missing`: длина 20, тележки ±7, 40 т, без тяги/кабины, с тормозом — не укатится): id сохраняется в NBT, и вернувшийся пак восстанавливает состав. Клиент без модели рисует коробку `WagonModel`, растянутую на длину типа. Сейв из времён до композиций → по заглушке `rwat:legacy` на сохранённый вагон. `/rwat spawn` без паков — ошибка с подсказкой про `rwat_packs`.

### 6.6 Модели на клиенте
`WagonModelReloadListener` (`RegisterClientReloadListenersEvent`) читает только декларации; OBJ парсится **лениво** при первом появлении типа в кадре, в фоне (`StockModels`, поколение на каждую перезагрузку ресурсов — загрузка из старого поколения уходит в мусор). Причина: OBJ MVP — ~80 МБ текста; грузить всё на старте = секунды запуска и сотни МБ хипа под меши, которых игрок может не увидеть. Пока модель грузится, вагон не рисуется (доли секунды, раз на тип). F3+T сбрасывает декларации, модели и бейки.

### 6.7 Ливреи
`ConsistComposition.Slot` несёт `livery` (`""` = базовые текстуры): NBT `Livery`, снапшот. Сервер ливреи не знает и не проверяет (это клиентские данные модели); незнакомая ливрея рисуется базовой. Ливрея — те же меши, запечённые с другими текстурами: ключ бейк-кэша — (модель, ливрея, свет).

### 6.8 Конвертер IR → RWAT (`tools/ir2rwat.py`)
Python 3, только stdlib: `python tools/ir2rwat.py packs/<рецепт>.json [--out DIR] [--zip]`. Рецепт: неймспейс, источники (zip IR-паков по приоритету, у каждого свой корень), `exclude`, `overrides` (deep-merge поверх сгенерированного `type`/`model`, `null` удаляет поле), файлы корня для копирования (LICENSE/Credits/ReadMe/pack.png). Пишет пак-каталог (по умолчанию `run/rwat_packs/<пак>/`; чужой непустой каталог без маркера `RWAT_CONVERSION.txt` не перезаписывает) или zip.
- Ассеты копируются **без изменений** (OBJ, MTL, текстуры из MTL, папки ливрей, `.anim` дверей); генерируются только `wagon_types`, `wagon_models`, lang, `pack.mcmeta`, `RWAT_CONVERSION.txt` (откуда и что сконвертировано, права — у авторов). Lang — `en_us` из имён IR плюс языки, которые дали файлы типов (`"name"`, `"lights"`, §9.6).
- **Физика — только то, что знает IR (1.3):** `length` = протяжённость модели по X без `HIDE` (воспроизводит ручные 18.125/25.125); `bogies` = IR `trucks`; масса = `weight_kg`; `max_speed_kmh` — только если есть в IR (нет — не пишется, вагон поезд не ограничивает); тяга+кабина — категория `locomotives` (`horsepower`·0.7457 кВт, `tractive_effort_lbf`·0.00445 кН; без него — 0.33·m·g); `brakes.system` — `freight` для `freight`/`tank`, иначе `passenger`. Сопротивление, силы тормозов, ручник, сцепление, времена — **значения движка** (§6.4), те же, что у пака, написанного руками. ~~Эвристики Дэвиса и тормозов в конвертере~~ (a = 20·m, c = 9–12 на вагон, тормоз 2 кН/т…) удалены — ревью 2026-10-10 показало, что они завышали сопротивление в 5–10 раз и тормоза в 2–4 раза. Тюнинг — через `overrides`.
- Несколько источников: первый выигрывает, следующие добавляют только отсутствующие id; корни разные (`stock/`, `stock_17/`) → одноимённые общие текстуры разных версий не перетирают друг друга.

### 6.9 MVP (`packs/mvp.json`)
Источники: **MVP 1.8** (36 единиц) + из **MVP 1.7 bugfix** недостающие в 1.8 (9: `cargopolu`, `thermos`, `r200h`/`r200c`/`r200m`, `sr3h`/`sr3m`, `tep70`, `tgm4`) = **45 типов**, 500 файлов ассетов, без ошибок конвертации. ### 6.10 Стили рельсов (решение 0.9, 2026-10-09)
Рельс MVP (`mvp_ir_rail.obj` + `mvp_tracks_map.png`) тоже был ассетом пака и уехал из jar вслед за составом. Вместо одной захардкоженной модели — **стиль рельса на сегмент**, тем же механизмом паков:
- **Декларация** `assets/<ns>/rail_models/<id>.json`: `{ "obj": "…/rail.obj", "tile_length": 1.0 }` (путь без неймспейса — в неймспейсе пака). Конвенция тайла = IR-трек: блоки, Y вверх, рельсы вдоль **X**, тайл центрирован на x = 0, колея по Z; объекты `RAIL_LEFT`/`RAIL_RIGHT` (рельсы) и `RAIL_BASE` (шпалы/балласт/насыпь). Текстуры — из MTL, как у вагонов; несколько текстур на стиль допустимы (насыпь MVP: атлас рельсов + карта грунта) — меш на текстуру.
- **`tile_length`** (по умолчанию 1) — шаг повтора. Рельсовые объекты **растягиваются** на длину тайла, `RAIL_BASE` сохраняет размер и центрируется: насыпь MVP длиной 1.625 повторяется со своим шагом, не накладываясь сама на себя (при шаге 1 соседние куски z-файтились бы). У IR-нормы (рельс длиной 1, шаг 1) растяжения нет.
- **Встроенный стиль мода** `railswheelsandtrains:standard` — своя простая модель (`assets/railswheelsandtrains/rail/standard.obj` + MTL + текстура 32×32, генерируется скриптом): шпала + рельсы (подошва/шейка/головка). Головка на y = 0.40625, оси рельсов z = ±0.8125 — **как у MVP**: колёса вагонов MVP откалиброваны под эту высоту и колею (`Y_LIFT`, §2.4). Объявлен тем же JSON, что и пак-стили, — отдельного кода нет.
- **Сегмент хранит стиль** (`RailSegment.style`, NBT `Style`, синк в `RailGraphSyncPayload`); `""` = стиль мода — его же получают сегменты из старых сейвов. Сервер стили не проверяет (клиентские ресурсы, как ливреи), но с 2026-10-09 читает их тайлы для полотна (§2.2); клиент без пака рисует незнакомый стиль стандартным — путь не пропадает, сервер без стиля кладёт полотно стандартного.
- **Рендер:** шаблон тайла на (стиль, текстура), регион-бакет держит по GPU-мешу на текстуру (`RwatRenderTypes.rails(texture)` — тот же террейн-шейдер); ключ кэша сегмента включает стиль — смена стиля пересвипывает только этот сегмент. F3+T (`RailModelReloadListener`) перечитывает стили и сбрасывает кэш рендера. Тайлы рельсов мелкие (весь MVP — сотни КБ), поэтому грузятся сразу при перезагрузке ресурсов, а не лениво, как вагоны.
- **Перекраска:** Shift+ПКМ рельсами по полотну — вся конструкция (группа сегментов) получает стиль из предмета (полотно перекладывается под тайл нового стиля); `/rwat rail style <id|standard>` — вся сеть измерения (вернуть старым мирам вид MVP: `/rwat rail style mvp:rail`).
- **Конвертер:** `ir2rwat.py` переносит IR `track/*.json` в `rail_models/` (имя → `rail.<ns>.<id>`), модель берётся первая (IR ключует модели условием колеи). Рецепт: `rail_exclude`, `rail_overrides` (deep-merge в декларацию). MVP: 8 стилей — `rail`, `cncrtrail`, `ct_rail`, `cncrt_ct_rail`, `grunt_c`/`grunt_w` (насыпь, `tile_length` 1.625), `rail_bridge`, `crossbridge`. Исключены не-путевые «треки» IR, которые наш свип по тайлу не изобразит: буфер-упор, сигнал, датчик, опоры/провод/порталы КС, мостовые фермы (`bridge`, `bridge_end` — не центрированы, ~24 блока длиной), концевик контррельса, стрелочный тайл.
- **Не сделано:** роли объектов IR полностью (IR кладёт `RAIL_BASE` со своим шагом, а рельсы тянет по каждой нитке — мы свипаем тайл целиком с одним шагом), параметры пути в GUI (колея) — место в экране и в декларации оставлено; материал полотна — сделано 2026-10-10, §2.2. (Ширина полотна по стилю — сделано 2026-10-09, §2.2.)

### 6.11 Предметы: рельсы и подвижной состав (решение 0.9, 2026-10-09)
Сценарий пользователя: **взял в руку → ПКМ в воздух → выбрал модель → поставил**.
- **Рельсы** (`rail`): ПКМ в воздух — экран выбора стиля (`RailStyleScreen`: стиль мода первым, затем стили паков по id; под превью — подложка, §2.2; прочие параметры — позже). Имя предмета показывает стиль: «Рельсы (MVP Rail)».
- **Подвижной состав** (`rolling_stock`): ПКМ в воздух — экран (`StockPickerScreen`): слева типы, которые объявил **сервер** (синк `WagonTypesPayload`; длина, масса, кабина/тяга/салон), справа ливреи из пака модели **этого клиента**. Выбор — на стеке (`railswheelsandtrains:stock_selection` = тип + ливрея); сервер принимает только известный ему тип (алиас сводится к настоящему id), ливрею не проверяет. ПКМ по пути — вагон ставится **центром кузова в точку клика** на ближайшем сегменте (`RailGraph.nearestPoint`: грубый отбор 16 сэмплами + точный поиск до миллиметров; дотягивается на 2.5 блока от оси — всё полотно), **передом туда, куда смотрит игрок** вдоль пути (маршрут при надобности разворачивается: `TrackPathSpec.Route.inverted`). Отказы — сообщением: не на пути, путь короче вагона, место занято (зонды по оси нового вагона против корпусов стоящих рядом). Новый вагон = состав из одного; поезда собираются сцепкой (§6.12). В выживании предмет тратится, в креативе — нет.
- **3D-превью** (`client.gui.ModelPreview`, по идее пользователя): справа от списка — «поворотный стол» с выбранной моделью, оборот за 16 с, наклон камеры −22°. Вагон — кузов, двери в покое, тележки на пивотах типа, колёса, **в выбранной ливрее**; модель вагона грузится той же ленивой загрузкой `StockModels` (пока грузится — надпись «Загрузка модели…», клиент без модели — «нет модели»). Рельс — прямой отрезок из 7 тайлов стиля. Рисуется как сущность в инвентаре (entity-тип рендера через буфер GUI, освещение инвентаря, полная яркость), меши эмитятся с CPU каждый кадр — без запечки и GPU-буферов: для меню это единицы миллисекунд даже на самых тяжёлых моделях MVP.
- **Сеть:** `SelectRailStylePayload`, `SelectStockPayload` (C→S, сервер проверяет, что в руке нужный предмет). Экраны открываются только на логическом клиенте через `client.ClientItemScreens` — единственная дверь из общего кода предметов в клиентские классы.

### 6.12 Сцепка и расцепка (решение 0.9, 2026-10-09; сборка + 110 юнит-тестов зелёные, в игре не проверено)

**Зачем.** Составы были жёсткими призраками: проходили друг сквозь друга, а «многовагонный состав» существовал только как результат `/rwat spawn with …`. С предметом, ставящим на рельсы одиночный вагон (`ConsistManager.spawn`), поезд собирается по вагону — значит, нужна сцепка как механика (v1 roadmap: «сцепить/расцепить в игре, многовагонные составы»). Модель данных к этому готова с v0 (принцип №6): состав — список вагонов, `ConsistComposition` — список слотов.

**Решение: автосцепка при наезде + монтировка для расцепки + управление из любой кабины.**

- **Чистое ядро** `consist.Coupling` (без MC-импортов, тесты `CouplingTest`): «касаются ли два состава» и «во что они превращаются» решает оно; `ConsistManager` — тонкий адаптер (прикладывает план к составам и сущностям вагонов).
- **Один путь, а не близость в мире.** Два состава сравнимы, только когда оба выражены на **одном маршруте**: `Placement` переводит собственную координату состава в координату маршрута-кандидата (`σ = offset + dir·s`) и существует, только если **каждая нога**, на которой стоят его рамы, есть в этом маршруте (и все ноги дают одно и то же отображение). Пробуется маршрут сохраняемого состава, затем поглощаемого. Мировая близость — лишь дешёвый префильтр (хорда ≤ дуги): параллельные пути в 1.5 блока и стрелка, переведённая «против» второго состава (маршрут через неё не содержит его ног), не сцепляются — оба случая покрыты тестами (у остряка стрелки рамы двух вагонов на разных ветках стоят в мире ближе зазора сцепки).
- **Зазор сцепки = 0 (2026-10-10, по просьбе пользователя).** Между рамами сцеплённых вагонов был блок воздуха (`ConsistComposition.COUPLER_GAP = 1.0`, заглушка v0). Длина типа меряется по сцепкам — это габарит видимой модели вдоль пути, головки автосцепок в него входят, — поэтому теперь `COUPLER_GAP = 0`: вагоны стоят сцепка к сцепке. Остальное не меняется: контакт — зазор ≤ 0.05 (запас на округление) при сближении, гистерезис по скорости, расцепленные половины стоят вплотную и не сцепляются, пока их не толкнут. Старые сейвы: состав хранит голову и слоты, поэтому при загрузке каждый вагон подтягивается к голове на блок за каждую сцепку перед ним (разовый сдвиг). Тесты `CouplingTest` переписаны через `GAP`, а не через числа под старый зазор.
  - **Точка сцепки — из пака (в тот же день, по скриншоту из игры).** С нулевым зазором по габаритам между плацкартами оставался просвет: габарит модели задаёт головка автосцепки (у плацкарта z = 12.562 на высоте 1–2 блока), а гармошка перехода кончается на 12.437 — между гармошками 0.25 блока. В IR это решено смещением сцепки `couplers.front_offset/rear_offset` (−0.12 у плацкарта: головки заходят друг в друга, гармошки смыкаются). Теперь это данные типа: `"couplers": {"front": …, "rear": …}` — где сцепка срабатывает относительно торца рамы (±length/2), + наружу, по умолчанию 0 (`WagonType.Couplers`, `couplerReach`). Состав расставляется точка сцепки к точке (`Slot.frontCouplerReach/rearCouplerReach`, у развёрнутого вагона концы меняются), касание, сцепка, точка расцепки и прицел монтировки — по ним же. Синк в `WagonTypesPayload`.
  - **Конвертер** переносит IR-смещения (`derive_couplers`): IR отсчитывает их от габарита **всей** модели, со скрытыми объектами (у ВЛ80 сзади висит скрытый рукав — отсюда −0.661), а наша длина — видимый габарит; поэтому точка сцепки считается в терминах IR и пересчитывается к нашему торцу. У MVP: −0.12…−0.15 у большинства; у несимметричных моделей пересчёт заодно чинит торцы — 2ТЭ116 спереди +0.037/сзади −0.337 (видимая модель −9.44…+9.81 при «торцах» ±9.63), ВЛ80 −0.077/−0.192. Перегенерированы только декларации типов, остальной пак и сводки — байт в байт. Тесты: разбор `couplers` (`WagonTypeParserTest`), расстановка по точкам сцепки с развёрнутым вагоном (`ConsistKinematicsTest`), сцепка с перекрытием рам (`CouplingTest`).
- **Контакт.** На общем маршруте у каждого состава — пролёт рам (передняя грань рамы вагона 0 … задняя грань последнего). Сцепка, если зазор между обращёнными друг к другу гранями `≤ COUPLER_GAP + 0.05` (зазор сцеплённых вагонов + запас на округление), они **сближаются** быстрее `MIN_CLOSING_SPEED = 1e-3` бл/тик (≈0.07 км/ч) и перекрытие не глубже `MAX_OVERLAP = 4` блоков (за тик в лоб на максимальной скорости проезжается ≤ ~3.3; глубже — поставили друг на друга, такие остаются призраками). На кольце зазор меряется ближним путём, слишком длинная пара для кольца не сцепляется.
- **Гистерезис — по скорости, не по расстоянию.** Две половины сразу после расцепки стоят ровно на зазоре сцепки с равной скоростью — сближения нет, повторной сцепки нет; толкнули друг на друга — сцепились (тест «стоят врозь, пока не толкнули»). Порог по расстоянию («сначала разъехаться на N») ломал бы второе требование.
- **Порядок нового состава.** Маршрут ориентируется так, чтобы **сохраняемый** состав ехал в +s (при надобности берётся обращённый маршрут — `Coupling.inverted`, двойник `TrackPathSpec.Route.inverted()`): его рамка не разворачивается, рукоятки сохраняют смысл, вагоны не двигаются. Голова — впереди (по большему σ); поглощаемый состав, едущий против маршрута, входит в обратном порядке, у каждого вагона переключается `flipped`. `headS` пересчитывается от центра вагона 0 сохраняемого состава; поглощаемая сторона **снапится** ровно на `COUPLER_GAP` (видимый сдвиг ≤ перекрытие/недолёт — доли блока).
- **Скорость — абсолютно неупругий удар:** `v = (m₁v₁ + m₂v₂)/(m₁ + m₂)`, массы — `ConsistComposition.totalMassT()`, знаки — в рамке нового маршрута.
- **Кто выживает:** состав с машинистом, иначе тяжелее, иначе старший id. Поглощённый удаляется из менеджера (`remove` чистит и `consistsWithRiders`), всем сущностям вагонов проставляются id и индекс. Звук — `ANVIL_LAND` (тихо, высоко) у сомкнувшейся сцепки; машинисту — actionbar «Coupled · N wagons», машинисту, оставшемуся в «неведущей» кабине, — что управляет другая кабина.
- **Пассажиры остаются на борту** — они пассажиры сущностей вагонов, а те не меняются. Тонкость: у «развёрнутого» при сцепке вагона поворачивается рамка позы (yaw + 180°, `flipped` переключён — модель в мире стоит как стояла), а ноги ходячих пассажиров (`riderLocal`) живут в рамке позы — сервер их зеркалит (`WagonEntity.turnAround`), клиент зеркалит свой предикшн и вычитает 180° из «камера следует за вагоном» (`ClientWalkInput`), иначе пассажир прыгал бы в противоположный конец вагона, а взгляд крутился бы на 180°.
- **Только `TrackPathSpec.Route`** сцепляется (дебаг-прямая `Straight` — нет) и только тикающие составы (заглушка чанклоадинга: у замороженного дальние вагоны могут быть не загружены).

**Расцепка — монтировка** (`crowbar`, «Монтировка», `CrowbarItem`; рецепта нет — креатив/команды). ПКМ по сцепке между вагонами режет состав: вагоны `[0, cut)` остаются составом (id, маршрут, голова — никто не двигается), `[cut, n)` — новый состав на том же маршруте со своей головой (передняя тележка бывшего вагона `cut`) и той же скоростью (`Coupling.split`). **Рукоятки уходят с машинистом** (без машиниста — с передней частью, как в задании); вторая часть получает реверсор и тормоз, тяга — 0. Звук `CHAIN_BREAK`, actionbar «Uncoupled · a + b wagons».
- **Прицеливание — клиентское** (`ClientCouplerInteract`, по образцу дверей): пик-бокс сущности — кубик в центре, поэтому луч взгляда переводится в локальную рамку каждого ближнего вагона и тестируется (а) против бокса **зазора сцепки** на каждом сцеплённом торце (поперёк ±1.2, по высоте 0…2.4 от рельса, по длине — зазор + 0.75 в каждую раму), (б) против **корпуса**: попадание в пределах 2.5 блока от сцеплённого торца = эта сцепка. Ближайшее попадание; корпус перед ним (сквозь вагон) или ближний блок забирают клик. Работает раньше дверей (с монтировкой в руке сцепка у тамбура важнее двери), промах проваливается к дверям и к самому предмету (подсказка в actionbar). ПКМ монтировкой по вагону не сажает в него.
- **Сеть:** `UncouplePayload(wagonId, front)` — вагон и его торец, а не индекс в составе (не протухает, если состав перенумеровала сцепка «в полёте»). Сервер проверяет монтировку в руке и дистанцию от глаз до сцепки (reach + 3).
- **Дебаг:** `/rwat uncouple <id> <index>` — отрезать перед вагоном `index`.

**Управление из любой кабины.** Машинист = игрок, сидящий в **первой по индексу** кабине (`drivable()`) с сидящим игроком (`ConsistManager.driverOf`; ходячие пассажиры не машинисты); сесть можно в любую кабину со свободным местом. Вторая занятая кабина не управляет (ввод отбрасывается валидацией `DriveInputPayload`, при посадке — подсказка). **Реверсор — рукоятка в кабине:** «вперёд» = куда смотрит активная кабина. Состав хранит `cabFacing` (±1, куда вдоль пути смотрит активная кабина; NBT `CabFacing`), тяга идёт в сторону `reverser × cabFacing` — кабина во `flipped`-слоте при том же положении реверсора гонит поезд назад по пути. Смена активной кабины с другой ориентацией: на стоянке с закрытой тягой рукоятка просто читается из новой кабины («перешёл в другую кабину — вперёд туда, куда смотрю»); на ходу или под тягой реверсор перекидывается, чтобы поезд продолжал тянуть туда же. Старые сейвы: `cabFacing = +1` — прежнее поведение для неразвёрнутой головы.

**Клиент: состав не прыгает и не пропадает.**
- **Рамка `s`.** Буфер интерполяции хранит `s` в рамке маршрута; сцепка (новая голова) и **перепривязка** (`reanchor`, перенумерация маршрута — и раньше двигала `s`, клиент тогда ~2 тика интерполировал поперёк скачка и поезд проезжал по пути туда-обратно — этот старый дефект закрыт заодно) меняют смысл `s`. Сервер ведёт счётчик рамки и сдвиг `s_new = s_old + shift` (`Consist.shiftFrame`; несколько смен до отправки снапшота копятся в один сдвиг); снапшот несёт `frame/frameFrom/frameShift`. Клиент на `frame+1` сдвигает буфер, на пропуск рамки — сбрасывает буфер (короткая пауза, не проезд). Новый состав после расцепки помечен `frameFrom = id родителя`: клиент засевает его буфер и часы из родительских со сдвигом — отцепленная половина не «замирает» на время задержки.
- **Членство вагонов.** Синхронизируемые `DATA_CONSIST_ID/INDEX` приходят ванильным трекером на тик позже нашего снапшота (наш тик — после `chunkSource.tick` уровня): тик вагон ставился бы по старому индексу в новую композицию — на чужое место. Снапшот теперь несёт сетевые id сущностей вагонов по индексам; клиентский `WagonEntity.getConsistId/getWagonIndex` берёт их из новейшего снапшота (`ClientConsists.memberConsist/memberIndex`), синк сущности — фолбэк. Переключение атомарно с композицией.
- **Сервер авторитетен по членству:** каждый тик вагонам состава переутверждаются id и индекс (no-op, если совпадают); проверка сироты раз в 100 тиков ищет владельца по UUID (`ownerOf`), а не по сохранённому id — вагон, пролежавший сцепку в выгруженном чанке, при загрузке чинится, а не удаляется.
- **Синк пассажиров:** пассажир принадлежит составу, который перечислил его последним (`ClientRiderSync`, передача владения); сервер шлёт все непустые списки тика раньше финальных «последний вышел» — пассажир, уехавший с отцепленной половиной, не стирается пустым пакетом старого состава, а запись поглощённого состава не висит в кэше. Тесты в `ClientRiderSyncTest`.

**Статус:** реализовано, `compileJava` + 110 юнит-тестов зелёные (новые: `CouplingTest` ×13 — тождество/зеркало размещения, неупругий удар и неподвижность сохраняемого, нет сцепки без сближения/вдали/при равной скорости, гистерезис после расцепки, расцепка без сдвига вагонов, поглощаемый против маршрута — обратный порядок и разворот, обращённый маршрут для сохраняемого, стрелка против, параллельные пути, шов кольца, то же кольцо, пройденное с другого сегмента (смещения сходятся по модулю круга), глубокое перекрытие; `ClientRiderSyncTest` +3). **В игре не проверено.**

**Удары и ручник (решение 1.3, 2026-10-10):**
- **Скорость сцепки** — из профиля (`coupling_max_speed_kmh`, §5.6: 10 / 15 / любая). Быстрее — **удар без сцепки** (`Coupling.Bump`): импульс сохраняется, буфера возвращают `RESTITUTION = 0.3` скорости сближения — составы расходятся; перекрытие разводится до касания, каждый сдвигается на долю массы другого (лёгкий отлетает больше). Звук удара (громче на скорости), машинистам — «Удар! Слишком быстро для сцепки · сцепляйте плавно, до N км/ч». Подъехал плавно — сцепился.
- **Пролёт насквозь закрыт:** контакт засчитывается при перекрытии до `MAX_OVERLAP + скорость сближения` (за тик глубже, чем на скорость сближения, не въехать), префильтр в мире — тоже с учётом скоростей. Раньше гарантия была только до ~363 км/ч сближения, а в паке есть 160 и 200 км/ч.
- **Конец пути:** по-прежнему остановка за тик (рельс кончился — путь не продолжить), но со звуком удара при скорости выше 2 км/ч.
- **Ручник монтировкой:** ПКМ по кузову вне торцевых зон сцепки — ручник этого вагона (сцепка у торца — как раньше, расцепка); `HandbrakePayload`, сервер проверяет монтировку и досягаемость. С монтировкой в руке дверь кликом по кузову не открыть (она — инструмент сцепок и ручников), изнутри вагона — как раньше.

**Не сделано / осознанно:** продольная динамика сцепок (набегание, растяжка — анти-скоуп §5.4: состав жёсткий), повреждения при ударах и о конец пути (удар без сцепки — есть, 1.3), отказ сцепки по типу (у всех типов сцепка совместима), «сцепка на скорости ломает» — нет; рецепт монтировки; управление «из второй кабины» (два машиниста — правит передний); торможение отцепленной части (в жизни разрыв магистрали даёт экстренное — у нас отцепленная часть просто сохраняет кран); перевод `flipped`-развёрнутого интерьера с асимметричным `interior` (у всех нынешних типов интерьер симметричен, и до сцепки это уже было ограничением `flipped`).

## 7. Переносимость: новые версии MC и Fabric (оценка 2026-10-09)

**Зачем.** Перед светом и кабинами (§8–§9) — оценка, во что обойдётся переезд на новые версии Minecraft и, возможно, на Fabric, чтобы новый код писался так, чтобы порт был дешёвым. Развивает принцип №4 и пункт v2+ «Порт на NeoForge 26.x».

**Вывод.** Дорогая часть любого порта — **наш собственный рендер-слой** (`GpuMesh`/`Batch`, `RailRenderer` с приёмом тумана через `ChunkOffset` террейн-шейдера, `RwatRenderTypes`), он переписывается при переходе на 1.21.5+ **независимо** от новых фич. Чистое ядро (путь, кинематика, физика, сцепка, ходьба, коллизия, парсеры) переезжает как есть. Свет и кабины добавляют к цене порта по одному тонкому адаптеру на точку касания; совместимость с LambDynamicLights — почти ноль.

### 7.1 Что меняется в MC после 1.21.1 и что из этого задевает нас
| Версия | Изменение | Нас касается |
|---|---|---|
| 1.21.2 | `EntityRenderState`: рендерер больше не получает сущность, всё нужное копируется в состояние до рендера | `WagonRenderer` читает сущность (двери, поза, слот) → собирать плоский «снимок» в начале `render()` уже сейчас |
| 1.21.5–1.21.6 | Переделка Blaze3D: `RenderPipeline`, `GpuDevice`/`GpuBuffer`/`RenderPass`; `ShaderInstance`/`drawWithShader`/`CoreShaders` уходят; GUI переведён на render state (1.21.6) | `GpuMesh`, `RwatRenderTypes`, `RailRenderer` — переписываются; экраны (`StockPickerScreen`, `ModelPreview`) — правятся |
| 1.21.9 | Сущности рисуются через submit (`SubmitNodeCollector`); 1.21.11 — `submitCustomGeometry` | Отрисовка вагона = «отправить запечённые меши», адаптер в одном месте |
| 26.1 | Игра без обфускации (оба загрузчика на именах Mojang, Yarn снят), Java 25, большие изменения API NeoForge (пример из чужого мода: 1.21.1 → 26.1.2 ≈ 645 ошибок компиляции) | Все 16 файлов с импортами NeoForge, миксины — сверить цели |
| 26.2 | Бэкенд Vulkan (экспериментальный, по умолчанию OpenGL); ломаются прямые вызовы GL | У нас прямого GL нет — всё через Blaze3D |
| 26.3 | Формат вершин сущности по-прежнему несёт `UV2` (лайтмап), `sample_lightmap.glsl` на месте | Свет, запечённый в вершины (§8), переживает все версии как идея |

### 7.2 Fabric
- ~40 из 82 классов — чистое ядро без загрузчика; NeoForge напрямую трогают 16: подписки на события, `DeferredRegister`, регистрация пакетов, перезагрузка/синк датапака, `shouldRiderSit` (метод NeoForge — на Fabric станет миксином). Миксины работают на обоих загрузчиках.
- С 26.1 оба загрузчика на именах Mojang → схема «общий модуль + тонкие модули neoforge/fabric» становится естественной.
- **Решение:** Fabric сейчас **не делаем** (двойная цена на каждом шаге, а 1.21.1 → 26.x всё равно переписывает рендер). Разделение на модули — в момент порта на 26.x.

### 7.3 Правила для нового кода (действуют с §8–§9)
1. Логика — в чистых пакетах с юнит-тестами (как `kinematics`): разбор групп из имён объектов, позиции ламп, поле света, геометрия конуса фары, разметка органов управления, раскладка кабины.
2. Рендерер собирает **плоский снимок** в начале `render()` (маска света, свет мира, поза, двери, положения рукояток) и дальше сущность не читает — это и есть будущий `EntityRenderState`.
3. Точки касания API рендера — только `RwatRenderTypes` (светящийся тип) и бейк `GpuMesh` (свет вершины — функция, а не одно число).
4. Всё загрузчико-зависимое (пакет, экран, клавиша, совместимость с LambDynamicLights) — по одному классу-адаптеру; совместимость — в пакете `compat`, загружается только при наличии мода.
5. Пакет `platform` заглушками заранее **не** наполняется (принцип №4): интерфейсы появляются вместе с реальной второй точкой вызова (Fabric).

## 8. Свет: салон, фары, ореол, луч (решение 1.0, 2026-10-09)

**Решение пользователя:** салон и кабина светятся от своих ламп; снаружи — свечение ламп + ореол (flare) + луч фары; LambDynamicLights (LDL) — опциональная поддержка, если мод установлен; включение — пока из меню машиниста (клавиша), плюс тумблеры в кабине (§9), раз они есть в ассетах.

**Данные — из имён объектов (конвенция IR, §5.2), без JSON:**
- `_LCG_<группа>` — объект горит, когда включена **группа управления** `<группа>` (`LINVERT` — наоборот); `FULLBRIGHT` — при включённой группе светится в полную яркость; `HEADLIGHT_<n>` — фара (ореол + луч), `_0X<RRGGBB>` — её цвет (ЧМЭ3: `HEADLIGHT_1_0XFFF0CC_FULLBRIGHT_LCG_FHL`).
- **Лампа салона** = связный остров меша (по общим вершинам) у `FULLBRIGHT`-объекта; позиция — центр острова. Координаты ламп в JSON не нужны.
- Группы MVP: плацкарт `IL`; ЧМЭ3 `FHL/RHL` (прожекторы), `FBL/RBL` (буферные), `FEL/REL` (хвостовые красные — `WIDGET_17/18_HIDE_INVERT_FULLBRIGHT`), `NL` (логотип), `BgL` (подсветка тележек), `IL` (кабина + подсветка приборов).

**Состояние — группы управления вагона** (`WagonEntity`, `SynchedEntityData` с `CompoundTag` «имя → 0..1», NBT `Controls`). Это одно хранилище и для света, и для тумблеров/окон кабины (§9): тумблер `WIDGET_6_TOGGLE_CG_FHL` и фара `…_LCG_FHL` смотрят в одну ячейку, как в IR. Сервер имён групп не знает и не проверяет (это данные модели клиента) — только ограничивает число (64) и длину имени (32). По умолчанию всё выключено.

**Рендер (клиент):**
- **Запечка учитывает свет:** ключ бейка = (модель, ливрея, свет мира, **маска включённых групп модели**). `FULLBRIGHT`-объекты включённых групп — `FULL_BRIGHT`; объекты с токеном `INTERIOR` получают блочный свет `max(свет мира, поле ламп)`: от каждой включённой лампы `15 − расстояние`, только если поверхность смотрит на лампу (нормаль · направление на лампу > 0 — наружные стены и крыша от ламп салона не светятся). Объект с `LCG` своей включённой группы, но без ламп рядом — не темнее 11 (как «interior light» IR). Переключение света = один перебейк (бюджет «1 бейк за кадр» сохраняется).
- **Пассажиры и рука в первом лице** освещаются полем ламп своего вагона: клиентский миксин на `EntityRenderer.getPackedLightCoords` (рука берёт свет из того же метода через `EntityRenderDispatcher`).
- **Ореол, луч и свет на пути** (`LampEffects`, переделано 2026-10-09 по замечанию «луч примитивный, с шейдером пропадает на фоне неба») — каждый кадр из мягких пятен (веер, прозрачность вершин падает от центра к краю ≈ по Гауссу), своим `RenderType` (`POSITION_COLOR`, аддитивное смешивание, тест глубины без записи): ореол — пятна к камере у линзы (ядро + гало, растёт при взгляде в фару); **луч** — объёмный конус 16 блоков из пятен к камере вдоль оси, каждое шириной с конус в этом месте, шаг — доля ширины: складываются как свет, рассеянный вдоль луча зрения, поэтому луч виден с любой стороны, в т. ч. из кабины вдоль оси (плоская полоса там пропадала); тускнеет с расширением и к концу; **свет на пути** — длинное мягкое пятно над головками рельсов впереди фары. Днём и под фонарями гаснет.
- **Когда рисуется:** пятна копятся в проходе сущностей, рисуются позже. Ванилла — после полупрозрачных блоков и частиц (`AFTER_PARTICLES`). **С шейдерпаком (Iris)** — после всего уровня (`AFTER_LEVEL`), поверх готового кадра пака, с тестом глубины: внутри уровня всё идёт через программы пака, и с Photon ломалось всё — небо (композит после непрозрачных проходов) закрашивало свет, нарисованный с сущностями; текстурный свет отсекался по альфе < 0.1 и смешивался обычной альфой (чёрные квадраты); вершинный — жёсткие «звёзды». И в проходе теней Iris рисует сущности ещё раз «глазами солнца» — пятна оттуда были бы полосами: в нём ничего не копится (`compat.IrisCompat`, API Iris через reflection, без зависимости).
- **LambDynamicLights (опционально):** пакет `compat`, загружается только при наличии мода; каждая включённая лампа/фара — `DynamicLightBehavior` (лампы салона — точка, фара — несколько точек по оси луча). API одинаков в 1.21.1 … 26.3 на обоих загрузчиках (§7).
- **Меню машиниста** (клавиша `L`, за пультом — §9.7; с 2026-10-10 это правая половина пульта машиниста): список групп света состава; переключение — на все вагоны состава (`ControlGroupPayload`, только из управляющей кабины). **Имена групп** (`client.LightNames`, то же — в подписи над тумблером, §9.3): ключ пака **для этого типа** `light.<ns>.<тип>.<группа>` (пишет конвертер из `"lights"` файла типа, §9.6 — у разных моделей одни и те же коды значат разное: `HL`, `IL`, `CL`…), иначе общий ключ мода `light.railswheelsandtrains.<группа>`, иначе `_LABEL_` тумблера модели, иначе сама группа.
- **Свет остальных моделей MVP** (проверено 2026-10-09, автосцена `er2`, Photon): разметки не требует — конвенции IR в моделях 1.8 полные (у каждой группы `LCG` есть светящиеся `FULLBRIGHT`-объекты, `INTERIOR`-детали и тумблер `CG_<группа>`). ЭР2 ночью: салон освещён лампами, окна светятся, у головного — прожектор с лучом и пятном на пути, буферные огни. Чего нет у паков: человеческих имён групп (у ДР1, ВЛ80 тумблеры без `_LABEL_` — в меню «CCL», «HBL») — это работа для агентов (`"lights"`). Модели MVP 1.7 (`r200*`, `sr3*`, `tep70`, `tgm4`) — один меш без объектов, света в них нет. Суффикс копии Blender (`DOOR_3_INTERIOR_LCG_IL.001`) отбрасывается при разборе имени — такие детали светятся со своей группой.

**Не сделано (осознанно):** питание (IR гасит свет без «электричества»), мигание, `FORWARD/REVERSE`-фары по направлению хода, освещение мира без LDL (свет на пути — только видимость пятна, блоки не освещаются).

**Проверено в игре (2026-10-09, автосцена `beam`, Photon и без шейдеров):** ночью у ЧМЭ3 виден мягкий конус луча, в т. ч. на фоне неба; путь впереди подсвечен пятном; ореол мягкий; кабину и капот ничего не перекрывает (тест глубины работает и после кадра Iris). Замечание пользователя «с шейдерами капот светился» — от фонаря в руке (ручное освещение Photon), не от мода.

**Статус (2026-10-09):** реализовано, `compileJava` + юнит-тесты зелёные. Код: теги света квадов (`StockModel.tag`: группа, `FULLBRIGHT`, `INTERIOR`, `LINVERT`), острова ламп (`LampIslands`, мельче 0.12 блока — не лампа: подсветка приборов), фары (`StockModel.Headlight`), запечка со светом по вершине (`BakedStockModel.light`, ключ кэша + маска групп), `LampEffects` (ореол/луч, `RwatRenderTypes.lightGlow`), пассажиры — `EntityRendererCabinLightMixin` + `CabinLight`, меню — `TrainLightsScreen` (клавиша `L`, `ClientLightsKey`; с §9.7 — пульт машиниста `DriverPanelScreen`, `ClientPanelKey`), LDL — `compat.LambDynLightsCompat` (интерфейсы LDL реализованы через `java.lang.reflect.Proxy`: **без зависимости при компиляции** — публичный maven LDL отдаёт API с Fabric-именами; точка входа — `[[modproperties.<modid>."yumi:entrypoints"."lambdynlights:initializer"]]` в `neoforge.mods.toml`, так LDL на NeoForge ищет инициализаторы через Yumi). Правило «какие лампы светят внутрь»: лампа группы, которой подписан хоть один `INTERIOR`-объект (ЧМЭ3/плацкарт: `INTERIOR_1_LCG_IL`) — буферные/тележечные лампы наружу не «просачиваются». Отладка: `/rwat control <группа> <0..1>`, `/rwat handle <рукоятка> <значение>` (ближайший состав), сценарий скриншотов `-Pautoscene=cab` (`debug.ClientAutoScene`). **Проверено в игре (2026-10-09, автосцена `cab`, с шейдерпаком Photon и без):** ночью горят прожектор с ореолом, буферные огни, подсветка тележек и номеров, в окнах кабины виден свет салона, кабина изнутри освещена лампами, приборы подсвечены. По ходу исправлено: (1) порог острова-лампы 0.12 → **0.3** (в лампы попадала подсветка пульта ЧМЭ3 — 15 «ламп» вместо 3); (2) луч — не конус (грани при сложении давали яркие полосы по силуэту), а **полоса-билборд вдоль оси** с градиентом от оси к краям и к концу; (3) рычаги стояли в покое, пока ни одна кабина не управляла — теперь «активная» по умолчанию первая кабина состава. Замечание: Photon заметно высветляет поверхности вблизи камеры (капот с мостика ночью) — освещение оценивать и без шейдеров. Не проверено: LambDynamicLights (мод не установлен в dev-окружении).

## 9. Кабины локомотивов (решение 1.0, 2026-10-09)

**Зачем.** Машинист сидел «в центре локомотива» на ванильном месте, управлял клавишами. Пользователь: ходьба в локомотиве как в пассажирском вагоне + управление элементами кабины мышью (IR-стиль).

### 9.1 Пол из зон, внутренние двери, проёмы
Кабина ЧМЭ3 — не салон-коробка: кабина у заднего конца, двери в **торцевых** стенах выходят на **мостики** вдоль капотов, на площадки по концам рамы поднимаются по угловым **подножкам**. Поэтому:
- `interior` может быть **списком зон** (`[{min,max}, …]`, старая форма — один бокс — остаётся): ходить можно, пока тело игрока (квадрат 0.6) целиком на полу. *С решения 1.4 (§9.8):* пол — **объединение** зон, ужатое на полуширину игрока; зоны, которые касаются, — один пол, перекрывать их не нужно (раньше требовалось перекрытие ≥ 0.6, у каждой зоны своё ужатие); щель любой ширины — стена. Шаг с пола — скольжение вдоль стены (кламп на ближайший кусок пола рядом).
- Дверь `"inner": true` — **внутренняя** (между зонами): закрытая — стена, открытая — «мостик» через проём (центр в пролёте минус 0.1 с краёв). В корпусе проёма не режет.
- Дверь `"fixed": true` — **проём без створки** (подножка): всегда открыт, не кликается, не рисуется; как наружная дверь — вход с земли через проём в корпусе, выход — шаг за край площадки.
- `doorsOnly` — есть хотя бы одна наружная дверь/проём.

### 9.2 Машинист
- В **ходимой** кабине (`cab` + `interior`) все на борту — у пульта: рычаги берут мышь. Машинист состава — игрок в первой по индексу занятой кабине (в кресле — приоритетнее, §6.12 расширен). *С §9.7 (2026-10-10): машинист — только тот, кто в кресле; ходящий по кабине переключает тумблеры, но рукоятки не двигает.*
- **Кресла машиниста** `cab.seats` — список `{"at": [x,y,z], "yaw": градусы}` (верх подушки; `yaw` 0 — вперёд, 180 — к другому концу; *до 2026-10-12 — одно кресло `cab.seat` `[x,y,z]` + `seat_yaw`, эта запись читается и теперь*): ПКМ по свободному креслу — сесть (поза сидя, взгляд к пульту), W/S/A/D/пробел управляют как раньше; Shift — встать. Сидит только тот, кто в кресле (клиентский миксин на `LivingEntityRenderer` спрашивает вагон о конкретном пассажире). Тело сидящего — к пульту, взгляд — не дальше **±105°** от направления кресла (как в ванильной лодке; `WagonEntity.clampSeatedLook` в `onPassengerTurned` и `positionRider`) — голова больше не крутится на 360°.
- Кабина **без** `interior` (остальные 40+ локомотивов MVP, пока им не размечены полы) — по-старому: ванильное место, клавиши.

**Несколько кресел (2026-10-12).** Решение пользователя: водительских кресел может быть несколько — «удобно, если в кабине два места или вагон двухсторонний».
- Водительское — каждое кресло списка: машиниста и помощника в одной кабине, кресла кабины на другом конце.
- В каждом кресле сидит свой игрок (`WagonEntity` `DATA_SEATED` — id сидящих по номеру кресла, пакет `SeatPayload` несёт номер). Поезд ведёт, как и раньше, первая по индексу занятая кабина, а в одном вагоне — первое по списку занятое кресло.
- Кресло лицом назад (больше 90° от «вперёд») ведёт в обратную сторону: «вперёд» реверсора — куда смотрит кресло (`ConsistManager.Driver.facing`), дальше обычная смена кабины (`Consist.takeControl`). Кресло боком считается смотрящим вперёд.
- Встать — значит дойти шагами от места, откуда садился, до кресла, пока пускает пол (`RiderWalk.toward`, клиент предсказывает то же место). Раньше игрок вставал на ближайший пол у кресла. Кресло помощника стоит сбоку от пульта, пола под ним нет, и ближайший пол может оказаться за стенкой: у правого кресла СР3 это тамбур за задней стенкой кабины. Теперь игрок встаёт рядом с креслом в той же кабине.
- Рукоятки одни на состав, поэтому рычаги пульта на другом конце показывают то же положение. Держать рычаги неактивного поста в покое — не сделано.
- MVP: кресла замерены по подушкам моделей. Второе кресло есть у всех 16 типов с кабиной. У М62 и ЧС4Т добавлены ещё оба кресла задней кабины; её пол и двери размечены зеркально передней, у каждой кабины свои подножки. У маневровых (ТЭМ2, ТЭМ2у, ТГМ23, ЧМЭ3) второе кресло стоит у второго поста и смотрит назад. Кресла помощника ЭР2, Р200, ДГКу и ДР1 повёрнуты к пульту (53°, 29°, 60° и 70°), у ТГМ4 — боком (90°). Подушки кресел у СР3 одинаковые, поэтому оба кресла водительские.
- **Проверено в игре** (2026-10-12) автосценой `stock` на 14 типах. Сцена теперь сажает игрока в каждое кресло по очереди и пишет в лог, ведёт ли кресло поезд и куда.
  - Сели во все 32 кресла, все ведут поезд.
  - У задних кабин и вторых постов `facing −1`, и направление кабины состава (`cabFacing`) следует за креслом.
  - Вставший оказывается у своего кресла; у СР3 с правого кресла — в кабине, а не в тамбуре.
  - Из каждого кресла виден свой пульт и окно.

### 9.3 Органы управления (конвенция IR, чистый разбор `convention.ObjectRole`)
- Рычаги: `THROTTLE_n`, `REVERSER_n`, `TRAIN_BRAKE_n`, `(INDEPENDENT|IND)_BRAKE_n` → рукоятки состава; тумблеры/кнопки/окна/кресла: `WIDGET_n`, `WINDOW_n`, `HORN/WHISTLE/BELL_CONTROL_n`, `ENGINE_START_n` → группа управления вагона (`_CG_<имя>`, иначе сам ключ); приборы: `GAUGE_SPEED/THROTTLE/REVERSER/TRAIN_BRAKE/IND_BRAKE_n`, `BRAKE_PRESSURE_n` (остальные — в покое). **Тормозные манометры (1.3)** — `GAUGE_TRAIN_BRAKE`, `GAUGE_IND_BRAKE`, `BRAKE_PRESSURE` (у MVP подписаны «Brake Pipe», «Brake Cylinders», «Equalizing Reservoir») — показывают **давление, а не кран**: долю тормоза в действии, которая догоняет рукоятку со временем наполнения (§5.3); снапшот несёт её байтом на контур. `BRAKE_PRESSURE` — большее из двух. **Маховик ручного тормоза (1.3)** — наш вид `HANDBRAKE` (`HANDBRAKE_<n>` или поле `handbrake` декларации модели, §6.3): клик шлёт `HandbrakePayload` (без перетаскивания; сервер проверяет досягаемость), положение — анимация к ручнику вагона из снапшота; подпись — «Ручной тормоз: затянут/отпущен». Работает и тот, кто ходит по кабине (как тумблеры). **Проверено в игре (2026-10-10, автосцена `-Pautoscene=handbrake`, М62, профиль `realistic`):** новый локомотив стоит на ручнике, маховик `WIDGET_13` в положении «затянут»; под прицелом — «Ручной тормоз: затянут»; клик отпускает ручник, маховик за 1.5 с доворачивается в «отпущен» (подпись сразу говорит «отпущен» — по состоянию, а не по анимации); кран машиниста на 8 — давление на манометре и полоса на пульте растут 0.07 → 0.38 → 0.59 → 0.80 → 0.96 за 4 с (пассажирский тормоз).
- Шарнир — объект `<ключ>_ROT_<градусы>`: центр bbox — ось вращения, направление оси — длинная ось «стержня» (правило UMC: две самые далёкие вершины → центроиды половин); поворот = значение × градусы. `TL_<f>_<ось>` — сдвиг на значение × f. Флаги `TOGGLE`/`PRESS`/`INVERT`/`HIDE`/`NOTOUCH`, `_OFFSET_`, `_RANGE_min_max`, `_LABEL_` — как в IR. Значение реверсора: 0 назад … ½ нейтраль … 1 вперёд (IR вычитает ½ — модель нарисована в нейтрали).
- Рукоятки синкаются в снапшоте состава (`Handles`: реверсор −1/0/+1 — **нейтраль добавлена**, тяга, автотормоз, **вспомогательный тормоз** — теперь управляемый, + индекс активной кабины; рычаги остальных кабин — в покое).
- **Мышь:** ПКМ по органу (луч в кадре вагона против bbox органа в текущем положении, ≤ 3 блоков; *с 2026-10-10* — не сквозь стены модели: пульт, перегородку, корпус, как у дверей, §3 v1.5 «Двери»): тумблер — переключается, кнопка — нажата, пока держишь; рычаг — **тянется, пока держишь**: значение = точка хода, ближайшая к лучу взгляда на дистанции захвата; рукоятки — по ближайшему нотчу (`CabLeverPayload`, сервер: только из управляющей кабины), остальное — `ControlGroupPayload` (на борту или в досягаемости). Луч берётся **на конец тика** (глаз и взгляд при partialTick = 1 — момент позы сущности вагона): клики и перетаскивание работают в тике, а глаз, интерполированный к кадру, против позы тика уводил точку на ход поезда за тик — на ходу рычаг дёргался между нотчами (замечание пользователя). Орган, внутри коробки которого глаз (кресло, в котором сидишь — ЧМЭ3 `WIDGET_4`), не выбирается — иначе кресло перехватывало клики по тумблерам.
- **Наведение:** орган под прицелом (или в руке) обведён рамкой своего bbox (двигается вместе с ним), под прицелом — подпись (`ClientCabHud`, слой GUI над прицелом): имя (группа света → `light.railswheelsandtrains.<группа>`, иначе `_LABEL_` модели, иначе вид органа) и положение — «Контроллер · 5 / 8», «Реверсор · вперёд», «Прожектор передний · вкл»; у кресла — «ПКМ — сесть». Actionbar при работе органом больше не нужен.

### 9.4 ЧМЭ3 (рецепт `packs/mvp.json`)
Замеры по мешу (модель-спейс, пол = настил рамы 2.311): кабина x ±1.44, z −5.5…−3.625; мостики |x| 0.875…1.625 вдоль капотов; площадки на концах рамы во всю ширину; двери `door1` (задняя стенка, −X) и `door2` (передняя стенка, +X) — внутренние, с IR-анимацией `Door1/Door2`; подножки — 4 проёма по углам; кресло — `WIDGET_4` (x −1.062, z −4.654, подушка 3.09), лицом вперёд.

**Не сделано:** ~~звуки органов, гудок~~ (рукоятки, тифон и свисток — §10; тумблеры — нет); поворот кресла; второй пост ЧМЭ3 (`IND_BRAKE_2`) — работает только вспомогательный тормоз (кресло у поста есть с 2026-10-12); сиденья пассажиров `SEAT_*`; полы остальных локомотивов; IR-анимации по группам управления (`WIDGET` с `.anim`: двери купе/туалета плацкарта `CG_DoorKupe`… кликаются, но не двигаются); колёсико мыши по органам.

**Статус (2026-10-09):** реализовано, `compileJava` + юнит-тесты зелёные (новые: `CabFloorTest` — зоны ЧМЭ3, закрытая/открытая внутренняя дверь, мостик ↔ площадка, капот — стена, выход через подножку без открытия, развёрнутый пол, посадка с земли на ближайший пол; `ObjectRoleTest`, `ControlValueTest`, `PivotAxisTest` — в т.ч. на настоящих шарнирах ЧМЭ3 из сгенерированного пака; `WagonTypeParserTest` +2). Отладка: `-Pautoscene=walk`.

Не проверено: само ощущение перетаскивания на ходу (сцены двигают рычаг пакетами, не мышью).

### 9.5 Переходы между вагонами (решение 1.1, 2026-10-09)

**Зачем.** Пользователь: «система переходов между вагонами через тамбур». IR делает это дверями `DOOR_n_CONNECTING` — они уже есть в моделях MVP (плацкарт `DOOR_5/6_..._CONNECTING_CG_Trap1/2` — торцевые двери тамбуров, ЭР2, ДР1, БМЗ, рефсекция).
- Дверь типа `"connecting": true` — **переходная**: в торцевой стене (ось Z). Открытая — шаг сквозь неё (тот же `RiderWalk.exitDoor`, что у наружных) переносит игрока **в сцепленного соседа** с этого конца (передняя, +Z, стена → вагон `index − 1`, задняя → `index + 1`) через его переходную дверь в стене, обращённой назад, — ближайшую к месту игрока поперёк вагона. Позы соседей смотрят в одну сторону, поэтому X игрока сохраняется (в пределах пролёта двери); точка — сразу за внутренней гранью двери (`RiderWalk.gangwayArrival`, чисто). ~~Дверь соседа открывается сама («открыл, проходя»)~~ — *с 2026-10-10 (замечание пользователя: проходил сквозь закрытую, а она распахивалась за спиной):* **закрытая дверь соседа — стена**; её открывают сами — кликом через свою открытую переходную дверь (`ClientDoorInteract`: игрок в вагоне выбирает и переходные двери соседних; если луч идёт сквозь свою открытую переходную дверь в закрытую соседа — клик её; по двум открытым — закрывает свою).
- Соседа нет (конец состава, расцеплено) или у него нет переходной двери навстречу — дверь как стена: из поезда между вагонами не выпасть.
- С земли через переходную дверь не войти: она не режет корпус (`Door.external()` — только наружные), `doorsOnly` её не учитывает.
- Перенос — на сервере (`WagonEntity.passGangway`: санкционированный выход из вагона в точку прибытия + посадка в соседа на эту локальную точку). Клиенту — `RiderPlacePayload` («теперь ты идёшь по вагону N, здесь»): предсказание шага по новому вагону начинается с неё, а не с мировой позиции, которую сдвинула ванильная высадка; `ClientWalkInput` при смене вагона сбрасывает прошлые ступни, рыскание и флаг разворота.
- Двери анимируются IR-анимацией своей группы: id двери ↔ группа `.anim` **без учёта регистра** (автодвери берут id из `CG_` с регистром модели — `Trap1`; рендер сравнивал с учётом — двери не открывались, исправлено).
- **Створки, которые IR двигает по имени** (решение 1.2, 2026-10-09): `DOOR_<n>_ROT_<градусы>` (шарнир — тонкий «стержень», как у органов управления §9.3) и `TL_<f>_<ось>` (сдвиг) — у ЭР2 (раздвижные боковые и тамбурные, переходные на шарнире), ДГКу, ТГМ23. Загрузчик собирает такую створку как орган управления (`ObjectRole.door`, `StockModel.doorLeaves`: все объекты `DOOR_<n>`, флаги — с любого из них, как в IR), а двигает её открытость двери типа, **в коробке которой (с запасом 0.1) центр створки** (`WagonType.doorHolding`) — без сопоставления имён, поэтому и дверь, объявленная автором вручную, подхватывает свою створку. `DOOR_<n>` без `ROT/TL` и без `.anim` — часть кузова, как раньше.
- **Группы дверей**: `"group": "<имя>"` у двери — двери одной группы открываются и закрываются вместе (`WagonEntity.setDoorOpen`, звук у каждой). Так в IR: все двери одной группы управления работают разом (левая сторона ЭР2 `DrL`, ДР1 `DL`), и одна IR-анимация может двигать створки нескольких проёмов (у ДР1 анимация `DL` двигает обе левые двери). Конвертер ставит `group`, когда одна `CG_` у нескольких проёмов.

**Проверено в игре (2026-10-09, автосцена `er2`: головной + моторный ЭР2, Photon):** клик по левой двери моторного — открываются оба левых проёма (группа), створки каждого разъезжаются; изнутри — раздвижные двери тамбура разъехались, переходная дверь распахнулась на шарнире; маска дверей у сервера `1100011`. Тесты: `ObjectRoleTest` (створки читаются только как двери, суффикс `.001`), `RecipeDoorsAndLightsTest` (каждая движущаяся створка — в коробке своей двери; створка с `.anim` — у двери, названной по группе анимации, или в её группе; `doorHolding`, `groupedWith`).

**Статус:** реализовано, тесты `GangwayTest` (дверь ведёт наружу только открытой, мимо пролёта — стена, прибытие у двери соседа, в пролёте, у развёрнутого соседа — через его другой конец, нет двери — нет перехода). **Проверено в игре (автосцена `gangway`, два плацкарта):** с земли в задний вагон через боковую дверь → к торцу → упор в закрытую переходную дверь (z 11.45) → открыта → в переднем вагоне у его задней двери (z −11.16), та открылась сама (до 2026-10-10; теперь её открывают кликом, см. выше) → дальше по вагону → обратно в задний. Видно и ограничение: пол плацкарта — одна коробка, по вагону идёшь сквозь полки (зоны коридора/тамбуров — §9.6, работа для паков).

### 9.6 Ходимый состав в паках: что выводится само, что размечает автор (решение 1.1, 2026-10-09)

**Вопрос пользователя:** что делать с остальными вагонами со стороны паков, как сделать создание паков удобным. Ответ — максимум брать из конвенций IR, остальное мерить инструментами и проверять автоматически.

**Выводится конвертером** (`tools/ir2rwat.py`, если рецепт не задал своё):
- **Пол пассажирского вагона** — *с шага 2 (§9.8):* генератор `tools/floorgen.py` по треугольникам модели (сетка 1/16, препятствия в слое тела игрока, зазор 0.1, достижимое от дверей) → список коробок. Прежний вывод — одной зоной из IR-блока `"passenger"` (`center_x` вдоль вагона, `length` — **половина** длины, `width` — полная ширина, `center_y` + 0.1 = пол RWAT) — остался запасным, если генератор не нашёл пола. Свой `type.interior` в файле типа главнее. Локомотивам — только если в файле типа есть ключ `"floor"` (кабине нужно ещё кресло — вручную).
- **Двери** — из объектов модели `DOOR_<n>`: `EXTERNAL` — вход/выход, `CONNECTING` — переход (§9.5), остальные (IR `INTERNAL`) — **внутренние** (`"inner": true`; внутри одной зоны пола не мешают ходьбе, но открываются и двигаются — тамбурные двери ЭР2, ДР1, БМЗ). Коробка — bbox всех объектов двери, id = группа `CG_<имя>` (тогда её IR-анимация открывает дверь; слово-флаг вместо группы, `CG_NOINTERACT`, — не группа), иначе `door_<n>`. **Две створки одного проёма** (одна группа, одна стена, сходятся вдоль неё — раздвижные пары ЭР2) — одна дверь; проёмы на одной группе получают `"group"` (§9.5). Маркеры и ручки меньше проёма (высота < 1.2 или ширина < 0.3, `DOOR_2_CONNECTING` 2ТЭ116) — не двери. Порядок — по `DOOR_<n>`. К ним дописываются **двери из `WIDGET_<n>`** (§9.8). Только для типов с полом. `"doors": []` в рецепте выключает; `"doors": {"<id>": {…} | null}` правит выведенные по id (§9.8).
- **Имена**: файл типа может нести `"name": {"ru_ru": "…"}` (имя состава) и `"lights": {"<группа>": {"en_us": "…", "ru_ru": "…"}}` (имена групп света в меню машиниста, §8) — конвертер пишет их в lang-файлы пака (`wagon.<ns>.<тип>`, `light.<ns>.<тип>.<группа>`) и предупреждает о группе, которой нет в модели. Пример — `chme3.json`, `amendorf.json`.
- Итог по MVP: ходимы 11 пассажирских типов (у 7 — переходные двери), ЧМЭ3 — ручная разметка.

**Размечает автор** — `packs/<рецепт>/<id>.json` (по файлу на тип, deep-merge поверх выведенного; `null` удаляет поле): пол из нескольких зон (коридор, тамбуры, кабина, мостики), внутренние двери между зонами, проёмы, кресла машиниста (`cab.seats`), исправления выведенного. *Решение 1.4 (§9.8): пол IR-паков будет выводить генератор, автор — писать исключения.*

**Инструменты:**
- `python tools/objinfo.py <тип> [--controls] [--grep RE] [--floors --x a b --z a b] [--doors] [--lights]` — габариты объектов в осях RWAT, уровни пола (площадь горизонтальных поверхностей по высоте), двери, которые выведет конвертер, группы света модели.
- `python tools/ir2rwat.py packs/mvp.json --geometry packs/mvp/geometry` — **сводки геометрии** по типам (только числа: bbox объектов, уровни пола, IR-зона пассажиров, выведенные пол и двери, `door_motion` — как движется створка каждой `DOOR_<n>`: `anim`/`rot`/`slide`/`none`, `animations` — группы IR-анимаций и их объекты, `lights` — группы света: светящиеся объекты, фары, сколько деталей салона светит, тумблеры).
- **Репозиторий (2026-10-09, по решению пользователя, временно):** для облачных агентов в репозиторий добавлены zip MVP (корень), сгенерированный пак (`run/rwat_packs/MatoiVanillaPack`) и сводки — всё, что нужно, чтобы мерить, перегенерировать и гонять `PackFloorTest` без локальных файлов. Контент — CC BY-NC-ND, его авторов; потом убрать (из истории — переписыванием).
- `kinematics.FloorCheck` — проверка разметки так, как её прочтёт `RiderWalk` (с §9.8 — по объединению зон): игрок не помещается нигде на полу или ни в одном месте зоны; часть пола, до которой не дойти ни от зоны 0, ни от своего входа (зоны должны касаться, их соединяет внутренняя дверь, или у части своя наружная дверь либо проём — *с 2026-10-12, для задней кабины двухкабинного локомотива*); наружная или переходная дверь не там, где кончается пол (перед ней, в пролёте, пол должен кончаться не дальше 0.4 от её внутренней грани) — сквозь неё не выйти; переходная не в торце; кабина с полом, но без кресла (клавиши ведут поезд только из кресла); кресло, к которому не подойти: ближайшее место, где стоит игрок, дальше 2.5 (досягаемость посадки) или подушка не на 0.2…1.5 выше пола там. *До 2026-10-12 кресло должно было стоять над зоной пола. Кресло помощника сбоку от пульта над полом не стоит, а вставание теперь ведёт к креслу шагами (§9.2), так что пол под креслом не нужен.* Пишет предупреждения в лог при загрузке типов; тесты `RecipeFloorTest` (по сводкам + файлам рецепта, без IR-паков) и `PackFloorTest` (по сгенерированному паку, если он есть) — по тесту на тип.
- В игре: `/rwatc floors` (клиентская команда) — каркасы зон (зелёные; ярко — где может стоять центр игрока), дверей (голубые — наружные, жёлтые — внутренние, пурпурные — переходные, серые — проёмы) и кресла (красное).
- Временные заглушки (2026-10-09, чтобы `FloorCheck` был зелёным): `amendorf_baggage` — пол как у плацкарта (багажные двери в середине вне IR-зоны), `bmz_diesel` — пол продлён до задней переходной двери. Проверить в игре.

**Инструкция для агентов** (облачных, по разметке остальных типов): `docs/agents/walkable-stock.md`.

**Не сделано:** сиденья пассажиров `SEAT_*`; грузовые вагоны не ходимы; тумблер дверей в кабине (`WIDGET_8_…_CG_DrL_GLOBAL` ЭР2, ДР1 `DL`/`DR`) не открывает двери группы — двери открываются кликом; IR-анимации органов управления, не дверей (окна, козырьки ДР1). ~~Двери с `ROT_`/`TL_` рисуются закрытыми~~ — сделано (§9.5); ~~`INTERNAL`-двери не выводятся~~ — выводятся.

### 9.7 Пульт машиниста: приборы на экране и меню света (решение 1.2, 2026-10-10)

**Запрос пользователя:** GUI машиниста — тяга, тормоз, реверс, скорость; вместе с меню света. Actionbar «`[F] Тяга 3/8 · Тормоз 0/8 · 12 км/ч`» (§5.5, шаг 4) был временной заменой HUD кабины.

**Кто видит пульт — по креслу, а не по классу вагона** (вопрос пользователя: делить ли вагоны на пассажирские и тяговые, а смешанные — по креслу машиниста?). Делить не нужно: роли вагона — возможности (§5.1), а не класс: `traction`, `cab`, `interior` встречаются в любых сочетаниях (бустер ЧМЭ3 — тяга без кабины, головной ЭР2 — кабина с салоном, ДР1 — всё сразу). Правило одно для всех: пульт видит тот, кто **за пультом** (`ClientDriveInput.atControls`) — ровно тогда, когда клавиши W/S/A/D управляют поездом: в кабине без ходимого салона — просто находясь в ней (ванильное место), в ходимой кабине — **только в кресле машиниста** (`cab.seats`, любом из них, §9.2). Пассажир в салоне головного вагона электрички пульта не видит. **Сервер — по тому же правилу** (решение пользователя, 2026-10-10): машинист состава (`ConsistManager.driverOf`) — игрок за пультом первой по индексу кабины; ходящий по кабине машинистом не бывает, даже если кресло пусто. Рукоятки (`CabLeverPayload` — рычаг мышью или клик в пульте), клавиши (`DriveInputPayload`) и свет на весь поезд принимаются только от самого машиниста — не от второго игрока в той же кабине. Ходящий по кабине ЧМЭ3 переключает тумблеры, окна и прочее (группы вагона, §9.3), а рычаги рукояток на клиенте не берутся: под прицелом — имя, положение и «Только из кресла машиниста». Ходимая кабина без кресла не водится вовсе — `FloorCheck` такую разметку и не пропускает.

**Что показывает** (`client.gui.DriverPanel`, одинаково в HUD и в экране; данные — чистый `convention.DriverReadout` с юнит-тестами, из снапшота состава, §2.1):
- **скорость** крупными цифрами (км/ч, `TrainPhysics.kmh`) и стрелка направления движения **относительно своей кабины** (▲ — туда, куда смотрит кабина, ▼ — назад; кабина во флипнутом слоте смотрит к −s) — видно, что состав откатывается на уклоне;
- **спидометр-полоса** до шкалы = допустимая скорость состава (самый медленный вагон; жёсткий кап — только в аркадном профиле, §5.6), округлённая вверх до 20 км/ч, засечки через 10/20/40 км/ч, красная метка — максимальная скорость; у предела — жёлтая, на пределе — красная;
- **реверсор** — три ячейки «Н · 0 · В» (en: R · N · F), горит выставленная;
- **тяга, тормоз, вспомогательный тормоз** — ряды из 8 «ламп» (нотчи 0–8) и цифра; ряд вспомогательного — только если у кабин состава он есть (`independent_kn > 0`);
- «Управляют из другой кабины», если рукоятки выставлены не из этой кабины (`Handles.activeCab`);
- «Ручники N/M» (жёлтым), пока у состава затянут хоть один ручник (1.3, §5.3; снапшот несёт маску ручников по индексам вагонов);
- под лампами тормоза и вспомогательного тормоза — тонкая полоса **давления** (тормоз в действии, 1.3): видно, как тормоз догоняет кран.

**HUD** (`ClientDriverHud`, слой GUI над хотбаром): правый нижний угол; рядом с хотбаром, если экран достаточно широк, иначе над полосками здоровья/голода. Скрывается по F1 и пока открыт пульт. Выключается кнопкой в пульте — настройка клиента `driverHud` (`config/railswheelsandtrains-client.toml`, адаптер `client.ClientConfig`, §7.3); с выключенным HUD движение рукоятки снова пишется в actionbar — но уже клиентом из снапшота, сервер больше ничего не шлёт.

**Пульт машиниста** (`DriverPanelScreen`, клавиша `L` за пультом; раньше — «меню света»; `L` — и ванильная клавиша достижений, а ванилла разбирает клавиши раньше: меню света с клавиатуры открывало достижения. Теперь `ClientPanelKey` читает клавишу в начале тика, за пультом забирает нажатие и гасит клик достижений на той же клавише; вне кабины `L` — по-прежнему достижения): слева приборы — **они же органы управления**: клик по лампе — нотч, клик по подписи ряда — 0, колёсико — ±1, клик по ячейке реверсора — реверс (только на стоянке при нулевой тяге, иначе подсказка); пакет — тот же `CabLeverPayload`, что у рычагов в кабине (§9.3), сервер принимает только из управляющей кабины. Так у **всех** локомотивов появилось управление вспомогательным тормозом, которого нет на клавишах. Справа — группы света (§8): на кнопке имя и лампа (горит — группа включена) вместо «: выкл», чтобы длинные имена помещались; одинаковые имена разных групп (у ЧС4Т два «Head Light» — тумблеры модели без имён в паке) различаются кодом группы; колонки подстраиваются под размер окна. Внизу — «Приборы на экране: вкл/выкл» и «Готово». Фон — лёгкое затемнение без размытия: поезд едет, путь впереди виден. Пульт закрывается сам, если игрок встал из кресла или вышел.

**Проверено в игре (2026-10-10, в облаке: Xvfb + Mesa, без шейдеров):** автосцена `-Pautoscene=panel` (`debug.ClientAutoScene`) — ЧС4Т с плацкартом, игрок в кабине, разгон на 5-м нотче в окне 1920×1080: HUD при автомасштабе GUI (4) стоит справа от хотбара, при масштабе 2 — тоже; пульт, наведение на 6-ю лампу тяги (рамка + подсказка «Контроллер: 6 / 8»), клик — сервер перевёл тягу 5 → 6; наведение на реверсор на ходу — без рамки, с подсказкой «Только на стоянке при нулевой тяге». ### 9.8 Пол — сетка проходимости (решение 1.4, 2026-10-10)

**Откуда:** разметка группы A (плацкарт, багажный) показала, что прямоугольные зоны дороги: салон — один меш, проходы косые, правила зон держатся в голове автора. Предложение — `docs/proposals/pack-markup.md`, вопросы и ответы — `docs/proposals/pack-markup-questions.md`.

**Решение пользователя:** будут **собственные паки RWAT**, не только конвертация IR. Поэтому формат пола выбирается под автора, который рисует пол в Blender:
- **Снаружи — фигуры пола с высотой:** прямоугольник (нынешняя зона `interior`, §9.1, без изменений) или многоугольник. Откуда берутся:
  - свой пак — объекты `FLOOR_n` и кресло `SEAT_DRIVER` в модели; мод читает их сам при загрузке, на сервере тоже (как OBJ рельсов для насыпи, §6.10);
  - IR-пак — генератор в `tools/`: сетка проходимости по треугольникам модели → фигуры. Исключения автор пишет в файле типа, это вход генератора; допуск узких проходов (коридор плацкарта 0.53 при игроке 0.6) — параметр генератора;
  - руками — зоны в файле типа.
- **Внутри движка — объединение фигур, ужатое на полуширину игрока**; нигде не хранится, строится при загрузке. Перекрытия зон не нужны: соседние фигуры сливаются, щель любой ширины — стена. Ловушки бокового шага и торца у переходной двери исчезают, `FloorCheck` теряет их правила. Чего так не выразить: двух полов друг над другом (под точкой берётся самая высокая зона) — в MVP таких нет.
- **Двери — по id:** состояние в сохранениях и правка в файле типа (`"doors": {"<id>": {…}}` дописывает или правит одну дверь, `null` удаляет). Старые сохранения — без миграции: забывается только, какие двери были открыты.
- **Внутренние двери из `WIDGET`** дверного размера с `TOGGLE` и `.anim` своей группы (плацкарт: `CG_DoorTambur`, `CG_DoorToilet`, `CG_DoorKupe`) выводит конвертер; лишнюю отключают по id.

**Порядок работ:**
1. Сетка в движке и двери по id; разметка ЧМЭ3 и плацкарта — без правки.
2. Генератор; сверка с ручной разметкой плацкарта.
3. Проверка в игре: узкий коридор, косой проход, дверь-виджет против органа управления (`ClientCabInteract`: клик забирает орган — группа переключается, дверь нет?).
4. Инструкция агентам, группы B–D (до шагов 1–2 их не запускаем).
5. `FLOOR_n` / `SEAT_DRIVER` — к первому своему паку.
6. Редактор пола в игре — решить после генератора; если делать, пишет только в исходники `packs/<рецепт>/<id>.json`.

**Шаг 1 сделан (2026-10-10).** Вместо растра — **точное** объединение (`stock.FloorRegion`): пол режется на полосы вдоль Z по краям зон, у каждой полосы — интервалы X; где помещается центр, хранится кусками-прямоугольниками (полосы между краями ± 0.3 и сами края — для зоны шириной ровно 0.6). Растр 1/16 блока давал бы ±3 см у стен и зону 0.6–0.65 то проходимой, то нет — в зависимости от того, как легла сетка; точное объединение отвечает так же, как прежние зоны, а многоугольники (`FLOOR_n`, генератор) придут прямоугольниками-строками. Как теперь:
- `WagonType.Interior` — класс (был record): `fits`, `region`, `clampFeet` (ближайшая точка, где игрок помещается), `floorAt` (самая высокая зона под центром, если помещается); зеркало для развёрнутого вагона и область строятся один раз.
- `RiderWalk.step` — шаг с пола скользит: кламп шага на каждый кусок области в пределах 0.3 от игрока, берётся дающий больше продвижения (прежний кламп в зону + «мягкий шаг» в соседнюю — частный случай), **но не дальше конца шага** (запас `AHEAD_SLACK` 1 см). Замечание пользователя: по коридору плацкарта шёл рывками — кусок пола впереди (вход в отсек) тянул игрока до 0.3 вперёд за тик (0.27 вместо 0.12, тест `theAisleAlongTheBays_isWalkedAtAnEvenPace`); без запаса в 1 см застревал на шаге из тамбура в косой проход (боковой сдвиг при чуть косом шаге выходит на 1 мм дальше). Мостики открытых внутренних дверей — как были.
- `RiderWalk.exitDoor` — стена двери — то, докуда игрок дойдёт **по прямой к двери** (`FloorRegion.reach`), а не грань любой зоны, где он стоит; запас `DOOR_WALL_SLACK` 0.6 → **0.4** (в MVP торцы пола от дверей — −0.09…0.35). Ловушка плацкарта (зона косого прохода, кончающаяся у торца, выводила в соседний вагон раньше тамбура) ушла — тест `FloorUnionTest`.
- `FloorCheck` — связность по кускам области (+ мостики внутренних дверей), «зона, в которой игрок не помещается нигде», двери — по тому же правилу выхода.
- `/rwatc floors` — ярко-зелёным рисует саму область (куски), а не каждую зону, ужатую отдельно.
- Двери по id: в мир пишется список id открытых (`OpenDoors`), старая маска `Doors` не читается (двери закрыты); пока тип вагона неизвестен — список хранится и пишется обратно. Конвертер: `"doors"` объектом в файле типа правит выведенные по id (`edit_doors`; `RecipeFloorTest` повторяет это правило); `amendorf.json` и `amendorf_baggage.json` переписаны так — вместо 9 и 11 дверей по 3 внутренних, пак перегенерирован байт в байт.
- Тесты: все прежние без правки чисел (позиции у стен — до 1e-6) + `FloorRegionTest`, `FloorUnionTest` (зоны, которые только касаются, проходимы; щель — стена; выход там, где кончается пол; дверь не у края пола — в отчёте `FloorCheck`; узкая зона рядом с широкой — не ошибка).

**Проверено в игре (2026-10-10, автосцены, регрессия — не шаг 3):** `walk` (ЧМЭ3, с Iris/Photon) — как в §9.4: подножка → площадка, мостик до закрытой двери кабины (упор на z −3.14 — край мостика), открыта — в проход у пульта, стоя рычаг не берётся, в кресле — тяга 5. `gangway` (два плацкарта с разметкой группы A, без модов) — посадка, к торцу, **переход в передний вагон** (его задняя дверь тогда ещё открывалась сама — до исправления ниже), там упор в закрытую тамбурную дверь, обратно — в задний вагон и по коридору. Со старым движком та же сцена в соседа не проходила: к торцу игрок выходил у x −0.6 из косого прохода — мимо пролёта переходной двери (±0.34). Посадка в сцене была нестабильна у обоих движков (через 10 тиков в проёме игрок шёл дальше, а сервер ещё не собрал состав — в логе «type ?») — не регрессия; сцена исправлена ниже. Ощущения (узкий коридор, косой проход, дверь-виджет) — шаг 3.

**Прогулка пользователя (2026-10-10) и исправления:** (1) рывки по коридору — см. `RiderWalk.step` выше; (2) переход сквозь закрытую дверь соседа — теперь стена, открывается кликом (§9.5). Автосцена `gangway` переписана под это: ждёт в проёме, пока сервер посадит (гонка «type ?» ушла), к торцу, своя дверь — пакетом, упор в закрытую соседа, **настоящий клик** правой кнопкой (`KeyMapping.click`, через `ClientDoorInteract`) по ней сквозь свою открытую, переход, упор в тамбурную дверь переднего, обратно — по косому проходу в коридор заднего; снимок каркасов вдоль коридора. **Проверено (с модами dev-окружения):** все шаги, в т. ч. клик открыл дверь соседа (`doors=100000`), без клика — стена.

**Клик по дверям и органам (2026-10-10, замечания пользователя):** клик берёт створку там, где она нарисована, и не проходит сквозь стены модели (§3 v1.5 «Двери», §9.3). **Вопрос 7** (дверь-виджет против органа): у плацкарта не мешает — объект, который двигает IR-анимация объявленной двери (`WIDGET_3_…_CG_DoorTambur`), загрузчик делает деталью двери, а не органом (`IrStockModel`: `track != null` → не control). Остаётся: тумблер дверей кабины (`CG_DrL_GLOBAL` ЭР2, ДР1 `DL`/`DR`) не открывает двери группы. Автосцена `-Pautoscene=doorclick` (плацкарт, все клики — настоящие, `KeyMapping.click`; сцена ждёт, пока тип вагона дойдёт до клиента): с земли по `Door4` — открылась; из тамбура по двери туалета за перегородкой — закрыта (стена); по тамбурной — открылась; в пустое место её закрытой створки у дальнего косяка — открыта; по открытой створке, где она нарисована, — закрылась. Снимок `rwat-doorclick-open-leaf.png`.

**Шаг 2 сделан (2026-10-10): генератор пола `tools/floorgen.py`.** Конвертер зовёт его для каждого пассажирского типа (и локомотива с ключом `"floor"` в файле типа), если в файле нет своего `type.interior`; в сводку геометрии (`derived.interior`, `derived.floor`) пол попадает для всех, в том числе размеченных вручную (`RecipeFloorTest` читает файл типа первым). Только стандартная библиотека, ~3 с на тип, вся конвертация ~1.5 мин.
- **Алгоритм** (подробно — докстринг модуля):
  1. Уровень пола — самый большой «смотрящий вверх» уровень рядом с IR `center_y + 0.1` (иначе самый большой в нижней части модели; `"level"` в файле типа). Поверхность на 0.15 ниже уровня и на 0.04 выше тоже пол (порожки ДР1).
  2. Клетка 1/16: пол — центр клетки под верхней гранью на уровне; препятствие — любой треугольник в слое тела `уровень + 0.3 … + 1.8`, все клетки его проекции (консервативно). Объекты с `HIDE` пропускаются (IR рисует их только по команде группы, это не стены); `"ignore"` — ещё по имени. Закрытые створки `DOOR_n` и дверей-виджетов — препятствия, двери соединяет мостик.
  3. **Зазор** `clearance` 0.1 (решение пользователя): прогон препятствий вдоль X и вдоль Z отдаёт до `round(0.1/клетка)` = 2 клеток свободной клетке на конце, но не последнюю — тонкая стена остаётся стеной (движок читает щель любой ширины как стену).
  4. Достижимость — **правилом движка**: порт `FloorRegion` (куски, где помещается центр), семена — наружные/переходные двери (`walkableThrough`), соединяют внутренние двери (мостики). Что недостижимо (шкафы без дверей, площадка под рамой снаружи) — отбрасывается; без дверей в модели — остаётся наибольший кусок. Пол тянется до внутренней грани наружной двери вдоль её пролёта, если там ничего не стоит и разрыв ≤ 0.7 (у ДР1 пол кончается в 0.47 от двери, ступени ниже).
  5. Свободные клетки → прямоугольники (лучшее из «столбцов» и «строк»); коробка, в которой не помещается игрок (`FloorCheck`: «holds no place a player fits»), заменяется коробками размером с тело вокруг кусков, что её покрывают (то же объединение). Координаты кратны 1/16, пишутся в 4 знака (3 дали бы 0.062).
- **Исключения** — вход генератора, ключ верхнего уровня файла `packs/<рецепт>/<id>.json` (не внутри `"type"`): `"floor": {"clearance", "level", "add", "remove", "ignore", "slab", "cell", "step_down"}` (все необязательны; `"floor": {}` включает генератор локомотиву; `"floor": false` — выключает). `add`/`remove` — коробки `{min, max}` (x, z; y выбирает уровень), `add` — до проверки достижимости (так чинят косой проход).
- **Двери из `WIDGET`** (`ir2rwat.widget_doors`): `WIDGET_<n>` высотой > 1.2, тонкий (≤ 0.35), шириной ≥ 0.3, с флагом `TOGGLE` (не `HIDE`), группа `CG_<имя>` которого имеет IR-анимацию → `{"id": "<имя>", "inner": true}` в bbox всех объектов `WIDGET_<n>` (с ручками); дописываются после `DOOR_n`; лишнюю убирают `"doors": {"<id>": null}`. У MVP — только плацкарт (и багажный): `DoorKupe`, `DoorToilet`, `DoorTambur`, коробки в точности как у ручной разметки группы A. У ЧМЭ3 (`Cable`, `HIDE`), БМЗ (`SME*`, ниже 1.2) не находятся.
- **Инструмент:** `python -I tools/floorgen.py packs/mvp.json <тип> [--ascii] [--png ФАЙЛ] [--compare] [--z a b] [--clearance …]` — карта «пол / препятствие / где помещается центр / двери» (PNG пишет zlib+struct; класть вне репозитория); `--compare` — с ручным `interior` файла типа (площади, разность, связные части, достижимость дверей).
- **Сверка с ручным плацкартом** (центральная область, где помещается тело, `amendorf`, зазор 0.1): генератор 5.79 м², рука 4.20, общая 2.98; только генератор 2.81, только рука 1.22. Что отличается:
  - *Коридор шире:* рука — 0.65 (центр в полосе 0.05), генератор — 0.75 (0.15): зазор 0.1 + консервативная растеризация (+до клетки). Это почти вся «лишняя» площадь (~2 м² на 20 м коридора); с зазором 1/16 генератор даёт 2.55 м² (общая 1.93, только рука 2.27: коридор не везде проходим) — шаг зазора грубый, 2 клетки = 0.125.
  - *Косой проход* у переднего тамбура (только рука, ~0.6 м²): диагональные стенки — лесенка прогонов по 2 клетки, зазор их не трогает, а квадрат 0.6 в диагональной полосе 0.5 не умещается; передний тамбур (0.72 м², двери `Door1`, `Door2`, `Trap1`) остаётся отдельной частью. Три коробки `add` (зоны 14–16 ручной разметки) соединяют всё в одну часть (только рука 0.56, общая 3.64). У багажного (нет прохода) совпадение 91 % (35.3 из 37.0 м²), тот же отдельный тамбур — его косой проход.
  - *Туалет и купе:* комнаты за `DoorToilet`/`DoorKupe` у генератора мельче ручных зон (причина не разбиралась: мебель в слое тела).
  - Те же 6 наружных/переходных дверей проходимы и у руки, и у генератора; внутренние двери стыкуют те же части.
  - Ручной `interior` `amendorf` и `amendorf_baggage` **не заменён** — решает пользователь.
- **По типам** (коробок / где помещается центр, м² / `FloorCheck` в `RecipeFloorTest` и `PackFloorTest`): `bmz_diesel` 153/10.5 (в паке — ручная заглушка), `dr1a_trailed` 42/12.5, `er2m`, `er2m_reversed`, `er2t` 54/10.2, `r200c`, `r200m` 43/6.2, `sr3m` 28/12.1 (у моделей MVP 1.7 нет объектов: дверей нет, остаётся наибольший кусок) — все зелёные. Внутренние двери из `WIDGET` — только у плацкарта.

**Шаг 3, сгенерированный пол в игре (2026-10-10, автосцены `-Pautoscene=walkgen` — ЭР2 моторный + прицепной, `walkgen-dr1` — ДР1 прицепной; все клики настоящие; с модами dev-окружения):** клик с земли по передней левой двери — открываются оба проёма группы (`DrL`+`DrL_3`, `DL`+`DL_3`); посадка через неё (у ДР1 — по полу, дотянутому до двери, пол 1.78); в тамбуре клик по его двери в салон (`FrontD`, `ID1`) — открылась; по проходу между сиденьями шаг **ровно 0.1200 каждый тик** (133 и 137 тиков, рывков нет); у ЭР2 — до закрытой двери заднего тамбура (z −7.68). ## 10. Звук и тряска (решение 1.5, 2026-10-11)

**Запрос пользователя:** «добавить звуки и тряску вагонов» (закрывает пункт v0.5 «звук, первый проход»). Обе вещи — **клиентская косметика**: по сети идёт только то, чего клиент не выведет сам — зажатые машинистом тифон и свисток (бит в снимке состава); остальное каждый клиент выводит из уже синхронизированного (`s`, `v`, рукоятки, двери). Сервер и физика не меняются.

### 10.1 Рельсовые стыки
Звеньевой путь, рельс 25 м (`TrackPath.JOINT_SPACING`). Стыки укладываются **от узлов каждого сегмента**: 0, 25, 50 … от его начального узла плюс стык в каждом узле; маршрут, идущий по сегменту задом, встречает те же стыки с другого конца — стык стоит на месте пути для любого поезда (`RoutePath.jointIndex`/`jointDistance`; прямая отладочная дорога — равномерно по `s`). `jointIndex(s)` — ступенька: сколько стыков тележка проехала за тик — разность двух значений.

### 10.2 Тряска кузова (`kinematics.RideMotion`)
Кузов на рессорах — три затухающих осциллятора: подпрыгивание (1.3 Гц, ζ 0.25), галопирование (1.6 Гц, 0.3), боковая качка (0.9 Гц, 0.15). Их тянет то, что задают путь и движение:
- **неровности пути** под каждой тележкой — гладкий шум от её `s` (октавы 31/13/5.7 м), вертикальный и боковой, растёт со скоростью (полная сила на 90 км/ч, до ×1.6); собственные частоты фильтруют его — кузов качается около раза в секунду, сильнее всего на резонансной скорости;
- **стыки** — тележка, переехавшая стык, бьёт кузов вниз на своём конце — в тот же тик, что звучит её «та-так»;
- **кривые** — кузов кренится наружу на непогашенное поперечное ускорение `v²·κ` (возвышения наружного рельса у нас нет), не больше 2.9°;
- **разгон и торможение** — клевок по инерции (до 1.7°); удар или сцепка — скачок скорости, рывок.

Стоящий состав успокаивается ровно. По умолчанию на 50 км/ч: крен ~0.3° RMS (пики ~0.8°), подпрыгивание ~6 мм RMS (пики ~1.8 см); на 90 км/ч — ~0.6° (пики ~1.5°) и ~1.2 см (пики ~4 см). Настоящие вагоны качаются в разы меньше — в игре этого не было бы видно (первая настройка, вдвое тише, в прогоне оказалась незаметной). Шаг — раз в клиентский тик, по позе тика и скорости на часах воспроизведения (`ClientConsists.tickSpeed`); рендер интерполирует окно тика, как и позу (`client.ClientRide`).
Применяется (`kinematics.Sway`: подъём, тангаж, крен в кадре позы, центр качания 1 м над путём): к **кузову** в рендере (тележки остаются на рельсе); к **пассажирам и машинисту** — они ставятся на качающийся кузов (`positionRider`, только клиент), глаз едет с вагоном; к **камере** едущего — крен и наклон кузова в проекции на взгляд (`client.ClientRideCamera`, `ViewportEvent.ComputeCameraAngles`): вперёд — крен вагона = крен взгляда, в боковое окно — взгляд кивает. Сервер, коллизия корпуса и лучи кликов работают без тряски (разница — сантиметры).
Клиентские настройки (`config/railswheelsandtrains-client.toml`): `swayStrength` (0–3, по умолчанию 1), `cameraSway` (0–1, по умолчанию 1 — камера часть вагона; 0 — горизонт не качается).

### 10.3 Звуки из пака
Декларация — в клиентской модели, поле `"sounds"` (`assets/<ns>/wagon_models/<id>.json`, разбор `client.sound.SoundSet`); ключи — IR: `idle` — двигатель, `horn` — тифон, `bell` — второй сигнал (у MVP — свисток), `wheels` — качение, `clack` — тележка на стыке, `doors` — по id двери, `controls` — по ключу органа IR (`"THROTTLE_1": {"move": …}`, `"TRAIN_BRAKE_1": {"engage": …}`):
```json
"sounds": {
  "idle": { "main": "stock/sounds/diesel/mvp_chme3/idle.ogg", "pitch": [1.0, 1.5], "volume": [0.55, 1.0] },
  "horn": "stock/sounds/diesel/mvp_chme3/horn.ogg",
  "bell": "stock/sounds/diesel/mvp_chme3/bell.ogg",
  "wheels": "stock/sounds/default/mvp_freight_stock_wheels.ogg",
  "clack": "stock/sounds/default/mvp_clack_wheelset_2-axle.ogg",
  "doors": { "door1": "stock/sounds/control/door/mvp_controls_door_close_1.ogg" },
  "controls": { "THROTTLE_1": { "move": "stock/sounds/control/switch/mvp_control_throttle.ogg" } }
}
```
Звук — путь к `.ogg` в любом месте пака (без неймспейса — неймспейс пака) или id звукового события из `sounds.json` (`"minecraft:entity.minecart.riding"`); для файлов `sounds.json` не нужен — декларация и есть регистрация. Петля — звук или `{start, main, stop}`; `pitch`/`volume` — диапазон от покоя до полного (тяга у `idle`, скорость у `wheels`).

Что звучит (`client.sound.TrainSounds`, каждый клиентский тик, вагоны в слышимости):
- **колёса** — петля, высота 0.7→1.3 и громкость по скорости (до 100 км/ч), затихают ниже 6 км/ч; у типа без звука колёс — вагонетка Minecraft;
- **стыки** — каждая тележка на каждом стыке, в своей точке, громче и выше со скоростью;
- **двигатель** — у вагонов с `idle`, пока поезд жив: машинист за пультом, или поезд едет, или открыта тяга; высота и громкость идут за тягой (~3 с вверх, ~1.5 с вниз); `start`/`stop` — запуск и останов (у ДР1);
- **двери** — свой звук при открытии и закрытии (нет — железная дверь); сервер звук двери больше не играет — каждый клиент озвучивает изменившиеся двери сам;
- **органы** ведущей кабины — `move` на каждый нотч рукоятки (тяга, тормоза, реверсор), `engage` (шипение крана) — если прежнее уже отзвучало;
- **тифон (`H`) и свисток (`J`)** — пока клавиша зажата; бит в `DriveInputPayload` → `Consist.signals` (транзиентно, без машиниста — ноль) → снимок → все клиенты; звучат с крыши ведущей кабины. Одиночный файл — как в IR: целиком, снова и снова, пока держат; отпустили — короткий (≤ 4 с) доигрывает, длинная запись обрывается. `{start, main, stop}` — начало, петля, хвост (ДР1).

Дальности: колёса 48, стыки 40, двигатель 64, тифон 192, свисток 128, двери 24, органы 16 блоков. Петли — только ближайшим 16 вагонам (колёса) и 8 (двигатели): каналов у звукового движка несколько сотен на всю игру. Громкость — ползунок «Дружелюбные существа» × клиентский `trainVolume` (0–2).
**Стерео:** OpenAL размещает в мире только моно-звуки — стерео-файл звучит одинаково громко на всей дальности. Многие файлы MVP стерео (колёса, стыки, двери), а переделывать их нельзя (CC BY-NC-ND, файлы байт-в-байт), поэтому громкость стерео-файла гасит по расстоянию сам мод — линейно до нуля на дальности, как OpenAL моно. Длительность и число каналов читаются из заголовков Ogg (`client.sound.OggLength`). Отладка: `/rwatc sounds` — что звучит сейчас.

### 10.4 Конвертер
`ir2rwat.py` переносит IR `sounds` (`idle`, `horn`, `bell`, `wheels`, `clack`; из `controls` — только `move`/`engage`) и звуки анимаций дверей (`sound.start` группы, совпадающей с id двери) в `"sounds"` модели; файлы — байт-в-байт в `<root>/sounds/…`. `sound_defaults` рецепта заполняет то, что IR берёт из своих встроенных звуков: колёса по категории (MVP: локомотивы, грузовые и цистерны — `mvp_freight_stock_wheels`, пассажирские — `mvp_pass_stock_wheels`) и стук стыков — всем. Диапазон двигателя — по IR `era`: дизель — высота 1.0→1.5, громкость 0.55→1.0; электро — 1.0→1.12, 0.45→0.9. М62 ссылается на встроенные звуки самого IR (`default/pressure`, `default/lever_engage`) — их в MVP нет, пропускаются с предупреждением.

**Статус (2026-10-11):** сборка + 425 юнит-тестов зелёные (`RailJointsTest`, `RideMotionTest`, `SoundSetTest` — разбор, заголовки Ogg и все ссылки сгенерированного MVP на месте).

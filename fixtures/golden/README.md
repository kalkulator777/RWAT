# Эталонные данные (golden)

Общий вход для тестов логики, у которой есть порты (решение R9 в `docs/roadmap.md`):
- Java — источник правды, тест `src/test/java/.../golden/GoldenTest.java`;
- Python-инструменты — `tools/tests/test_golden.py`, только портированное;
- TypeScript — будущий веб-редактор.

Расхождение порта с движком ловит тест того порта, который разошёлся.

## Формат

Одна логика — один файл JSON:

```json
{
  "$comment": "что за логика, какой класс, что во входе и в ожидаемом",
  "cases": [
    {"name": "уникальное имя случая", "input": {…}, "expected": …}
  ]
}
```

- `input` пишет человек. `expected` считает Java, руками его не правят.
- Числа — обычные числа JSON. NaN и «нет значения» записываются как `null`: в JSON нет NaN.
- Координаты — в кадре, который назван в `$comment` файла:
  - OBJ — кадр пака;
  - модели — кадр движка (`stock.ObjFrame`).
- В каждом файле от 10 до 40 случаев. Меньше десяти не пропустит `GoldenTest`.

## Как сверять

Java сверяет `expected` с результатом как JSON, точно: значения посчитала она сама.

Порты (Python, TypeScript) сверяют так:
- числа — с допуском `1e-9`, потому что порядок операций с плавающей точкой может отличаться;
- `null` в ожидаемом совпадает и с `null`, и с NaN;
- строки и логические значения — точно.

## Как обновить

Логика поменялась намеренно, или добавлен случай (новый случай пишется с `"expected": null`):

```sh
./gradlew test --tests '*GoldenTest' -Dgolden.update=true
git diff fixtures/golden      # каждое изменённое ожидание должно быть объяснимо
./gradlew test                # без флага всё зелёное
python -I -m unittest discover tools/tests
```

- С флагом `GoldenTest` переписывает файлы: `expected` берётся из кода, остальное форматируется заново. `build.gradle` передаёт флаг в JVM тестов.
- Без флага тест сверяет и при расхождении называет случай.
- Изменённые эталоны коммитятся вместе с правкой кода и правкой портов.
- Без флага переписать ожидание нельзя. Порт, который разошёлся с движком, правится сам, а не через эталон.

| `obj_frame.json` | `stock.ObjFrame` | `floorgen.point_from_obj` / `point_to_obj` / `box_from_obj` / `box_to_obj` | точка или коробка из кадра OBJ в кадр модели и обратно |
| `pivot_axis.json` | `convention.PivotAxis` | — | углы граней маркера `…_ROT…` в порядке файла → число точек, шарнир, ось |

## Что знать порту

- **Шарнир (`pivot_axis`).**
  - Входные углы — числа float32, как их читает загрузчик OBJ: в TypeScript `Math.fround` каждой координаты до расчёта. Сам расчёт идёт в double.
  - Порядок углов важен. У симметричного маркера (коробки) знак оси решает первая вершина файла, как в IR.
  - Точки — каждая позиция один раз, первое появление. `-0` и `0` — одна позиция.
- **`.anim`.** Кадры — float32. `model` — кадр, переведённый в кадр модели с подъёмом `ObjFrame.Y_LIFT` (0.43625), построчно (row-major), как в файле.
- **Пол (`floor`).**
  - Кадр модели: так тип хранит движок. Пак пишет кадр OBJ, и редактор переводит его через `obj_frame`.
  - `margin` по умолчанию — 0.3, полуширина игрока.
  - Дверь режет пол, только если она `inner`, не `fixed` и закрыта (бит `open`).
- **Замечания (`floor_check`).** Текст — английский, как в логе движка. Порт должен совпасть дословно, вместе с числами (`%.2f` — округление половины от нуля, `Locale.ROOT`).
- **Створки (`door_leaves`).**
  - Тип для поиска двери — обёртка `{"length": 30, "bogies": [8, -8], "mass_t": 40, "doors": …}`: на ответ влияют только двери.
  - Коробка створки — объединение коробок объектов с текстурой. Её центр переводится в кадр модели и ищется в коробках дверей с запасом 0.1.
- **Пробелы.**
  - `object_names`: пробелом считаются символы до U+0020 (как `String.trim`). Неразрывный пробел — часть имени.
  - `material_names`: случаи только с ASCII-пробелами. На прочих пробелах Unicode Java и Python расходятся: `Character.isWhitespace` против `str.split`.
